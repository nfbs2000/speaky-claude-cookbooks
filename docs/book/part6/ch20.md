# 20장: AgentDefinition과 실제 worker 위임

> 공개 GitHub Pages 투영판: [20장: 에이전트 생성과 오케스트레이션](https://nfbs2000.github.io/speaky-claude-cookbooks/book/part6/ch20/)
>
> 실제 실행 판독: [20장 실제 SDK 관찰: AgentDefinition에서 leader synthesis까지](../evidence/ch20-live.md)

멀티 에이전트를 가르칠 때 `AgentDefinition`을 선언한 것만으로 worker가 실행됐다고
말하면 안 됩니다. Parent의 Agent ToolUse, worker의 nested tool event, task lifecycle,
worker 결과, leader 종합이 같은 ID 사슬로 이어져야 실제 위임입니다.

## 20.1 핵심 질문

> Leader가 worker를 실제로 호출했고, worker가 자기 도구로 근거를 읽은 뒤, leader가 그 결과를 받았는가?

## 20.2 현재 Python SDK의 AgentDefinition

설치된 Python Agent SDK 0.2.128의 `AgentDefinition`에서 직접 확인한 필드는 다음과
같습니다. Python option은 `Options.agents`가 아니라 `ClaudeAgentOptions.agents`입니다.

| 필드 | 현재 타입에서 확인한 의미 |
| --- | --- |
| `description` | leader가 이 worker의 용도를 판단할 설명 |
| `prompt` | worker 지침 |
| `tools` | worker에게 노출할 도구 |
| `disallowedTools` | worker에서 제거할 도구 |
| `model` | alias, full model ID 또는 `inherit` |
| `skills` | worker에 연결할 skill 이름 |
| `memory` | `user/project/local` memory source |
| `mcpServers` | worker의 MCP server 목록 |
| `initialPrompt` | main-thread agent로 시작할 때의 초기 prompt |
| `maxTurns` | worker turn 제한 |
| `background` | background 실행 설정 |
| `effort` | worker effort |
| `permissionMode` | worker permission mode |

책의 기존 설명처럼 권한은 선언만 보고 단정하지 않습니다. Parent options와 worker
definition, permission/hook/sandbox, 실제 ToolUse·handler 결과를 함께 봐야 합니다.

## 20.3 Python 메시지 이름 정정

현재 Python SDK에서 task lifecycle class는 다음 네 개입니다.

```text
TaskStartedMessage
TaskProgressMessage
TaskUpdatedMessage
TaskNotificationMessage
```

`SDKTaskStartedMessage`, `SDKTaskProgressMessage`, `SDKTaskUpdatedMessage`,
`SDKTaskNotificationMessage`라는 Python class는 없습니다. 또한 설치된
`ClaudeAgentOptions`에는 `forwardSubagentText`와 `agentProgressSummaries` 필드가
없습니다. 이들은 다른 언어 binding이나 CLI surface와 섞어서 Python option처럼 쓰면
안 됩니다.

이번 Python run은 두 option을 주지 않아도 nested transcript와 task progress를
수신했습니다. 이것은 이번 버전/foreground worker의 관찰 결과이지 모든 버전의 전달
정책을 보장하는 주장은 아닙니다.

## 20.4 실제 controlled delegation

실험은 parent와 worker의 책임을 분리했습니다.

```text
Leader tools: Agent, Read
Worker: evidence-reader
Worker tools: Read
Worker disallowed: Agent, Bash, Edit, Write
Worker model: inherit
Evidence file: worker/evidence.txt
```

Leader는 직접 파일을 읽지 말고 Agent를 정확히 한 번 호출하게 했습니다. Worker는
파일을 정확히 한 번 읽고 `WORKER_RETURN:CH20_WORKER_EVIDENCE_CONTENT`를 반환합니다.
Leader는 그 결과를 받은 뒤 `LEADER_SYNTHESIS_CONFIRMED:...`를 반환합니다.

- attempt: `131541-c05b4d89`
- OTel trace: `702e839fcfbb947dc492d57eb4af8c52`
- actual response model: 네 `AssistantMessage.model` 모두 `claude-opus-5`
- worker `resolvedModel`: `claude-opus-5`
- provider usage boundary: terminal `model_usage`에는 Opus 5와 보조 Haiku 4.5가 함께 있음
- terminal status: success

`requested_model`, init의 model, worker의 `inherit` 선언만으로 actual model을 판정하지
않습니다. 이 attempt의 보이는 leader/worker 응답은 원시 `AssistantMessage.model` 네 건으로
Opus 5임을 확인했습니다. 다만 terminal Result는
`claude-haiku-4-5-20251001`의 보조 사용량도 보고하므로, provider run 전체를
"Opus-only"라고 부르지 않습니다.

## 20.5 실제 event 사슬

```text
sequence 19  Agent ToolUse
  tool_use_id = toolu_01XVBQy3MKeFB1KBAXXxGFWJ
  subagent_type = evidence-reader

sequence 20  TaskStartedMessage
  task_id = adfa31ba06e619f29
  tool_use_id = parent Agent ID

sequence 22  nested worker prompt
  parent_tool_use_id = parent Agent ID

sequence 25  TaskProgressMessage
  last_tool_name = Read
  tool_uses = 1

sequence 26  worker Read ToolUse
  parent_tool_use_id = parent Agent ID

sequence 27  worker ToolResult
  parent_tool_use_id = parent Agent ID
  content = CH20_WORKER_EVIDENCE_CONTENT

sequence 28  TaskUpdatedMessage(status=completed)
sequence 29  TaskNotificationMessage(status=completed, worker marker)
sequence 30  parent Agent ToolResult(worker marker, resolvedModel=opus-5)
sequence 36  leader synthesis
sequence 40  successful terminal Result
```

이 사슬은 `configured agent`와 `observed worker`를 분리합니다. `agents` map에
`evidence-reader`가 있었다는 사실은 configured이고, sequence 19 이후의 사건이 실제
실행 증거입니다.

### `Agent`와 init의 `Task`

이 run은 options에 `tools=["Agent", "Read"]`를 넘겼습니다. 그러나
`SystemMessage.init.tools`는 `["Task", "Read"]`로 나타났고 실제 delegation
`ToolUseBlock.name`은 `Agent`였습니다. UI나 projector가 한 이름만 가정하면 위임을
놓칠 수 있으므로 configured name, init exposure, actual ToolUse를 각각 보존해야 합니다.

### task terminal을 하나만 가정하지 않기

이번 foreground run에서는 `TaskUpdatedMessage(status="completed")`와
`TaskNotificationMessage(status="completed")`가 모두 왔습니다. SDK type docstring은
background task가 notification 없이 terminal `TaskUpdatedMessage`만 보낼 수도 있다고
설명합니다. Task tracker는 두 terminal surface 중 어느 쪽이 와도 active task를
정리해야 합니다.

## 20.6 이번 실행으로 증명하지 않은 것

| 주장 | 현재 분류 | 이유 |
| --- | --- | --- |
| standard foreground subagent 위임 | observed | Agent/worker/task/result 사슬 존재 |
| worker가 parent 전체 context를 상속하는 fork mode | 미관찰 | context 상속 대조 없음 |
| 여러 worker의 병렬 실행 | 미관찰 | worker 1명만 순차 실행 |
| validator가 다른 worker를 독립 검증 | 미관찰 | validator run 없음 |
| native Team mailbox/claim loop | 미관찰 | Agent delegation만 실행 |
| remote bridge/planner | 미관찰 | 외부 실행 주체 없음 |
| background worker의 단독 terminal 경로 | 미관찰 | foreground worker만 실행 |
| worker 금지 도구의 실제 deny | 미관찰 | 허용된 Read만 실행 |

한 worker 실행을 native team, remote planner, 병렬 swarm으로 확대 해석하지 않습니다.

## 20.7 시각화 원칙

```text
configured AgentDefinition
  -> Agent ToolUse
  -> TaskStarted
  -> nested worker prompt
  -> worker ToolUse
  -> worker ToolResult
  -> task terminal
  -> Agent ToolResult
  -> leader synthesis
```

Worker lane의 모든 nested message에 `parent_tool_use_id`를 표시하고, task lifecycle은
`task_id`와 parent Agent `tool_use_id`를 함께 보존합니다. Worker 결과와 leader 최종
문장은 서로 다른 노드여야 합니다.

## 20.8 학생 실습

```text
하나의 read-only worker를 AgentDefinition으로 정의하고 실제 실행한다.

1. worker tools를 Read 하나로 제한한다.
2. leader가 Agent를 한 번 호출하게 한다.
3. Agent/Task 명칭 차이를 원시 event로 기록한다.
4. nested Read와 ToolResult의 parent_tool_use_id를 확인한다.
5. task terminal과 leader Result를 연결한다.
6. 실행하지 않은 fork/team/remote 기능은 observed로 표시하지 않는다.
```

## Takeaway

멀티 에이전트의 증거는 역할 설명이 아니라 연결된 실행 사슬입니다. 이번 실제 Opus 5
run은 한 read-only worker의 위임, nested Read, task lifecycle, worker 반환, leader
종합을 증명했습니다. 팀이나 원격 오케스트레이션은 별도 실행 증거가 생기기 전까지
다른 범주로 남겨 둡니다.
