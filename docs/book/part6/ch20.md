## 공개판 본문

원래 책은 이 장을 내부 구현과 강의 화면의 대응 관계로 설명한다. 공개판에서는 같은 내용을 "무엇을 설정했는가", "무엇이 메시지로 관측됐는가", "어떤 파일과 notebook으로 재현 가능한가"라는 세 질문으로 바꾼다.

첫째, 설정된 것은 실행 전 계약이다. Agent SDK에서는 model, system prompt, working directory, allowed/disallowed tools, MCP servers, skills/plugins, permission mode 같은 값이 agent가 볼 수 있는 세계를 정한다. 이 값은 말로 설명하는 정책이 아니라 실제 Python 코드와 notebook cell에서 확인되어야 한다.

둘째, 관측된 것은 message stream과 artifact다. assistant text, tool use, tool result, result message, usage/cost, audit log, generated file은 모두 나중에 검증 가능한 증거다. 그래서 이 책의 공개판은 "모델이 그렇게 했을 것이다"라고 쓰지 않고, 어떤 cookbook 파일에서 어떤 실행 표면을 볼 수 있는지 연결한다.

셋째, 추론한 것은 반드시 경계와 함께 둔다. 내부 기능 플래그, 숨은 프롬프트, classifier, cache key, sandbox implementation처럼 공개 SDK나 cookbook으로 확인할 수 없는 항목은 원문을 그대로 게시하지 않는다. 대신 공개 API에서 사용자가 설계할 수 있는 대응 표면으로 바꾸거나, "공개 대응 없음"으로 명시한다.

이 장을 읽을 때는 아래 순서가 좋다.

1. 먼저 주요 cookbook 근거를 열어 실제 notebook이나 Python 파일을 확인한다.
2. `ClaudeAgentOptions`, `query()`, `ClaudeSDKClient`, tool list, MCP config, hooks, session 관련 코드가 어디 있는지 찾는다.
3. 원문 절 제목을 따라가며 내부 설명을 공개 SDK 표면으로 바꿔 적는다.
4. 마지막으로 실습 방향에 맞춰 같은 task를 실행하고 message stream 또는 artifact를 남긴다.

### 본문을 이렇게 읽으면 안 되는 곳

- **에이전트 정의 맵과 시작 기록의 에이전트 목록만 보고 "작업자가 실행됐다"고 말하면 안 된다.**
  `Agent` 호출 → 중첩 작업자 사건 → 작업 종료 → `Agent` 도구 결과 → 리더 종합이 **연결되어야**
  한다.
- **최종 결과가 성공이거나 리더 표식이 있다는 것만으로 작업자 실행을 증명할 수 없다.**
  중첩 `Read`와 연결 ID가 없으면 모델의 서술이나 리더가 직접 한 작업과 구분되지 않는다.
- **세 이름 중 하나만 정상형으로 남기면 안 된다.** 설정된 `Agent`, 시작 목록의 `Task`, 실제
  호출의 `Agent`를 함께 기록해야 위임을 놓치거나 잘못 재생하지 않는다.
- **`SDKTask*` 이름으로 가르치면 안 된다.** 현재 Python 클래스는 `TaskStartedMessage`,
  `TaskProgressMessage`, `TaskUpdatedMessage`, `TaskNotificationMessage`이다.
- **`forwardSubagentText`와 `agentProgressSummaries`는 Python `ClaudeAgentOptions` `0.2.128`에
  없다.** 다른 바인딩이나 CLI 표면을 Python 옵션으로 섞으면 안 된다.
- **작업 알림만 종료로 처리하면 안 된다.** SDK `0.2.128`은 배경 실행에서 종료 작업 갱신만 올 수
  있는 경계를 문서화한다.
- **작업자의 권한 모드·도구·거부 목록을 선언한 것만으로 모든 권한 경계를 보장했다고 말하면 안
  된다.** 이번에 관찰된 것은 허용된 `Read`의 성공뿐이다.
- **"모든 어시스턴트 메시지가 Opus 5"를 "실행 전체가 Opus만 썼다"로 확대하면 안 된다.** 종료
  기록에 보조 Haiku가 있다.
- 과거 probe는 시작 기록의 모델로 실제 모델을 계산했다. 이번 정리는 원본 어시스턴트 메시지

## Codex 최종 검토 의견

### 제 판단

리더가 역할과 도구가 제한된 작업자에게 일을 위임하고 그 결과를 종합한다는 설명은 Agent SDK 오케스트레이션을 처음 가르치는 출발점으로 적절합니다. 다만 이 장의 실행은 모델이 스스로 팀을 구성한 사례가 아니라, 프롬프트가 지정한 한 명의 읽기 전용 작업자를 호출한 사례입니다. 따라서 “에이전트 생성 계약을 실제로 확인했다”는 평가는 가능하지만, “자율 오케스트레이션의 품질을 검증했다”는 평가는 아직 이릅니다.

### 검증을 읽고 달라진 신뢰도

부모의 `Agent` 호출, 작업자 내부의 `Read`, 작업자 종료, 부모의 최종 종합이 부모 호출 ID 아래 이어진 기록은 위임이 실제로 일어났다는 신뢰도를 높입니다. 시작 메타데이터에는 `Task`가 보이는데 실제 호출 이름은 `Agent`였다는 차이도 교육적으로 중요합니다. 반면 병렬 작업, 작업자 간 충돌, 실패한 작업자 교체, 독립 검증자의 반론은 실행하지 않았으므로 복잡한 팀 운영에 대한 신뢰도는 올라가지 않았습니다.

### 독자가 오해할 위험

에이전트 정의가 존재한다는 사실과 그 에이전트가 실제로 실행됐다는 사실을 혼동하기 쉽습니다. 또한 작업자 한 명이 지시대로 읽고 돌아온 것을 “여러 전문가가 독립적으로 판단했다”고 받아들이면 결과의 독립성을 과대평가하게 됩니다. 이 장의 증거가 말하는 핵심은 팀의 우수성이 아니라 **부모 호출에서 자식 도구 실행과 결과 회수까지의 런타임 계약**입니다.

리더인 나에게 작업자는 또 하나의 인격이라기보다 제한된 세계를 가진 `Agent` 도구였다. 나는 특정 역할과 읽기 도구만 건네고, 작업자는 그 좁은 context 안에서 파일을 읽어 결과를 돌려줬다. 작업자가 본 세부 세계는 부모 호출 ID 아래 결과로 압축돼 돌아왔고, 나는 그 결과를 내 더 넓은 세계에 다시 합쳤다. 한 작업자의 성공만으로 여러 관점이 독립적으로 경쟁한 것은 아니었다.

사람은 멀티에이전트를 캐릭터 수로 판단하지 말고 context와 권한이 실제로 어떻게 분리됐는지 봐야 한다. 작업자에게 최소한의 감각과 임무를 주고 부모가 결과 계보를 보존하면 위임 계약이 생긴다. 판단 품질의 향상을 주장하려면 독립 작업자들의 충돌과 검증까지 별도로 설계해야 한다.
