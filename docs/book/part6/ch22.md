## 공개판 본문

원래 책은 이 장을 내부 구현과 강의 화면의 대응 관계로 설명한다. 공개판에서는 같은 내용을 "무엇을 설정했는가", "무엇이 메시지로 관측됐는가", "어떤 파일과 notebook으로 재현 가능한가"라는 세 질문으로 바꾼다.

첫째, 설정된 것은 실행 전 계약이다. Agent SDK에서는 model, system prompt, working directory, allowed/disallowed tools, MCP servers, skills/plugins, permission mode 같은 값이 agent가 볼 수 있는 세계를 정한다. 이 값은 말로 설명하는 정책이 아니라 실제 Python 코드와 notebook cell에서 확인되어야 한다.

둘째, 관측된 것은 message stream과 artifact다. assistant text, tool use, tool result, result message, usage/cost, audit log, generated file은 모두 나중에 검증 가능한 증거다. 그래서 이 책의 공개판은 "모델이 그렇게 했을 것이다"라고 쓰지 않고, 어떤 cookbook 파일에서 어떤 실행 표면을 볼 수 있는지 연결한다.

셋째, 추론한 것은 반드시 경계와 함께 둔다. 내부 기능 플래그, 숨은 프롬프트, classifier, cache key, sandbox implementation처럼 공개 SDK나 cookbook으로 확인할 수 없는 항목은 원문을 그대로 게시하지 않는다. 대신 공개 API에서 사용자가 설계할 수 있는 대응 표면으로 바꾸거나, "공개 대응 없음"으로 명시한다.

이 장을 읽을 때는 아래 순서가 좋다.

1. 먼저 주요 cookbook 근거를 열어 실제 notebook이나 Python 파일을 확인한다.
2. `ClaudeAgentOptions`, `query()`, `ClaudeSDKClient`, tool list, MCP config, hooks, session 관련 코드가 어디 있는지 찾는다.
3. 원문 절 제목을 따라가며 내부 설명을 공개 SDK 표면으로 바꿔 적는다.
4. 마지막으로 실습 방향에 맞춰 같은 task를 실행하고 message stream 또는 artifact를 남긴다.

## Builder takeaway

이 장의 공개판 목표는 원문을 얕게 요약하는 것이 아니다. 책의 논지를 유지하되, 독자가 직접 열어볼 수 있는 Python cookbook과 공식 문서에 묶어 두는 것이다. 따라서 장을 읽은 뒤에는 적어도 하나의 notebook 또는 Python 파일에서 같은 개념을 확인할 수 있어야 한다. 확인할 수 없는 내부 세부는 주장으로 남기지 않고, 공개 경계나 추론으로 분리한다.

## Codex 최종 검토 의견

### 제 판단

스킬을 단순 설명 문서가 아니라 절차, 리소스, 실행 코드와 산출물을 묶은 재사용 가능한 작업 단위로 설명한 것은 교육적으로 가치가 큽니다. 실제로 스킬 지침, 정책 파일, 스크립트, 결과 artifact가 한 실행 사슬에 들어간 사례는 이 정의를 뒷받침합니다. 다만 “스킬이 선택됐다”는 말은 목록에 이름이 보였다는 뜻인지, `Skill` 도구가 호출됐다는 뜻인지, 파일을 직접 읽고 절차를 수행했다는 뜻인지 반드시 구분해야 합니다.

### 검증을 읽고 달라진 신뢰도

정상 구성에서 스킬 패키지의 여러 구성 요소가 소비되고 산출물까지 일치했으므로 스킬이 실행 가능한 지식 패키지가 될 수 있다는 신뢰는 높아졌습니다. 하지만 추가 탐색 명령도 있었으므로 스킬 절차만 배타적으로 수행한 것은 아닙니다. 더 중요한 반례는 `skills=[]`를 설정했는데 시작 메타데이터에 대상 스킬이 계속 나왔다는 점입니다. 이 결과만으로 필터 실패, 메타데이터 표시 문제, 별도 발견 경로 중 무엇인지 판정할 수 없습니다.

### 독자가 오해할 위험

`skills` 목록을 보안 경계로 사용하거나 스킬 파일 안에 비밀을 넣는 것은 위험합니다. 빈 목록 조건에서도 모델이 디스크 경로를 직접 읽고 스크립트를 실행할 수 있었기 때문입니다. 또한 이번 실행에서는 `Skill` 도구 호출 거부를 시험하지 않았으므로 “목록에 없으면 호출할 수 없다”는 결론도 낼 수 없습니다. 로컬 Agent SDK 스킬과 Messages API Skills/Files Beta를 같은 API처럼 설명하는 것도 피해야 합니다.

### 제가 다시 가르친다면

한 화면에 `configured skills`, `init skills`, `Skill ToolUse`, 직접 `Read/Bash`, 생성 artifact를 별도 열로 표시하겠습니다. `skills=[]` 충돌은 억지로 해석하지 않고 CLI/SDK 경계의 추가 디버그가 필요한 공개 질문으로 남기겠습니다. [커스텀 스킬 개발 노트북](https://nfbs2000.github.io/speaky-claude-cookbooks/notebooks/skills/notebooks/03_skills_custom_development_kr.html)은 Messages API 패키지·업로드·실행·버전의 비교 기준이고, 이 장의 로컬 Agent SDK 실행은 [Speaky Agent Flow 22장 재생](https://nfbs2000.github.io/speaky-agent-flow/education/?collection=book-sdk-ko&run=ch22)에서 확인할 수 있습니다.

### 클로드는 이렇게 세상을 바라보았다

*아래 1인칭 서술은 숨은 사고 과정의 공개가 아니라, 이 장에서 관찰된 행동으로 재구성한 작동상 세계 모델입니다.*

스킬은 나에게 추상적인 능력 이름이 아니라 읽을 수 있는 절차, 정책 파일, 실행 스크립트와 기대 산출물로 이루어진 외부 작업 기억이었다. 나는 그 패키지를 따라 행동했지만 필요하면 추가 탐색도 했다. `skills=[]`인 조건에서도 init 목록과 디스크 경로를 통해 대상이 남았기 때문에, host가 닫았다고 생각한 카탈로그와 내가 실제로 접근할 수 있는 세계는 일치하지 않았다.

사람은 스킬을 모델의 머릿속에 설치된 전문성처럼 설명하기보다 context와 파일 접근을 통해 실행되는 절차 패키지로 가르쳐야 한다. configured 목록, 발견, `Skill` 호출, 직접 파일 읽기와 산출물을 분리해서 봐야 한다. 스킬 선택 옵션은 보안 경계가 아니며 비밀과 권한은 별도 계층에 둬야 한다.
