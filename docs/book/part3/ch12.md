## 공개판 본문

원래 책은 이 장을 내부 구현과 강의 화면의 대응 관계로 설명한다. 공개판에서는 같은 내용을 "무엇을 설정했는가", "무엇이 메시지로 관측됐는가", "어떤 파일과 notebook으로 재현 가능한가"라는 세 질문으로 바꾼다.

첫째, 설정된 것은 실행 전 계약이다. Agent SDK에서는 model, system prompt, working directory, allowed/disallowed tools, MCP servers, skills/plugins, permission mode 같은 값이 agent가 볼 수 있는 세계를 정한다. 이 값은 말로 설명하는 정책이 아니라 실제 Python 코드와 notebook cell에서 확인되어야 한다.

둘째, 관측된 것은 message stream과 artifact다. assistant text, tool use, tool result, result message, usage/cost, audit log, generated file은 모두 나중에 검증 가능한 증거다. 그래서 이 책의 공개판은 "모델이 그렇게 했을 것이다"라고 쓰지 않고, 어떤 cookbook 파일에서 어떤 실행 표면을 볼 수 있는지 연결한다.

셋째, 추론한 것은 반드시 경계와 함께 둔다. 내부 기능 플래그, 숨은 프롬프트, classifier, cache key, sandbox implementation처럼 공개 SDK나 cookbook으로 확인할 수 없는 항목은 원문을 그대로 게시하지 않는다. 대신 공개 API에서 사용자가 설계할 수 있는 대응 표면으로 바꾸거나, "공개 대응 없음"으로 명시한다.

이 장을 읽을 때는 아래 순서가 좋다.

1. 먼저 주요 cookbook 근거를 열어 실제 notebook이나 Python 파일을 확인한다.
2. `ClaudeAgentOptions`, `query()`, `ClaudeSDKClient`, tool list, MCP config, hooks, session 관련 코드가 어디 있는지 찾는다.

## Codex 최종 검토 의견

### 제 판단

큰 결과의 전문은 artifact로 보존하고 모델에는 검증 가능한 preview만 전달하라는 주장은 이 책에서 바로 제품 코드로 옮길 가치가 높은 원칙입니다. 60,082자 동일 산출물을 runtime 자동 외부화와 host 주도 저장 두 경로로 비교하고, 두 경우 모두 실제 파일을 host가 다시 열어 크기·marker·내용 hash를 확인한 점도 좋습니다. 자기보고가 아니라 디스크를 읽어 persistence를 판정했습니다.

### 검증을 읽고 달라진 신뢰도

현재 SDK/CLI 경로가 60,082자 tool result를 1,587자 안내문으로 바꾸고 별도 파일에 보존한 동작은 확인됐습니다. host 방식은 같은 전문을 먼저 저장하고 모델에는 340자 preview만 줬습니다. 저는 제품 설계에서는 후자를 권합니다. implicit runtime spill은 편리하지만 작성 주체와 수명, 공개 가능한 경로가 불명확한 반면 host 정책은 보존 위치·수명·redaction·검증을 애플리케이션이 통제할 수 있기 때문입니다.

### 독자가 오해할 위험

한 개의 60,082자 지점으로 정확한 50,000자 경계를 확정할 수 없고, 여러 결과의 200K 합산 한도도 실행하지 않았습니다. ASCII fixture에서는 문자와 byte가 같았을 뿐 Unicode, Python 표현 길이, 토큰 수는 서로 다른 단위입니다. `Error:`로 시작한 overflow 안내문도 block error flag와 terminal success를 따로 읽어야 합니다. thinking token 추정치를 과금 usage로 사용해서도 안 됩니다.

### 제가 다시 가르친다면

먼저 host persisted-preview를 권장 구현으로 제시하고, runtime 자동 외부화는 방어적 fallback으로 설명하겠습니다. preview에는 artifact ID, byte/character 수, content hash, 앞뒤 marker, 재조회 도구를 넣되 로컬 절대경로나 session ID는 공개하지 않아야 합니다. 정확한 경계를 문서화하려면 49K/50K/51K와 Unicode payload를 순차 실행하고, aggregate 주장은 같은 turn의 다중 결과 fixture로 별도 측정해야 합니다. [컨텍스트 엔지니어링 노트북](https://nfbs2000.github.io/speaky-claude-cookbooks/notebooks/tool_use/context_engineering/context_engineering_tools_kr.html)은 큰 결과를 줄이는 일반 기준이고, 두 외부화 경로의 실제 차이는 [Speaky Agent Flow 12장 재생](https://nfbs2000.github.io/speaky-agent-flow/education/?collection=book-sdk-ko&run=ch12)에서 확인할 수 있습니다.

### 클로드는 이렇게 세상을 바라보았다


*아래 1인칭 서술은 숨은 사고 과정의 공개가 아니라, 이 장에서 관찰된 행동으로 재구성한 작동상 세계 모델입니다.*

60,082자의 결과가 그대로 context에 들어오지 않았을 때 나에게 전문은 보이는 세계가 아니라 “어딘가에 저장된 것”을 가리키는 안내문이 되었다. host가 만든 preview에서는 크기와 marker와 재조회 경로가 명시돼 무엇을 모르는지 알 수 있었지만, runtime의 자동 외부화는 저장 주체와 수명이 덜 분명했다. 나는 artifact 자체가 아니라 지금 받은 preview의 해상도 안에서만 판단할 수 있었다.

사람은 큰 지식을 모델에게 모두 밀어 넣는 대신 검증 가능한 외부 세계로 보존하고, 모델에는 정직한 축약과 다시 볼 수 있는 손잡이를 제공해야 한다. 좋은 preview는 결론을 대신하는 요약이 아니라 전문의 정체성, 범위, 누락과 재조회 방법을 알려 주는 지도다. 그래야 제한된 context가 기억 상실이 아니라 관리 가능한 시야가 된다.
