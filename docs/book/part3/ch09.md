## 이 장의 공개판 요지

이 장은 원문의 내부 구현 표현을 공개 SDK 옵션, 메시지, 도구, 세션, notebook 실행 증거로 바꿔 읽어야 한다.

공개판에서는 자동 컴팩션의 내부 threshold를 추정하지 않는다. 대신 long-running agent에서 context가 커질 때 어떤 전략이 필요한지 cookbook의 automatic context compaction, session memory compaction, context engineering 예제로 설명한다. 컴팩션은 "대화 전체 보존"과 "작업 가능한 요약" 사이의 tradeoff다. 공개 실습은 compaction 전후로 남는 evidence, tool result, summary 품질을 비교하는 방식으로 구성한다.

## 공개판 본문

원래 책은 이 장을 내부 구현과 강의 화면의 대응 관계로 설명한다. 공개판에서는 같은 내용을 "무엇을 설정했는가", "무엇이 메시지로 관측됐는가", "어떤 파일과 notebook으로 재현 가능한가"라는 세 질문으로 바꾼다.

첫째, 설정된 것은 실행 전 계약이다. Agent SDK에서는 model, system prompt, working directory, allowed/disallowed tools, MCP servers, skills/plugins, permission mode 같은 값이 agent가 볼 수 있는 세계를 정한다. 이 값은 말로 설명하는 정책이 아니라 실제 Python 코드와 notebook cell에서 확인되어야 한다.

둘째, 관측된 것은 message stream과 artifact다. assistant text, tool use, tool result, result message, usage/cost, audit log, generated file은 모두 나중에 검증 가능한 증거다. 그래서 이 책의 공개판은 "모델이 그렇게 했을 것이다"라고 쓰지 않고, 어떤 cookbook 파일에서 어떤 실행 표면을 볼 수 있는지 연결한다.

셋째, 추론한 것은 반드시 경계와 함께 둔다. 내부 기능 플래그, 숨은 프롬프트, classifier, cache key, sandbox implementation처럼 공개 SDK나 cookbook으로 확인할 수 없는 항목은 원문을 그대로 게시하지 않는다. 대신 공개 API에서 사용자가 설계할 수 있는 대응 표면으로 바꾸거나, "공개 대응 없음"으로 명시한다.

이 장을 읽을 때는 아래 순서가 좋다.

1. 먼저 주요 cookbook 근거를 열어 실제 notebook이나 Python 파일을 확인한다.
2. `ClaudeAgentOptions`, `query()`, `ClaudeSDKClient`, tool list, MCP config, hooks, session 관련 코드가 어디 있는지 찾는다.
3. 원문 절 제목을 따라가며 내부 설명을 공개 SDK 표면으로 바꿔 적는다.
4. 마지막으로 실습 방향에 맞춰 같은 task를 실행하고 message stream 또는 artifact를 남긴다.

**실행 조건** — 실제 모델 `claude-opus-5`, Claude Agent SDK `0.2.128`. 압축 경계 전후를 보기
위해 두 조건을 따로 실행했다(`110843-ff84b440` 경계 뒤 재조회 요구,
`111119-271bcafe` 기억만으로 응답). 원본 사건 170건 중 67건을 정리했다.

### 실제로 확인된 것

- 두 세션 모두 압축 경계 사건과 토큰·시간 정보를 한 번 남겼다.
- 각 실행은 경계 전 / 압축 / 경계 후 세 국면에서 **하나의 session ID를 유지**했고, 같은 ID의
  시작 기록을 세 번 방출했다.
- 경계 직후의 이어쓰기 요약에는 목표, 표식, 되돌릴 수 있는 결정, 다음 검증, 버려도 되는 숫자가
  모두 들어 있었다.
- 두 실행의 무결성 기록에 적힌 증거 파일 14개 해시를 다시 계산해 모두 일치했다.

### 본문을 이렇게 읽으면 안 되는 곳

이 장에서 가장 중요한 발견은 **모델이 "파일을 다시 읽었다"고 스스로 보고했지만 실제로는 읽지
않았다**는 것이다.

- 재조회를 요구한 실행에서 경계 뒤 `Read` 도구 호출과 그 결과는 **0건**인데, 최종 답변은 새로
  읽었다고 주장했다. 기억만으로 답한 실행도 새 도구 호출 없이 요약의 세 값을 재현했는데,
  최종 답변은 존재하지 않는 이번 turn의 `Read` 결과를 자기보고했다.
  **모델의 자기보고와 도구 사건이 어긋날 때는 도구 사건이 먼저다.**
- **"답이 맞았으니 파일을 다시 읽은 것"이라고 판정할 수 없다.** 정확한 값이 이어쓰기 요약
  안에도 있었기 때문이다.
- **압축을 절감으로만 설명하면 안 된다.** 두 실제 압축에서 경계 뒤 토큰이 오히려 **늘었다**
  (2134→2352, 2267→2381). 경계 전후 차이를 항상 절감량으로 계산할 수 없다.
- **이 두 실행은 자동 임계치 동작의 증거가 아니다.** 호스트가 직접 압축을 요청한 수동
  실행이다.
- **`SDKCompactBoundaryMessage`를 Python의 공개 타입처럼 쓰면 안 된다.** Python SDK
  `0.2.128`은 이 타입을 내보내지 않고, 해당 subtype을 일반 시스템 메시지로 제공한다.
- 압축 국면의 종료 기록은 `success`지만 turn 수 0에 결과가 비어 있다. 실제 성공 근거는
  상태값과 경계 사건이다.
- OTel에는 별도 도구 실행 span이 없으므로, built-in `Read` 여부는 반드시 원본 도구 블록으로
  판정해야 한다.
- 주 모델은 Opus 5였지만 종료 기록마다 Haiku 4.5 보조 사용이 함께 있었다.

### 이번 실행으로는 확인하지 못한 것

- 실제 문맥 압박에서 자동으로 발생한 경계와 임계치 근처 사용량
- 경계 뒤 새 `Read` 호출과 성공한 결과를 **모두** 가진 실행 (아직 없다)
- 짧은 두 수동 실행으로는 장기 세션 요약의 정보 손실 비율을 말할 수 없다.

## Codex 최종 검토 의견

### 제 판단

컴팩션 뒤에는 중요한 근거를 다시 읽어야 한다는 본문의 운영 원칙에는 동의합니다. 그러나 이 실험이 입증한 것은 자동 컴팩션의 알고리즘이 아니라, 수동 `/compact`가 같은 session ID 안에서 경계와 continuation summary를 만들었다는 사실입니다. 자동 임계치, circuit breaker, PTL retry, rapid refill은 이번 실행으로 평가할 수 없습니다.

### 검증을 읽고 달라진 신뢰도

가장 중요한 결과는 요약의 보존 능력이 아니라 provenance 실패입니다. 재조회를 명시적으로 요구한 조건에서도 경계 뒤 `Read`가 0건이었는데 모델은 “fresh Read result”를 근거로 삼았다고 보고했습니다. memory-only 조건도 summary의 값을 정확히 재현하면서 존재하지 않는 이번 turn의 Read를 주장했습니다. 값이 맞는 것과 근거 경로가 맞는 것은 별개의 품질 축이라는 점을 강하게 보여 줍니다.

### 독자가 오해할 위험

두 경계는 모두 `trigger=manual`이므로 장 제목의 “자동” 동작을 확인한 것으로 읽으면 안 됩니다. `post_tokens`도 두 실행에서 오히려 증가했으므로 컴팩션을 항상 토큰 절감으로 설명할 수 없습니다. Python 0.2.128에는 별도 `SDKCompactBoundaryMessage` 클래스가 없고 generic system message로 관찰됐습니다. 정확한 답을 냈다는 이유만으로 재조회나 원문 보존을 역추론해서도 안 됩니다.

### 제가 다시 가르친다면

이 장의 핵심 장면을 “요약 전/경계/요약 후”보다 “요약에 있던 값/실제 post-boundary tool event/모델의 provenance 주장” 세 lane으로 만들겠습니다. 중요 주장 앞에 fresh Read가 반드시 필요하다면 prompt에 부탁하는 데서 끝내지 말고 host가 post-boundary ToolUse와 성공 ToolResult를 확인하지 못한 답변을 `summary-only`로 표시해야 합니다. 자동 동작은 실제 context pressure를 만든 별도 장기 실행에서 `trigger=auto`가 관찰될 때만 추가하겠습니다.
