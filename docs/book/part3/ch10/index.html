    10장: 컴팩션 이후의 파일 상태 보존¶

    공개 GitHub Pages 투영판: 10장: 컴팩션 이후의 파일 상태 보존

    공개 실제 실행 증거: 10장 컴팩션 이후 stale 파일 상태 관찰

    압축이 끝났다고 해서 작업이 끝나는 것은 아닙니다. 사실 함께 살펴볼 진짜 이야기는 그 다음에 시작됩니다. 모델은 방금 읽은 파일, 사용한 스킬, 진행 중이던 계획, 큰 도구 결과의 세부 내용을 잃을 수 있거든요.

    원본 Claude Code 관점에서 이 장은 pre-compact file snapshot, post-compact file restore, skill reinjection, plan attachments, delta attachments를 다뤘습니다. SDK판에서는 Read 재실행, file checkpointing, session_store, tool result/file artifact 연결로 관찰합니다. 현재 Python SDK에 없는 event 이름을 보존 사실의 근거로 사용하면 안 됩니다.

    10.1 핵심 질문¶

    압축 후에도 파일과 산출물의 상태가 사용자가 이해할 수 있게 유지되는가?

    10.2 원본의 핵심 설계: 스냅샷-클리어-선택 복원¶

    원본 구현의 흐름을 천천히 따라가 보면 다음과 같습니다.

    압축 전
  -> readFileState snapshot
  -> old cache clear
  -> 가장 가치 있는 파일/스킬/플랜만 선택 복원

    여기서 짚어둘 점은 “모두 복원하지는 않는다”는 것입니다. 압축으로 확보한 공간을 다시 모든 파일 내용으로 채우면 압축한 의미가 사라지기 때문이지요.

    원본이 사용한 판단 축을 함께 보겠습니다.

    판단 의미
    최근 읽은 파일 우선 다음 작업에 필요할 가능성이 높음
    파일당 예산 큰 파일 하나가 context를 먹지 않게 함
    총 예산 복원 전체가 압축 효과를 지우지 않게 함
    plan/CLAUDE.md 제외 별도 채널로 주입되므로 중복 방지
    skill selective restore 호출된 skill만 복원

    SDK판에서는 이 내부 상태를 직접 보지 못할 수도 있습니다. 그럴 때는 대신 후속 이벤트로 판단하면 됩니다.

    10.3 SDK에서 볼 수 있는 파일 상태¶

    SDK 표면 의미
    enable_file_checkpointing Python에서 사용자 메시지 기준 파일 되감기 활성화
    ClaudeSDKClient.rewind_files() Python에서 특정 사용자 메시지 시점으로 파일 복구
    Read tool_use 압축 후 파일을 다시 확인함
    Write/Edit tool_use 압축 후 파일 변경 발생
    session_store Python에서 transcript 외부 저장/복원
    final report/artifact 산출물이 사용자에게 남음

    강의 화면에서는 파일을 단순 path로만 보여주지 않습니다. “이 파일이 어느 prompt와 어느 tool_use 뒤에 생겼는가”를 함께 연결해 주는 것이 좋습니다.

    현재 Python SDK 타입 교정 claude-agent-sdk==0.2.128은 SDKFilesPersistedEvent라는 class를 export하거나 parse하지 않습니다. 이번 live stream에도 그런 system event는 없었습니다. 별도 언어·버전의 이름을 Python의 현재 보장처럼 쓰지 말고, 실제 tool event, checkpoint/rewind, session store, 디스크 hash를 각각 관찰해야 합니다.

    10.4 실제 Opus 5 실행: V1 기억과 V2 디스크의 충돌¶

    Python SDK 0.2.128, Claude Code CLI 2.1.220, 실제 claude-opus-5로 다음 순서를 한 persistent session에서 실행했습니다.

    continuation-check skill 읽기
  -> state.md V1 Read
  -> manual /compact
  -> host가 state.md를 V2로 변경
  -> 같은 skill과 fresh Read를 다시 요구
    attempt OTel trace 핵심 raw sequence
    111658-cc5ddf5e acdc29d83d98975062b6a99e32a9446f V1 Read result seq 46, boundary seq 65, host mutation seq 70, final text seq 80

    직접 관찰 결과는 기대와 달랐습니다.

    • init의 skills에는 continuation-check가 포함됐습니다.
    • 압축 전에는 skill file을 seq 21/25에서 읽고 state.md의 V1을 seq 42/46에서 읽었습니다.
    • boundary는 trigger="manual", pre_tokens=5281, post_tokens=2278, cumulative_dropped_tokens=3003으로 관찰됐습니다.
    • host는 boundary 뒤 seq 70에서 파일 hash와 marker를 V1에서 CH10_FILE_STATE_V2_B903으로 변경했습니다.
    • post-boundary 구간에는 Skill 호출도 Read tool use/result도 없었습니다.
    • 그런데 final text는 오래된 V1을 RE-READ evidence라고 보고하고 V1 파일 line까지 인용했습니다.

    이 attempt의 raw는 SDK message 78건, host process event 9건, permission/hook callback 0건이며 OTel span은 89건입니다. integrity.json이 열거한 manifest, verdict, raw 4종, OTel의 SHA-256 7개를 현재 파일에서 다시 계산해 모두 일치했습니다. 같은 recorder가 raw와 host event를 OTel로 투영했기 때문에 OTel은 독립 provider 관측기가 아닙니다.

    세 phase의 terminal ResultMessage는 모두 success였습니다. /compact 결과는 num_turns=0, 빈 자연어 result였고, 마지막 result는 stale V1을 그대로 RE-READ라고 반환했습니다. 세 Result의 model_usage에는 primary claude-opus-5뿐 아니라 claude-haiku-4-5-20251001 보조 사용도 기록됐습니다. 따라서 primary model과 전체 provider usage를 같은 뜻으로 쓰지 않습니다.

    이 실행은 스킬이 init 목록에 존재하고 compaction summary에 규칙이 남았다는 사실만으로 그 규칙이 다시 수행되지는 않는다는 것을 보여줍니다. 현재 디스크는 V2였지만 모델의 claim은 V1이므로, 해당 claim은 stale이며 re-read가 아닙니다.

    또한 “정확한 경로와 line을 인용했다”는 표현도 freshness 증거가 아닙니다. boundary 뒤 새 tool event가 없다면 과거 summary에서 재생한 provenance일 수 있습니다.

    manifest의 source hash는 실행 당시 10장 원문과 연결되고 fixture/skill hash도 남아 있습니다. 그러나 exact probe, case, runtime source hash는 attempt에 묶이지 않았습니다. 현재 코드를 실행 당시 코드와 암호학적으로 동일하다고 단정하지 않고, 다음 capture부터는 이 네 source hash를 모두 provenance manifest에 넣어야 합니다.

    10.5 보존 상태 분류¶

    파일과 스킬, 플랜은 압축 뒤 다음 상태 중 하나로 표시해 줍니다.

    상태 설명
    restored 압축 후 다시 주입됨
    re-read 모델이 다시 Read해서 확인함
    persisted 파일/도구 결과가 외부 저장됨
    checkpointed 되감기 가능한 상태로 저장됨
    stale 압축 전 내용과 현재 디스크 내용이 다를 수 있음
    dropped 압축 후 더 이상 근거로 쓰면 안 됨

    이 상태 표시가 없으면 사용자는 “왜 모델이 방금 읽은 파일을 또 읽지?” 하고 의아해하기 쉽습니다.

    이번 실행을 위 표로 분류하면 다음과 같습니다.

    대상 상태 근거
    V1 marker stale boundary 뒤 host가 V2로 변경했지만 summary와 final claim은 V1 유지
    V2 marker current on disk, not observed by model host hash/marker 기록은 있으나 post-boundary Read 없음
    continuation-check listed and read before compact init skills와 pre-boundary skill file Read
    continuation-check after compact not executed post-boundary Skill/Read event 0건
    final RE-READ claim correction required raw stream에 대응하는 post-boundary tool result 없음

    10.6 스킬과 계획도 상태다¶

    원본에서 스킬 재주입이 필요했던 이유는 의외로 간단합니다. 스킬은 단순한 설명 문서가 아니라 행동 제약이거든요. 압축 후 스킬 설명이 사라지면 모델은 같은 작업을 다른 규칙으로 이어갈 수 있습니다.

    SDK에서는 다음을 함께 살펴봅니다.

    항목 SDK 표면
    발견된/사용 가능한 skill SystemMessage.init.data.skills
    skill 사용 흔적 Skill tool/event 또는 Read된 skill file
    plan mode permissionMode: "plan", ExitPlanMode
    plan artifact generated file / assistant plan text
    hook-based restore includeHookEvents, hook response

    책 캔버스에는 “압축 후에도 이 skill/plan이 살아 있는가”를 별도 카드로 따로 두면 좋습니다.

    init.skills는 사용 가능 목록이지 “활성화되어 실제 수행된 스킬”의 증거가 아닙니다. 실제 사용 여부는 해당 turn의 Skill tool event, skill file Read, 그리고 그 지시를 수행한 후속 tool event로 확인해야 합니다.

    이번 실행에서는 boundary 뒤 같은 session ID의 init이 다시 방출됐고 그 목록에 continuation-check가 다시 나타났습니다. 그러나 그 뒤 Skill/Read event는 0건입니다. 그러므로 재방출된 init 목록은 available의 근거일 뿐 restored and executed의 근거가 아닙니다.

    10.7 아직 관찰하지 못한 복원 주장¶

    주장 현재 판정
    runtime이 호출된 skill만 선택 재주입한다 Not observed / internal policy unknown
    plan artifact를 압축 뒤 자동 복원한다 Not observed
    file persisted 전용 system event가 발생한다 Not observed; 현재 Python type도 없음
    checkpoint/rewind가 파일을 복구한다 6b장의 실제 attempt 103401-427be665에서 별도 관찰
    session store가 transcript를 mirror한다 6b장의 실제 attempt 103439-e3093bb2에서 별도 관찰

    checkpoint나 session store 관찰을 skill/plan 자동 복원의 증거로 확대하지 않습니다.

    10.8 캔버스 표현¶

    Compact boundary
  -> restored files
  -> restored skills
  -> restored plan
  -> re-read evidence
  -> next action

    파일 카드에는 다음 필드를 붙여 줍니다.

    필드 이유
    short name 긴 경로 대신 읽기 좋게
    role evidence / artifact / plan / report
    state restored / re-read / persisted / stale
    linked tool_use_id 어떤 도구 호출과 연결되는가
    linked claim 어떤 응답 주장의 근거인가

    10.9 학생 실습¶

    압축 후에도 작업을 이어갈 수 있게 파일 상태 체크리스트를 만들어 줘.

다음을 분리해라.
1. 다시 읽어야 할 핵심 파일
2. 이미 산출물로 저장된 파일
3. 현재 내용이 바뀌었을 수 있어 stale 위험이 있는 파일
4. 스킬/계획 중 다시 확인해야 할 것

    Takeaway¶

    압축 후 복원은 단순한 편의 기능이 아니라 데이터 손실을 막는 운영 문제입니다. 그러나 skill 목록, summary, final answer만으로 복원을 판정하면 안 됩니다. SDK 기반 시각화는 파일이 어느 사건 뒤에 바뀌었는지, boundary 뒤 fresh tool result가 있는지, final claim이 그 최신 증거와 일치하는지까지 연결해야 합니다.
