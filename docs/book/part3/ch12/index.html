    12장: 토큰 예산 전략¶

    공개 GitHub Pages 투영판: 12장: 토큰 예산 전략

    공개 실제 실행 증거: 12장 runtime overflow와 host preview 비교

    컴팩션은 컨텍스트가 이미 커진 뒤에 하는 대응이에요. 그보다 더 좋은 설계는, 애초에 너무 큰 도구 결과와 메시지를 컨텍스트에 밀어 넣지 않는 것입니다.

    원본 Claude Code 관점에서 이 장은 단일 도구 결과 50K 문자 게이트, 메시지당 200K 집계 상한, persisted tool result, 대략적 토큰 추정, 그리고 병렬 도구 호출의 토큰 카운팅 함정을 함께 살펴봤어요. SDK판에서는 usage/model usage, tool result preview, 실제 persisted artifact, compact/retry 신호로 관찰합니다. 현재 Python SDK에 없는 event 이름을 사실처럼 먼저 가정하지 않습니다.

    12.1 핵심 질문¶

    모델이 답을 만들기 전에, 도구 결과와 문서 입력의 크기를 통제할 수 있는가?

    12.2 원본의 세 단계 예산¶

    레벨 원본 설계 SDK/제품 관찰
    단일 도구 결과 큰 결과는 파일로 persist하고 preview만 모델에 전달 overflow ToolResult, 실제 output path/file, preview
    메시지 집계 병렬 tool_result 합계 상한 한 턴의 tool_result 총량
    토큰 카운팅 API usage와 rough estimation 병행 SDKResultMessage.usage, modelUsage

    이 구조의 목적은 단순한 비용 절감이 아니에요. 큰 결과 하나 때문에 세션 전체가 압축으로 떠밀려 가는 일을 막아 주는 것이랍니다.

    현재 Python SDK 타입 교정 claude-agent-sdk==0.2.128은 SDKFilesPersistedEvent라는 class를 export하지 않습니다. 이번 실제 overflow에서도 전용 system event가 아니라 대체된 ToolResult text와 tool-results/*.txt 파일이 관찰됐습니다. 따라서 event 이름이 아니라 raw ToolResult와 실제 파일을 연결해야 합니다.

    12.3 큰 도구 결과는 artifact가 되어야 한다¶

    좋은 제품은 100KB짜리 로그를 그대로 채팅에 밀어 넣지 않아요. 대신 파일로 저장해 두고, 모델에는 핵심 미리보기와 경로만 건네줍니다.

    Tool result too large
  -> persist full output
  -> send preview
  -> attach artifact card
  -> answer cites relevant excerpt only

    SDK 화면에서는 이 흐름을 이렇게 표시해요.

    항목 표시
    full output artifact/file drawer
    preview tool result card
    extracted keywords keyword chips
    claim link preview sentence -> claim
    persisted event file persistence lane

    12.4 실제 Opus 5 재현: runtime overflow와 host policy 비교¶

    Python SDK 0.2.128, Claude Code CLI 2.1.220, 실제 claude-opus-5로 동일한 60,082-character payload를 두 번 순차 실행했습니다. manifest는 실행 당시 장, probe, case, runtime source SHA-256 네 개를 함께 기록했습니다.

    case attempt OTel trace SDK / process / permission / hook 모델에게 전달된 결과
    runtime overflow 221711-cf0efe19 676fc703db0806defc07340853426cfd 64 / 4 / 0 / 0 1,587-character overflow 안내
    host persisted preview 221742-59006bcd b6603aebcc62c1f5fb06d9cc943cdd18 52 / 4 / 0 / 0 340-character preview text

    두 attempt의 integrity.json이 열거한 evidence file SHA-256은 각각 8/8개가 현재 파일과 일치했습니다. CAPTURED, verdict TODO, passed=null은 수집 완료 표식이며 아래 판정 자체가 아닙니다.

    runtime overflow case¶

    MCP handler는 process seq 16에서 60,082-character full result를 반환했고 직접 파일을 쓰지 않았습니다. 그러나 raw SDK ToolResult seq 20에는 full payload 대신 다음 1,587-character text가 왔습니다.

    • maximum allowed tokens를 초과했다는 문구
    • 원래 결과가 60,082 characters, 3 lines라는 크기
    • 격리 config 아래 tool-results/*.txt 경로
    • offset/limit으로 다시 읽으라는 안내

    ToolResult의 is_error 필드는 null이지만 text는 Error:로 시작하고, terminal Result seq 65는 success, is_error=false, terminal_reason=completed입니다. 따라서 overflow notice, ToolResult error flag, 전체 run 종료 상태는 서로 다른 층입니다.

    capture host는 임시 디렉터리가 삭제되기 전에 reported path를 직접 열었습니다. 실제 파일은 60,082 bytes/characters였고 head/tail marker와 SHA-256 e45a9cd05a27dc4d40a85b9a57911f70058bfcc77a890a54c4fa3341ab71142e가 handler 원본과 일치했습니다. 전체 파일은 immutable evidence attempt의 artifacts/runtime-overflow-output.txt에도 복제했습니다.

    허용되는 결론은 현재 Agent SDK/Claude Code CLI 실행 경로가 이 60,082-character result를 자동 외부화했다는 것입니다. 전용 persisted event가 없으므로 어느 내부 함수가 썼는지까지 이름 붙이지 않습니다. 또한 한 점에서 gate가 동작했다는 사실만으로 exact threshold가 50,000 characters라고 확정하지 않습니다. notice 자체도 characters를 보고하지만 제한 사유는 maximum allowed tokens라고 씁니다.

    모델은 이 path를 “host tool policy”라고 분류했습니다. 하지만 controlled MCP handler에는 write가 없고 handler 이후 raw ToolResult가 바뀌었습니다. 모델은 자기 바깥 pipeline의 소유권을 직접 볼 수 없으므로, 이 attribution은 host/process evidence와 모순됩니다.

    host persisted preview case¶

    두 번째 case에서는 MCP handler 자체가 같은 full payload를 artifacts/ch12-full-output.txt에 저장하고 path, count, hash, head/tail marker만 반환했습니다.

    • host persist process event: seq 15
    • tool handler: seq 16
    • bounded ToolResult: seq 18
    • 실제 ToolResult text: 340 characters
    • Python list representation: 376 characters
    • disk snapshot: 60,082 bytes/characters, 같은 SHA-256과 marker
    • evidence copy: artifacts/host-persisted-full-output.txt
    • runtime overflow 안내: 없음

    340은 ToolResultBlock.content[0].text 길이이고 376은 Python list representation 길이입니다. 화면의 payload meter는 실제 text 340을 사용해야 합니다. host process event와 disk snapshot이 실제 write를 확인하므로, 모델이 “tool의 자기보고만으로는 파일을 검증할 수 없다”고 말한 한계도 host observer가 보완합니다.

    이것은 애플리케이션이 구현한 host policy입니다. 자동 runtime gate와 외형이 비슷해도 handler code, process event, path ownership으로 구분합니다.

    현재 판정¶

    주장 판정
    큰 단일 결과는 현재 SDK/CLI path에서 자동 외부화될 수 있다 Observed at 60,082 characters
    gate가 정확히 50,000 characters다 Not observed; boundary sweep 필요
    메시지당 aggregate 200K 상한이 적용된다 Not observed / TODO
    Python에서 SDKFilesPersistedEvent가 발생한다 Correction required; 현재 type/event 없음
    host가 full artifact + preview 정책을 구현할 수 있다 Observed
    모델의 persistence attribution만으로 소유 주체를 알 수 있다 Contradicted
    runtime 원본 파일이 session/process 종료 뒤에도 남는다 Not observed; capture 중 read-back만 확인

    12.5 병렬 도구 호출의 함정¶

    결과 하나하나는 작더라도, 병렬 호출이 여러 개 모이면 어느새 커지곤 해요.

    Grep A: 40K
Grep B: 40K
Grep C: 40K
Grep D: 40K
Grep E: 40K
=> 한 턴에 200K

    모델은 “검색을 많이 했다”고 생각하지만, 정작 제품은 컨텍스트 예산을 잃게 돼요. 그래서 캔버스에는 한 턴의 tool result aggregate meter가 있으면 좋습니다.

    위 200K 예시는 설계 설명이며 이번 Agent SDK 실행으로 확인한 수치가 아닙니다. exact aggregate gate를 실제 사실로 표시하려면 같은 turn의 여러 tool result가 만든 원본 합계, 대체 결과, 저장 파일을 모두 보존한 별도 실행이 필요합니다.

    Turn result budget
  Read: 12K
  Grep: 86K
  Bash: 7K
  Persisted: 140K outside context

    12.6 토큰 카운팅은 정확값과 추정값을 분리한다¶

    원본은 API usage 기반의 정확한 카운트와 rough estimation을 따로 나눠 두었어요. SDK판에서도 같은 구분이 필요합니다.

    카운트 근거 신뢰도
    API usage SDKResultMessage.usage, modelUsage 높음
    rough estimate 문자/바이트 길이 추정 중간
    UI projected size preview/file size 낮음~중간

    추정값을 정확값처럼 보여 주는 건 피하는 게 좋아요. 그래서 캔버스에서는 estimated badge를 붙여 둡니다.

    실제 run에서도 host의 60,082 character count와 ResultMessage의 API usage는 다른 값이었습니다. 문자 수를 4로 나눈 값을 API input token처럼 표시하면 안 됩니다.

    surface runtime overflow host preview 의미
    thinking_tokens 마지막 estimate 283 150 stream 중 추정 신호
    Opus cache create/read 1,510 / 722 1,012 / 726 terminal API usage
    Opus input/output 4 / 1,243 4 / 894 terminal API usage
    Haiku input/output 588 / 22 591 / 19 model_usage의 보조 model

    thinking_tokens는 SystemMessage의 estimate이며 terminal billing/API usage와 같은 값이 아닙니다. primary assistant model은 Opus 5지만 model_usage에는 Haiku 4.5도 있으므로 전체 provider usage를 Opus 하나로 표시하지 않습니다. 두 independent run의 차이에는 모델 출력 길이와 cache 상태도 섞이므로 이 한 pair로 비용 절감률을 일반화하지 않습니다.

    공개 증거에는 overflow notice의 로컬 절대경로와 runtime session identifier를 그대로 복사하지 않습니다. 제품 화면에는 redacted artifact label과 content hash만 투영합니다.

    12.7 예산과 근거 추적의 관계¶

    사용자가 정말 궁금해하는 것은 “토큰을 얼마나 썼는가”가 아니라 “근거가 잘 유지됐는가”예요. 그래서 예산 절감은 근거 추적과 늘 함께 가야 합니다.

    나쁜 절감 좋은 절감
    큰 결과를 잘라서 근거 문장도 잃음 전체는 파일로 저장하고 핵심 문장만 추출
    검색 결과를 무조건 삭제 현재 claim과 연결 안 된 오래된 결과만 prune
    답변을 짧게 하느라 검증 생략 검증 여부는 짧게라도 명시
    경로만 남김 경로 + 핵심 단어 + 문장 snippet

    Token Budget

    12.9 학생 실습¶

    큰 문서와 긴 로그를 다루는 에이전트의 토큰 예산 정책을 설계해 줘.

정책에는 다음을 포함해라.
1. 한 도구 결과가 너무 클 때 처리 방법
2. 병렬 검색이 많을 때 aggregate budget을 보는 방법
3. 전체 결과를 파일로 보존하고 핵심 문장만 답변에 쓰는 방법
4. 추정 토큰과 실제 usage를 구분해서 표시하는 방법

    Takeaway¶

    토큰 예산 전략은 비용 절감 장치라기보다 근거를 지키는 장치입니다. 현재 runtime의 자동 overflow와 애플리케이션의 persisted-preview 정책은 둘 다 실제 파일을 남길 수 있지만 소유 주체와 사건 경로가 다릅니다. raw ToolResult, process event, 실제 파일 hash를 연결하고, estimate/API usage/provider model usage를 분리하며, exact threshold와 aggregate limit, 원본 spill file의 장기 수명은 별도 실행 전까지 미확정으로 남겨야 합니다.
