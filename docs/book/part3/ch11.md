# 11장: 마이크로 컴팩션 — 정밀한 컨텍스트 가지치기

> 공개 GitHub Pages 투영판: [11장: 마이크로 컴팩션 — 정밀한 컨텍스트 가지치기](https://nfbs2000.github.io/speaky-claude-cookbooks/book/part3/ch11/)
>
> 공개 실제 실행 증거: [11장 large-result와 micro-compaction 비관찰](https://nfbs2000.github.io/speaky-claude-cookbooks/book/evidence/ch11-live/)

자동 컴팩션이 큰 수술이라면, 마이크로 컴팩션은 좀 더 가벼운 손질이라고 생각하면 편해요. 자동 컴팩션은 대화 전체를 요약하고 구조를 바꾸지만, 마이크로 컴팩션은 오래된 도구 결과나 더 이상 중요하지 않은 컨텍스트를 정밀하게 줄여서, 전체 압축까지 가지 않도록 버텨 줍니다.

원본 Claude Code 관점에서 이 장은 시간 기반 microcompact, cache 기반 `cache_edits`, API context management, compactable tool inventory를 다뤘어요. SDK판에서는 이런 내부 메커니즘을 직접 조작하지는 않습니다. 대신 도구 결과가 언제 사라졌고, 어떤 정보는 다시 읽어야 하며, 캐시/사용량 변화가 어떻게 나타나는지를 함께 관찰해 봅니다.

> **API 경계 주의**
> Anthropic cookbook과 [공식 context editing 문서](https://platform.claude.com/docs/ko/build-with-claude/context-editing)의 `context_management`, `clear_tool_uses_20250919`, `applied_edits` 예제는 Messages API를 사용합니다. 이번에 실행한 Python `claude-agent-sdk==0.2.128`의 `ClaudeAgentOptions`에는 동급 context-management, micro-compaction, `cache_edits` option이 없습니다. 관련 API의 존재를 Agent SDK runtime의 동작 증거로 바꾸어 읽으면 안 됩니다.

## 11.1 핵심 질문

> 전체 압축 없이도, 오래된 도구 결과를 줄였을 때 근거 품질을 유지할 수 있는가?

## 11.2 원본의 세 가지 마이크로 압축

| 종류 | 원본 의미 | SDK 관찰 |
| --- | --- | --- |
| 시간 기반 | 긴 유휴 뒤 오래된 tool_result를 placeholder로 대체 | 세션 재개 뒤 이전 결과 세부가 사라짐 |
| cache 기반 | 서버 캐시를 깨지 않고 특정 tool result 삭제 | usage/cache/latency 변화, 결과 재조회 |
| API context management | API가 선언적 전략으로 context 정리 | compact/usage 신호, tool result visibility 변화 |

강의에서는 이것을 “시스템이 똑똑하게 줄인다”라고 설명하지는 않아요. 우리가 함께 봐야 할 것은, 어떤 정보가 줄었고 현재 답변이 그 정보를 다시 확인했는지입니다.

## 11.3 Compactable tool result

모든 정보가 똑같은 가치를 갖는 것은 아니에요.

| 정보 | 줄이기 쉬움 | 이유 |
| --- | --- | --- |
| 오래된 Grep 결과 | 높음 | 다시 검색 가능 |
| 오래된 Bash 로그 | 중간 | 실패 원인은 중요할 수 있음 |
| 최종 plan | 낮음 | 작업 방향 유지에 필요 |
| 사용자 요구사항 | 낮음 | 목표 손실 위험 |
| generated report | 낮음 | 산출물 자체 |
| permission decision | 낮음 | 안전/감사 기록 |

책 캔버스에서는 도구 결과를 다음처럼 분류해 두면 좋아요.

```text
tool_result
  compactable: yes/no
  current relevance: high/medium/low
  re-readable: yes/no
  linked claims: [...]
```

## 11.4 SDK에서 추적할 수 있는 것

마이크로 압축은 직접적인 이벤트로 드러나지 않을 수 있어요. 그래도 다음은 충분히 추적할 수 있습니다.

| 신호 | 해석 |
| --- | --- |
| 이전 tool_result 내용이 answer에서 사라짐 | 단순 생략일 수 있음. pruning 증거가 아님 |
| 모델이 같은 Grep/Read를 다시 수행 | evidence re-acquisition |
| `compact_boundary` 없이 usage가 가벼워짐 | 변화량만 관찰. 원인 알고리즘은 미확정 |
| usage/input token 변화 | context pressure의 간접 신호 |
| persisted output path만 남음 | large result가 외부화됨 |

직접 이벤트가 없으면 inferred로 표시해요. “마이크로 압축이 일어났다”라고 단정하기보다는, “이전 결과 세부가 현재 event tape에 없고 모델이 재조회했다”라고 말해 주는 편이 좋습니다.

여기에도 한 단계가 더 필요합니다. **현재 event tape에 없다는 사실**과 **최종 답변에 언급되지 않았다는 사실**은 다릅니다. raw tool result가 tape에 그대로 있는데 답변만 짧을 수 있습니다. pruning을 추론하려면 적어도 raw transcript, runtime event, usage를 함께 읽어야 합니다.

## 11.5 실제 Opus 5 실행: 답변 생략은 pruning이 아니다

Python SDK `0.2.128`, Claude Code CLI `2.1.220`, 실제 `claude-opus-5`의 한 persistent session에서 `/compact`를 보내지 않고 read-only MCP tool을 두 번 순차 호출했습니다.

| phase | 실제 MCP result text | recorder 파생 길이 | marker |
| --- | ---: | ---: | --- |
| ALPHA | 24,088 characters | 24,122 | `CH11_ALPHA_HEAD`, `CH11_ALPHA_TAIL` |
| BETA | 24,085 characters | 24,119 | `CH11_BETA_HEAD`, `CH11_BETA_TAIL` |

표의 recorder 파생 길이는 `ToolResultBlock.content` list를 Python `str()`로 바꾼
길이다. 실제 tool payload text 길이가 아니다. 이 값을 raw result 크기로 쓰면 34자가
부풀려진다.

| attempt | OTel trace | raw SDK tape |
| --- | --- | ---: |
| `112453-6f7401e1` | `1860600cab1bb4a73e672d54f71ee253` | 152,378 bytes |

직접 판독 결과:

- ALPHA tool use/result는 seq 15/18, BETA는 seq 45/50에서 연결됐습니다.
- 두 full payload text는 raw SDK tape에 남았습니다. 이는 **증거 보관소의 보존**이지
  마지막 provider 요청의 활성 context 보존 증거는 아닙니다.
- raw SDK message는 72건, host process event는 10건, permission/hook callback은
  각각 0건입니다. OTel은 86 span입니다.
- system event는 init 3건과 status 5건뿐이었고 `compact_boundary`나
  micro-pruning 전용 event는 없었습니다.
- 최종 turn은 tool을 다시 호출하지 않고 네 head/tail marker를 정확히 답했습니다.
  그러나 marker는 이미 seq 26과 56의 짧은 assistant 답변에도 반복됐습니다. 따라서
  마지막 회상 성공은 큰 payload 전체가 활성 context에 남았다는 증거가 아닙니다.
- 최종 답변은 약 48KB filler를 언급하지 않았습니다. 하지만 raw 결과가 존재하므로 이 생략은 pruning 증거가 아닙니다.
- cache creation/read와 input/output usage 변화는 수치로 관찰됐지만, 그 변화만으로 `cache_edits` 또는 특정 micro-compaction 알고리즘이 실행됐다고 이름 붙일 수 없습니다.

세 terminal Result는 모두 success였습니다. 각 Result의 `usage`는 해당 query의 수치이고,
`model_usage`는 세 phase가 진행되며 누적됐습니다. final Result의 Opus 항목은 cache
creation 23,862, cache read 49,330, input 10, output 383이었고, Haiku 4.5 보조
항목도 세 Result에 존재했습니다. primary model과 전체 provider usage를 같은 뜻으로
쓰지 않습니다.

raw SDK 72건과 OTel `sdk.message` 72건의 sequence는 정확히 일치합니다. 86개 OTel
span은 `sdk.message` 72, `process.event` 10, `tool.execution` 2,
`oracle.verdict` 1, `proof.attempt` 1입니다. 같은 recorder가 raw와 host 사건을 OTel로
투영했으므로 독립 provider 관측기는 아닙니다. `CAPTURED`, assertion count 0,
`verdict=TODO`, `passed=null`은 수집 완료와 수동 판독 대기를 뜻하며 합격이 아닙니다.

이번 실행의 판정은 `micro-compaction not observed`입니다. 이는 “내부에서 절대로 일어나지 않았다”가 아니라, 현재 Agent SDK event surface와 이 workload에서 직접 증거를 얻지 못했다는 뜻입니다.

## 11.6 캐시를 깨지 않는 정리의 제품 의미

원본의 cache 기반 microcompact는 중요한 제품 철학을 잘 보여줘요.

> 컨텍스트를 줄이더라도, 캐시 prefix를 불필요하게 깨지 말아야 한다.

SDK 책에서는 이것이 학생에게 다음 원칙으로 전해집니다.

- 도구 결과를 너무 크게 만들지 않는다.
- 한 번에 너무 많은 병렬 검색을 하지 않는다.
- 긴 로그는 파일로 남기고 핵심 문장만 답변에 연결한다.
- 오래된 근거는 현재 claim에 쓰기 전에 다시 확인한다.

## 11.7 판정 규칙

| 관찰 | 허용되는 판정 | 금지되는 확대 |
| --- | --- | --- |
| raw tool result가 있고 답변에서 filler 생략 | answer omitted detail | tool result pruned |
| raw archive에 tool result가 존재 | recorder retained evidence | active provider context preserved |
| final이 이전 marker를 재현 | marker recall observed | full payload retained; marker가 중간 답변에도 있으면 출처도 미확정 |
| 같은 Read/Grep를 다시 호출 | evidence reacquired | 이전 결과가 반드시 삭제됨 |
| compact boundary event 존재 | compaction observed | micro-pruning 세부 알고리즘 확정 |
| usage/cache 수치 변화 | numeric usage changed | `cache_edits` 실행 확정 |
| `applied_edits`가 Messages API 응답에 존재 | Messages API context edit observed | Agent SDK에도 같은 event가 존재 |

시간 기반 idle pruning, Agent SDK의 cache-based microcompact, compactable tool inventory
내부 정책, 큰 payload 전체의 마지막 turn 활성 context 보존은 아직
`Not observed / TODO`입니다.

## 11.8 캔버스 표현

```text
Context Pressure
  -> Raw Evidence Archive
  -> Active Model Context (unknown unless directly surfaced)
  -> Assistant Summary
  -> Pruned / Preserved / Unknown
  -> Re-read Required
  -> Current Claims
```

하단 테이블:

| tool result | 상태 | 현재 답변에서 사용 가능? | 조치 |
| --- | --- | --- | --- |
| Grep result A | pruned/inferred | 아니오 | 다시 검색 |
| Read section B | preserved | 예 | claim 연결 |
| Bash failure C | stale | 주의 | 실패 재현 또는 로그 확인 |

## 11.9 학생 실습

```text
긴 세션에서 오래된 도구 결과를 정리한다고 가정해라.

다음을 분류해 줘.
1. 버려도 되는 오래된 검색 결과
2. 다시 읽어야 하는 문서 근거
3. 반드시 보존해야 하는 사용자 요구사항
4. 산출물로 외부 저장해야 하는 결과
```

## Takeaway

마이크로 컴팩션을 가르칠 때는 답변의 길이나 usage 변화만 보고 내부 동작을 단정하면 안 됩니다. raw 증거 보관, provider의 활성 context, 직접 runtime event, 재조회 tool chain, 현재 claim을 분리해야 합니다. 이번 실제 실행에서는 큰 결과가 recorder의 raw archive에 남은 채 답변만 짧아졌습니다. marker 회상은 중간 assistant 답변 때문에 출처가 혼재하며, micro-compaction 자체는 관찰되지 않았습니다.
