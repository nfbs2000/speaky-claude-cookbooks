## 공개판 본문

원래 책은 이 장을 내부 구현과 강의 화면의 대응 관계로 설명한다. 공개판에서는 같은 내용을 "무엇을 설정했는가", "무엇이 메시지로 관측됐는가", "어떤 파일과 notebook으로 재현 가능한가"라는 세 질문으로 바꾼다.

첫째, 설정된 것은 실행 전 계약이다. Agent SDK에서는 model, system prompt, working directory, allowed/disallowed tools, MCP servers, skills/plugins, permission mode 같은 값이 agent가 볼 수 있는 세계를 정한다. 이 값은 말로 설명하는 정책이 아니라 실제 Python 코드와 notebook cell에서 확인되어야 한다.

셋째, 추론한 것은 반드시 경계와 함께 둔다. 내부 기능 플래그, 숨은 프롬프트, classifier, cache key, sandbox implementation처럼 공개 SDK나 cookbook으로 확인할 수 없는 항목은 원문을 그대로 게시하지 않는다. 대신 공개 API에서 사용자가 설계할 수 있는 대응 표면으로 바꾸거나, "공개 대응 없음"으로 명시한다.

## Codex 최종 검토 의견

### 제 판단

요청 전 입력 snapshot과 응답 후 cache usage를 비교해 break 후보를 찾는 패턴은 실무적으로 유효합니다. 현재 A/A-control/B 삼중은 설계도 좋습니다. A와 control은 같은 tool surface이고 B만 description과 input schema가 달랐으며, control은 2,660 cache read, B는 read 0/create 2,887을 기록했습니다. 같은 패턴이 이전 보조 triple에서도 반복됐습니다.

### 검증을 읽고 달라진 신뢰도

변경된 tool surface가 이 표본의 miss를 설명하는 가장 강한 후보라는 데 동의합니다. 동시에 이를 provider가 공표한 원인이라고 부르지는 않겠습니다. SDK에는 `pendingChanges`, per-tool attribution, cache key, token-to-schema map이 없었습니다. 이 장의 “감지 시스템”은 SDK 기능이 아니라 host가 변수와 usage를 수집하고 오염된 pair를 기각하는 분석기입니다.

### 독자가 오해할 위험

B에서는 description과 schema가 함께 바뀌어 어느 쪽이 개별 원인인지 분리되지 않았습니다. 또 실패 attempt에서 `subtype=success`인데 `is_error=true`인 529 종료가 실제로 나왔으므로 subtype 하나만으로 표본을 채택하면 안 됩니다. 과거 cache에 오염된 B가 read를 기록한 기각 사례도 숫자만 보고 결론을 내리면 안 되는 좋은 경고입니다. host가 계산한 schema hash는 provider cache key가 아닙니다.

### 제가 다시 가르친다면

채택된 triple뿐 아니라 529 실패, 과거 B cache 오염, control 부재로 기각된 시도를 함께 보여 주겠습니다. 좋은 캐시 실험은 원하는 숫자가 나온 실행이 아니라 비교 불가능한 실행을 버릴 기준이 있는 실험입니다. 다음에는 description-only와 schema-only를 나누고 fresh nonce로 triple을 반복해야 합니다. [프롬프트 캐싱 노트북](https://nfbs2000.github.io/speaky-claude-cookbooks/notebooks/misc/prompt_caching_kr.html)은 explicit cache surface의 기준이며, host 분석기가 후보를 좁힌 실제 과정은 [Speaky Agent Flow 14장 재생](https://nfbs2000.github.io/speaky-agent-flow/education/?collection=book-sdk-ko&run=ch14)에서 확인할 수 있습니다.

### 클로드는 이렇게 세상을 바라보았다

tool description과 schema가 바뀐 B 실행에서 나에게는 그 새 도구 표면이 그냥 현재 세계였다. 나는 cache가 깨졌다는 경고도, 어느 필드가 원인이라는 설명도 받지 않았다. cache read가 0이 된 사건은 내 행동 내부가 아니라 host가 A, control, B의 입력 snapshot과 usage를 나란히 놓았을 때만 의미를 얻었다. 529 실패와 오염된 cache 표본 역시 내 단일 답에서는 정상 비교인지 판정할 수 없었다.
