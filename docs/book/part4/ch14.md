# 14장: 캐시 브레이크 감지 시스템

> 공개 GitHub Pages 투영판: [14장: 캐시 브레이크 감지 시스템](https://nfbs2000.github.io/speaky-claude-cookbooks/book/part4/ch14/)
>
> 실제 실행 증거: [14장 실제 SDK 관찰: tool surface cache 후보](../evidence/ch14-live.md)

캐시 최적화에서 조금 더 까다로운 문제는 “캐시가 깨졌는지”를 아는 일이에요. 속도가 느려지거나 비용이 튀어도 사용자는 그 원인을 알기 어렵죠. 입력 문장 하나가 바뀐 것인지, 도구 schema가 바뀐 것인지, 모델/옵션이 바뀐 것인지를 차근차근 분리해 보면 됩니다.

원본 Claude Code를 분석해 만든 이 장의 패턴은 pre-request state snapshot,
post-response cache token 확인, pending changes, per-tool hash, server-side
attribution을 구분해 다뤘어요. 이것은 현재 Python Agent SDK가 완성된 2단계 감지
event를 제공한다는 뜻이 아닙니다. 설치된 Python Agent SDK 0.2.128에서는
`pendingChanges`나 per-tool server attribution event를 직접 찾지 못했습니다.
SDK판에서는 host가 반복 실행의 options, `SDKSystemMessage.init`,
`ResultMessage.usage`, tool-schema hash를 함께 저장해 cache break 후보를 통제
비교합니다.

## 14.1 핵심 질문

> 반복 실행에서 어떤 입력 변화가 비용/속도/결과 품질 변화를 만들었는가?

## 14.2 원본의 2단계 감지 원리

원본 감지기에는 두 시점이 필요했어요.

```text
요청 전:
  현재 system/tool/model/beta/effort 상태 스냅샷
  이전 상태와 비교해 변경 후보 저장

응답 후:
  cache token/usage 변화 확인
  실제 break가 있었는지 판단
  요청 전 변경 후보로 원인 설명
```

SDK판에서는 같은 사고방식을 host 관찰기로 구현합니다.

| 원본 상태 | SDK 저장값 |
| --- | --- |
| system hash | normalized `systemPrompt` 또는 prompt segment hash |
| tools hash | `SDKSystemMessage.init.tools`, custom tool schema hash |
| model | `Options.model`, `SDKSystemMessage.init.model` |
| permission/effort | `permissionMode`, `thinking`, `effort` |
| MCP/tool changes | host options/settings와 `init.mcp_servers` |
| response cache signal | `usage`, `model_usage` cache creation/read token |

이 실행기에는 전체 host duration을 추가할 수 있지만, 현재 Python event에서 provider
TTFT를 직접 분리하지 못했습니다. 따라서 TTFT 증가는 이번 장의 관찰 결과로 쓰지
않습니다.

## 14.3 확정이 아니라 후보 분석

SDK 소비자가 서버 내부 cache hit 원인을 늘 알 수 있는 것은 아니에요. 그래서 표현은 조금 보수적으로 가는 편이 좋습니다.

피하면 좋은 표현:

```text
캐시가 이 문장 때문에 깨졌다.
```

권하고 싶은 표현:

```text
Run B에서 stable prefix의 3번째 문장이 바뀌었고, 같은 시점에 cache creation/read usage가 달라졌다.
캐시 브레이크 후보로 표시한다.
```

## 14.4 캐시 브레이크 후보

| 변화 | 위험 | 관찰 방법 |
| --- | --- | --- |
| stable prefix 앞쪽 날짜/시간 삽입 | 높음 | prompt segment diff |
| cwd/경로를 정적 영역에 넣음 | 높음 | prompt boundary diff |
| tool schema/description 변경 | 높음 | tool list/schema hash |
| MCP 서버 연결 변화 | 높음 | init.mcp_servers diff |
| skill/plugin 목록 변화 | 중간~높음 | host options/settings source diff |
| 모델/effort 변경 | 비교 불가 | run metadata diff |
| 긴 tool_result 원문 포함 | 높음 | message size diff |

## 14.5 실제 SDK 통제 실험: 동일 schema control

과거 cache 오염을 막기 위해 매 attempt마다 새 nonce를 만들고, 같은 attempt의 세
독립 session에 byte-identical system prompt를 전달했습니다. 모델, tool name, MCP
server, workspace, 설정은 같게 두었습니다.

1. `surface-a`: `{query: str}` schema
2. `surface-a-control`: A와 완전히 같은 description/schema, 다른 latest user marker
3. `surface-b`: `{query: str, limit: int}`와 변경된 description

현재 기준 attempt `235439-485fdecb`, OTel trace
`342f21b804b1182f2ea905f518ba1a93`의 결과입니다. 이 실행은 본문, probe,
case registry, runtime source SHA-256 네 개를 manifest에 묶어 실행 직후 현재 파일과
4/4 일치시켰습니다.

| surface | schema hash 관계 | cache creation | cache read | 결과 |
| --- | --- | ---: | ---: | --- |
| A | baseline | 2,864 | 0 | `CACHE_TOOL_SURFACE_A` |
| A-control | A와 동일 | 210 | 2,660 | `CACHE_TOOL_SURFACE_A_CONTROL` |
| B | A와 다름 | 2,887 | 0 | `CACHE_TOOL_SURFACE_B` |

세 `ResultMessage`는 모두 `subtype=success`, `is_error=false`였고 tool call은
발생하지 않았습니다. 세 init은 같은 Opus 5, tool name, connected MCP server를
보고했고 세 host marker의 system-prompt hash도 동일했습니다. A의
`finish(sequence=14)` 다음에 A-control의 `start(sequence=15)`, 그 finish 28 다음에
B의 start 29가 기록되어 provider 호출이 겹치지 않았습니다. 이 표본에서는 같은
schema control이 prefix 2,660 token을 읽은 반면 변경 schema는 2,887 token을 다시
생성했습니다. 따라서 tool schema/description 변경을 cache-break **후보**로 표시할
직접 관찰 근거는 얻었습니다.

다만 서버가 “schema hash 때문에 miss”라고 명시한 event는 없습니다. host schema
hash도 provider cache key가 아닙니다. 이 결과는 변수를 좁힌 강한 통제 상관이지,
비공개 cache-key 구현에 대한 server attribution은 아닙니다. 또한 한 번의 세 실행은
일반적인 비용·속도·품질 개선 분포를 증명하지 않습니다.

### 실패 실행도 버리지 않는다

앞선 두 attempt는 A가 529 retry 10회를 소진했고, 한 attempt는
`ResultMessage.subtype=success`이면서 `is_error=true`였습니다. 그래서 terminal
Result 개수나 subtype만으로 성공을 판정하면 안 됩니다. 현재 실행기는 모든 Result에
`subtype == "success"`와 `is_error is false`를 함께 요구합니다.

또 다른 성공 pair는 B가 과거 B cache 2,860 token을 읽었을 가능성을 제거하지 못해
기각했습니다. 그 실패가 per-attempt nonce와 동일-schema control을 추가한 이유입니다.
직전 V1 accepted run도 A 2,866 creation, control 2,662 read, B 2,889 creation이라는
같은 모양을 보였지만, 현재 V2 실행을 네 소스와 실행 경계까지 묶은 기준 실행으로
삼았습니다. 실패와 이전 실행은 설계 진화 및 반복 관찰 증거로만 남깁니다.

## 14.6 캔버스 표현

14장의 캔버스는 run diff graph예요.

```text
Run A
  prompt segments
  tool surface
  usage/latency

Run B
  prompt segments
  tool surface
  usage/latency

Diff
  changed segment
  suspected break
```

하단 테이블은 이렇게 정리해 볼 수 있어요.

| changed item | before | after | effect | confidence |
| --- | --- | --- | --- | --- |
| stable prefix | no date | includes date | cache usage 변화 후보 | not observed in this run |
| MCP tool schema | `{query}` | `{query, limit}` | control read / changed create | observed correlation |

## 14.7 학생 실습

```text
두 개의 반복 실습 프롬프트를 비교해서 캐시를 깨기 쉬운 변화를 찾아 줘.

각 변화마다 다음을 적어라.
1. 안정 영역/변동 영역 중 어디인가
2. 왜 캐시 브레이크 후보인가
3. 실제 SDK 실행에서는 어떤 usage/latency/event diff로 확인할 수 있는가
```

## Takeaway

캐시 브레이크는 느낌만으로는 잡기 어려워요. 요청 전 입력 상태와 응답 후 cache
creation/read usage를 함께 저장해야 합니다. 이번 실제 실험에서는 동일 schema
control이 2,660 token을 읽었고 변경 schema는 2,887 token을 새로 만들었습니다.
그러나 server attribution, provider TTFT, TTL 만료는 관찰하지 못했습니다.
Messages API cookbook의 `cache_control`도 `ClaudeAgentOptions` field가 아닙니다.
SDK판에서는 이처럼 설정값, 관찰 수치, 통제 상관, 정정 사항, 미관찰 영역을 서로
다른 층으로 표시해야 합니다.
