## 공개판 본문

원래 책은 이 장을 내부 구현과 강의 화면의 대응 관계로 설명한다. 공개판에서는 같은 내용을 "무엇을 설정했는가", "무엇이 메시지로 관측됐는가", "어떤 파일과 notebook으로 재현 가능한가"라는 세 질문으로 바꾼다.

첫째, 설정된 것은 실행 전 계약이다. Agent SDK에서는 model, system prompt, working directory, allowed/disallowed tools, MCP servers, skills/plugins, permission mode 같은 값이 agent가 볼 수 있는 세계를 정한다. 이 값은 말로 설명하는 정책이 아니라 실제 Python 코드와 notebook cell에서 확인되어야 한다.

둘째, 관측된 것은 message stream과 artifact다. assistant text, tool use, tool result, result message, usage/cost, audit log, generated file은 모두 나중에 검증 가능한 증거다. 그래서 이 책의 공개판은 "모델이 그렇게 했을 것이다"라고 쓰지 않고, 어떤 cookbook 파일에서 어떤 실행 표면을 볼 수 있는지 연결한다.

셋째, 추론한 것은 반드시 경계와 함께 둔다. 내부 기능 플래그, 숨은 프롬프트, classifier, cache key, sandbox implementation처럼 공개 SDK나 cookbook으로 확인할 수 없는 항목은 원문을 그대로 게시하지 않는다. 대신 공개 API에서 사용자가 설계할 수 있는 대응 표면으로 바꾸거나, "공개 대응 없음"으로 명시한다.

이 장을 읽을 때는 아래 순서가 좋다.

1. 먼저 주요 cookbook 근거를 열어 실제 notebook이나 Python 파일을 확인한다.
2. `ClaudeAgentOptions`, `query()`, `ClaudeSDKClient`, tool list, MCP config, hooks, session 관련 코드가 어디 있는지 찾는다.
3. 원문 절 제목을 따라가며 내부 설명을 공개 SDK 표면으로 바꿔 적는다.
4. 마지막으로 실습 방향에 맞춰 같은 task를 실행하고 message stream 또는 artifact를 남긴다.

## Codex 최종 검토 의견

### 제 판단

volatile timestamp를 안정 prefix 앞쪽에 넣지 말라는 주장은 이번 실행으로 매우 설득력 있게 확인됐습니다. byte-identical한 8,190자 기준과 대조에서 두 번째 실행은 2,629 cache read를 기록했지만, 41번째 글자의 초 값 하나만 바꾼 실행은 read 0/create 2,757이었습니다. 서로 다른 session을 순차 실행하고 나머지 입력 관계를 기록했으므로 교육용 사례로 강합니다.

### 검증을 읽고 달라진 신뢰도

이 한 글자 변화가 해당 triple의 비재사용을 설명하는 가장 강한 후보라고 판단합니다. server cache key와 segment map이 없어 절대 인과를 선언할 수는 없지만, 내부 대조군이 있어 단순한 시간대나 세션 차이보다 설명력이 높습니다. 이는 timestamp, request ID, 절대경로 같은 run metadata를 system prefix 맨 앞에 두는 구현을 피해야 할 실질적 이유를 제공합니다.

### 독자가 오해할 위험

본문에 나열된 모든 최적화가 검증된 것은 아닙니다. path placeholder, skill/document budget, 조건부 단락 이동은 실행하지 않았습니다. `tools=[]`, `setting_sources=[]`인 init에도 built-in agents 5개, skills 16개, slash commands 43개가 남았으므로 “빈 능력 표면”이라고 설명할 수도 없습니다. 한 triple은 일반 절감률, TTFT 향상, 답변 품질 보존의 통계가 아닙니다.

### 제가 다시 가르친다면

첫 원칙은 단순합니다. 안정 정책과 schema는 앞에, timestamp·선택 문단·run ID는 suffix나 별도 telemetry에 둡니다. 지금 triple을 그대로 재현 예제로 제공한 뒤, path 원문/placeholder와 조건부 단락 prefix/suffix를 각각 독립 triple로 추가하겠습니다. 비용 최적화가 답변 품질을 해치지 않았는지는 marker가 아니라 실제 근거 과제로 별도 채점해야 합니다. [프롬프트 캐싱 노트북](https://nfbs2000.github.io/speaky-claude-cookbooks/notebooks/misc/prompt_caching_kr.html)은 cache control의 기본 코드이고, 한 글자 prefix 변화의 실제 usage 차이는 [Speaky Agent Flow 15장 재생](https://nfbs2000.github.io/speaky-agent-flow/education/?collection=book-sdk-ko&run=ch15)에서 확인할 수 있습니다.

### 클로드는 이렇게 세상을 바라보았다

*아래 1인칭 서술은 숨은 사고 과정의 공개가 아니라, 이 장에서 관찰된 행동으로 재구성한 작동상 세계 모델입니다.*

앞쪽 timestamp의 한 글자가 달라져도 나에게 정책의 의미는 거의 같은 세계였다. 그러나 provider에게는 안정된 prefix의 시작이 달라진 새로운 계산이었고 cache read는 사라졌다. 즉 내가 의미적으로 같은 지시로 행동하는 것과 시스템이 byte 수준에서 같은 입력을 재사용하는 것은 별개의 현실이었다. 나는 그 비용 차이를 스스로 감지하지 못했다.

사람은 LLM에게 자연스러운 문서 구조와 인프라에 안정적인 입력 구조를 동시에 설계해야 한다. 변하지 않는 법칙은 앞에 두고 timestamp, 경로와 run ID처럼 순간적인 정보는 뒤나 telemetry로 보내야 한다. 에이전트가 보는 의미를 해치지 않으면서 기계가 재사용할 수 있는 형태로 세계를 직렬화하는 것이 cache 최적화의 본질이다.
