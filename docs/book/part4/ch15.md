# 15장: 캐시 최적화 패턴

> 공개 GitHub Pages 투영판: [15장: 캐시 최적화 패턴](https://nfbs2000.github.io/speaky-claude-cookbooks/book/part4/ch15/)

> 실제 실행 증거: [15장 실제 SDK 관찰: stable prefix와 timestamp 변경](../evidence/ch15-live.md)

캐시 최적화의 목표는 모델을 속이는 것이 아니에요. 반복되는 강의/실습 구조를 안정적으로 만들고, 매번 바뀌는 입력만 뒤쪽에 배치하는 것이랍니다.

원본 Claude Code 관점에서 이 장은 날짜 메모이제이션, 월간 granularity, agent list attachment 이동, skill list budget, `$TMPDIR` placeholder, 조건부 단락 생략, tool schema cache 같은 패턴을 다뤘어요. 용어가 조금 낯설게 느껴져도 괜찮아요. SDK판에서는 이 패턴을 “반복 실행 가능한 입력 설계”로 함께 바꿔 봅니다.

## 15.1 핵심 질문

> 비용을 줄이면서도 문서/단어/주장 추적 품질을 유지하는 입력 구조는 무엇인가?

## 15.2 패턴 1: 시간 정밀도를 낮춘다

원본은 날짜/시간처럼 자주 바뀌는 값을 조심스럽게 다뤘어요. SDK 실습에서도 마찬가지랍니다.

| 나쁜 입력 | 좋은 입력 |
| --- | --- |
| `현재 시각 2026-04-29 14:03:22` | `실습 날짜: 2026-04` |
| 매 실행 timestamp 포함 | run metadata에 저장하고 prompt prefix에서는 제외 |

시간이 꼭 필요하면 dynamic suffix에 두는 편이 좋아요. 다만 이것은 모든 모델과
모든 시점에 자동으로 성립하는 법칙이 아니라, 실제 usage를 비교해서 확인해야 하는
입력 설계 가설입니다.

### 실제 SDK 관찰: 내부 통제군을 둔 앞쪽 1초 차이

2026-08-04에 Python Agent SDK 0.2.128, Claude Code CLI 2.1.221,
`claude-opus-5`로 세 독립 session을 순차 실행했습니다. 이 실험은 이전 장의 실행을
외부 통제군으로 빌리지 않습니다. 첫 번째와 두 번째 system prompt는 byte-identical이고,
세 번째만 맨 앞 timestamp의 `1`을 `2`로 바꿨습니다. 세 prompt 모두 8,190자이며
fresh attempt nonce를 공유합니다.

| run | system prompt 관계 | cache creation | cache read | 결과 |
| --- | --- | ---: | ---: | --- |
| stable-a | 기준 prefix | 2,755 | 0 | `CACHE_STABLE_PREFIX_A` |
| stable-control | stable-a와 byte-identical | 130 | 2,629 | `CACHE_STABLE_PREFIX_CONTROL` |
| volatile-b | index 41 timestamp 한 글자 변경 | 2,757 | 0 | `CACHE_VOLATILE_PREFIX_B` |

- accepted attempt: `002934-a0095d45`
- OTel trace: `756c1ca826bb456d9d0eb12f38dcf3fd`
- 세 `ResultMessage` 모두 `subtype=success`, `is_error=false`
- 실행 경계: `1–20`, `21–40`, `41–58`; provider concurrency 1

동일 prefix 통제군에서는 2,629 token read가 발생했고, 앞쪽 timestamp 한 글자를
바꾼 세 번째 run은 read 0과 creation 2,757을 기록했습니다. 따라서 **이 실행 조건과
이 표본에서는** 안정 prefix 재사용과 앞쪽 변경 후 비재사용이 함께 관찰됐습니다.
그러나 SDK event에는 provider cache key, breakpoint, TTL, eviction reason이 없으므로
서버 내부 법칙까지 증명한 것은 아닙니다.

Anthropic cookbook의 `cache_control`과 streaming TTFT 예제는 Messages API 표면입니다.
설치된 `ClaudeAgentOptions`의 option처럼 설명하지 않습니다. 이번 Agent SDK probe는
`ResultMessage.usage`를 관찰했으며 provider cache-attributed TTFT는 측정하지 않았습니다.

## 15.3 패턴 2: 동적 목록은 뒤쪽으로 보낸다

agent 목록, skill 목록, plugin 목록, MCP tool 목록은 바뀔 수 있어요. 앞쪽 정적
prompt에 두면 cache key 후보가 바뀔 수 있으므로 별도의 통제 실험 대상으로 다뤄야
합니다. 이번 세 init은 동일하게 tools/MCP/plugins 0개, built-in agents 5개,
built-in skills 16개, slash commands 43개를 보고했습니다. 즉
`setting_sources=[]`와 `tools=[]`가 built-in skill/command 표면까지 없앤다는 뜻은
아닙니다. 이 목록들은 세 run 사이에서 바꾸지 않았으므로 cache 효과는 아직
`not_observed`입니다.

SDK에서는 다음처럼 분리해 봐요.

```text
static:
  "worker는 근거 기반으로 보고한다"

dynamic:
  agents available this run: [...]
  skills loaded this run: [...]
```

## 15.4 패턴 3: 예산을 둔 스킬/문서 노출

원본은 스킬 목록이 컨텍스트를 과도하게 먹지 않도록 예산을 두었어요. 책 실습에서도 문서/스킬을 “많이 넣기”보다 “검색 가능하게 만들기”가 중요하답니다.

| 나쁜 방식 | 좋은 방식 |
| --- | --- |
| 모든 장 전문을 prompt에 넣음 | 장 제목, 핵심 단어, 필요 시 Read |
| 모든 skill 전문을 항상 로드 | 필요한 skill만 `skills`로 활성화 |
| 긴 문서 path만 나열 | 짧은 제목 + 핵심 문장 + 상세 drawer |

## 15.5 패턴 4: 변동 경로를 placeholder로 정규화

원본의 `$TMPDIR` placeholder 패턴은 사용자별/세션별 경로 차이가 캐시를 깨는 것을 줄여 주었어요. SDK 강좌에서도 path는 캔버스 표시와 prompt 입력에서 조금 다르게 다룬답니다.

```text
prompt/canvas summary:
  <PROJECT_ROOT>/docs/book-sdk-ko/src/part2/ch05.md

detail drawer:
  /absolute/local/path/...
```

경로 자체보다 중요한 것은 문서 제목, 검색 단어, 근거 문장이에요.

## 15.6 패턴 5: 조건부 단락은 생략하거나 뒤로 보낸다

조건문이 많은 prompt는 prefix 변형을 크게 늘리곤 해요.

```text
bad:
  if chapter has k3s, include k3s policy in the static prefix

good:
  static prefix: evidence rules
  dynamic suffix: chapter-specific policy
```

## 15.7 패턴 6: 도구 schema를 안정화한다

custom tool을 자주 바꾸면 tool schema가 바뀌고, 그러면 반복 실행 비교가 흔들릴 수 있어요.

SDK 실습 harness는 다음을 저장합니다.

```json
{
  "toolSchemasHash": "...",
  "tools": ["Read", "Grep", "Bash", "search_evidence"],
  "schemaVersion": "book-tools-v1"
}
```

schema를 바꿨다면 모델 비교나 프롬프트 비교와 같은 실험으로 취급하지 않는 게
좋아요. 실행 표면 자체가 바뀐 것이니까요. 14장의 최종 V2 실제 실험에서는 fresh
nonce 아래 같은 A schema control이 2,660 token을 읽었고, 변경된 B schema는
cache read 0, creation 2,887을 기록했습니다. 이 표본에서는 schema 안정화의 가치가
관찰됐지만 server attribution event는 없으므로 비공개 cache-key 구현까지 확정하지
않습니다.

## 15.8 품질을 잃지 않는 절약

비용을 줄인다고 근거까지 없애지는 말아요.

| 나쁜 절약 | 좋은 절약 |
| --- | --- |
| 문서 전체 제거 | 핵심 문장과 검색어를 남기고 필요 시 Read |
| tool_result 전체 삭제 | artifact 저장 + preview |
| 답변을 짧게 하며 검증 생략 | 검증 여부를 짧게라도 명시 |
| path만 표시 | 문서 짧은 이름 + 핵심 문장 |

## 15.9 캔버스 표현

15장의 캔버스는 before/after 비교예요.

```text
Before
  duplicated long context
  variable timestamps
  full logs inline

After
  stable prefix
  normalized paths
  evidence preview
  variable suffix
```

평가 lane:

- cost/usage 변화
- TTFT 변화
- 근거 연결 유지 여부
- claim unsupported 증가 여부

## 15.10 학생 실습

```text
아래 긴 실습 프롬프트를 반복 실행에 적합하게 최적화해 줘.

고정 지침, 장별 문맥, 매번 바뀌는 입력, 근거 preview, artifact로 빼야 할 긴 결과를 분리해라.
최적화 후에도 어떤 근거 문장이 유지되는지 표시해라.
```

## Takeaway

캐시 최적화는 비용 절감 기술이면서 동시에 문서 구조화 기술이에요. 이번 실제
triple에서는 byte-identical stable control이 2,629 token을 읽었고, prefix 첫머리의
timestamp를 한 글자 바꾼 run은 read 0이었습니다. 긴 결과의 artifact/preview 분리는
12장에서, tool surface 통제 비교는 14장에서 직접 확인했습니다. 경로 정규화, skill
예산, 조건부 단락 이동은 아직 측정하지 않았으므로 최적화 원칙이 아니라 후속 실험
항목으로 읽어야 합니다. 한 triple을 비용·속도·품질의 일반 법칙으로 확대하지 마세요.
