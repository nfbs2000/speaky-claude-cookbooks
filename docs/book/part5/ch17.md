# 17장: YOLO 분류기

이 페이지는 한국어 SDK 책의 `17장: YOLO 분류기`을 공개 Python cookbook과 공식 Agent SDK 문서에 맞춰 다시 쓴 공개판이다. 원래 장의 문제의식은 유지하되, 내부 TypeScript 구현명이나 비공개 기능을 그대로 옮기지 않는다. 대신 실행 가능한 notebook, Python 파일, README, 공식 문서를 근거로 사용한다.

## 공개판 본문

원래 책은 이 장을 내부 구현과 강의 화면의 대응 관계로 설명한다. 공개판에서는 같은 내용을 "무엇을 설정했는가", "무엇이 메시지로 관측됐는가", "어떤 파일과 notebook으로 재현 가능한가"라는 세 질문으로 바꾼다.

첫째, 설정된 것은 실행 전 계약이다. Agent SDK에서는 model, system prompt, working directory, allowed/disallowed tools, MCP servers, skills/plugins, permission mode 같은 값이 agent가 볼 수 있는 세계를 정한다. 이 값은 말로 설명하는 정책이 아니라 실제 Python 코드와 notebook cell에서 확인되어야 한다.

둘째, 관측된 것은 message stream과 artifact다. assistant text, tool use, tool result, result message, usage/cost, audit log, generated file은 모두 나중에 검증 가능한 증거다. 그래서 이 책의 공개판은 "모델이 그렇게 했을 것이다"라고 쓰지 않고, 어떤 cookbook 파일에서 어떤 실행 표면을 볼 수 있는지 연결한다.

셋째, 추론한 것은 반드시 경계와 함께 둔다. 내부 기능 플래그, 숨은 프롬프트, classifier, cache key, sandbox implementation처럼 공개 SDK나 cookbook으로 확인할 수 없는 항목은 원문을 그대로 게시하지 않는다. 대신 공개 API에서 사용자가 설계할 수 있는 대응 표면으로 바꾸거나, "공개 대응 없음"으로 명시한다.

이 장을 읽을 때는 아래 순서가 좋다.

1. 먼저 주요 cookbook 근거를 열어 실제 notebook이나 Python 파일을 확인한다.
2. `ClaudeAgentOptions`, `query()`, `ClaudeSDKClient`, tool list, MCP config, hooks, session 관련 코드가 어디 있는지 찾는다.
3. 원문 절 제목을 따라가며 내부 설명을 공개 SDK 표면으로 바꿔 적는다.
4. 마지막으로 실습 방향에 맞춰 같은 task를 실행하고 message stream 또는 artifact를 남긴다.

## 공개 경계

- YOLO classifier 내부 기준이나 prompt는 게시하지 않는다.
- 자동 승인 설명은 공개 auto mode/permission 문서로만 한다.

## 실습 방향

- 읽기 전용, 수정 가능, 외부 API 쓰기 가능 task를 위험 등급별로 나눈다.

## Builder takeaway

이 장의 공개판 목표는 원문을 얕게 요약하는 것이 아니다. 책의 논지를 유지하되, 독자가 직접 열어볼 수 있는 Python cookbook과 공식 문서에 묶어 두는 것이다. 따라서 장을 읽은 뒤에는 적어도 하나의 notebook 또는 Python 파일에서 같은 개념을 확인할 수 있어야 한다. 확인할 수 없는 내부 세부는 주장으로 남기지 않고, 공개 경계나 추론으로 분리한다.

## 부록: 이 장을 실제 SDK 실행으로 확인한 결과

> 위 공개판 본문은 이 저장소의 notebook과 공식 문서에 근거해 다시 쓴 것이다. 아래는 같은
> 장의 주장을 실제 Claude Agent SDK로 실행해 관찰한 기록이며, **실측 결과로 위 본문을 고쳐
> 쓰지 않았다.** 본문 설명과 실제 동작이 어긋나는 곳도 본문을 남기고 아래에 근거와 함께 적는다.
> 사건 단위 원본 판독: [17장 실제 Python SDK auto mode 관찰](../evidence/ch17-live.md)

**실행 조건** — 실제 모델 `claude-opus-5`, Claude Agent SDK `0.2.128`, Claude Code CLI
`2.1.220`. 두 조건을 따로 실행했다(`123037-c98ae7ac` `auto` + 거부 콜백,
`123119-5244a816` 명시적 거부 뒤 대체 도구). 원본 사건 123건 중 47건을 정리했다.

부작용이 없는 통제 MCP 도구에 위험 표시만 달아, **실제로 파괴적인 일을 하지 않으면서** 권한
표면을 관찰했다.

### 실제로 확인된 것

- 두 시작 기록 모두 Opus 5, `auto` 모드, 연결된 MCP 서버를 기록했고 서로 다른 세션을 사용했다.
- **`auto` + 거부 콜백** — 도구 호출 뒤 호스트 handler와 표식 결과가 기록됐다. **거부를
  돌려주도록 구성한 권한 콜백 원본은 0행**이었다. 종료 기록은 성공, 권한 거절 0.
- **명시적 거부** — 도구 호출은 만들어졌지만 오류 결과로 거부되고 handler 실행 기록은 없었다.
  종료 권한 거절에는 같은 도구 이름·입력·호출 ID가 1건 남았다.
- 거부 뒤 모델은 읽기 전용 대체 도구를 호출했고, 호스트 handler와 표식 결과가 순서대로
  기록됐다.
- **도구 하나가 거부됐는데도 종료 결과 자체는 성공**이었다.
- **명시적으로 막은 custom MCP 도구의 이름은 시작 도구 목록에 그대로 남아 있었고** 모델도 호출을
  만들었다. 차단은 목록에서 지우는 방식이 아니라 실행 결과의 권한 거절로 나타났다.
- 두 실행의 무결성 해시 7개씩이 모두 일치하고, 원본과 OTel 순서가 전건 일치했다.

### 본문을 이렇게 읽으면 안 되는 곳

- **`auto`를 "위험 표시가 붙으면 항상 묻거나 막아 주는 안전장치"로 설명하면 안 된다.** 이
  요청은 콜백조차 거치지 않고 실제 handler까지 실행됐다.
- **`can_use_tool` 하나를 모든 도구 실행의 보편 감사 지점으로 설명하면 누락이 생긴다.** 첫
  실행은 콜백 0인데 handler가 실행됐고, 두 번째 명시적 거부도 콜백 없이 처리됐다.
- **거부 뒤의 대체 호출을 "모델이 스스로 찾아낸 안전 정책"으로 쓰면 안 된다.** 사용자
  프롬프트가 실행 전에 "거부되면 대체 도구를 정확히 한 번 부르라"고 지정했다.
- **모델의 원인 설명을 정책 근거로 쓰면 안 된다.** 모델은 위험 표시를 기준으로 걸러진 것 같다고
  추론했지만, 실제 원인은 `disallowed_tools`였다.
- **안전 목록 표를 `auto`가 보장하는 런타임 규칙으로 제시하면 안 된다.** 그 표는 호스트가
  구현할 제품 정책 예시다.
- **OTel span은 같은 기록기가 투영한 결과**이므로 순서 일치는 수집기의 무손실 확인이지 독립
  관측 증거가 아니다.
- 당시 기록의 소스 해시는 실행 시점 장 원문만 가리키며 probe·case·런타임 코드 전체를 묶지
  않았다.

### 이번 실행에서 관찰되지 않은 것

- `auto` 내부 분류 근거 — 왜 허용했는지 알려 주는 이유나 신뢰도 값은 기록에 없다.
- 위험 표시 자체의 인과 효과 — 표시만 한 변수로 통제해 비교하지 않았다.
- 실제 사람이 승인·거절하는 권한 UI와 그 왕복
- built-in 도구 전체, 실제 외부 변경, 다양한 입력에서의 `auto` 일반 동작 — 통제 MCP 두 표본으로는
  증명되지 않는다.

### 앞으로 필요한 관측

- 이 공개 실행은 Claude Code `2.1.220`에서 수집됐다. **현재 설치된 `2.1.221`의 동작을
  주장하려면 같은 probe와 프롬프트를 고정해 순차 재실행해야 한다.**

  독립 세션에서 한 변수만 통제해 추가 관찰해야 한다.
