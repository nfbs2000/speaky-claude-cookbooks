# 16장: 권한 시스템

이 페이지는 한국어 SDK 책의 `16장: 권한 시스템`을 공개 Python cookbook과 공식 Agent SDK 문서에 맞춰 다시 쓴 공개판이다. 원래 장의 문제의식은 유지하되, 내부 TypeScript 구현명이나 비공개 기능을 그대로 옮기지 않는다. 대신 실행 가능한 notebook, Python 파일, README, 공식 문서를 근거로 사용한다.

**분류:** 제5부: 안전성과 권한<br>
**공개 상태:** `public`<br>
**근거 신뢰도:** `high`<br>

## 이 장의 공개판 요지

이 장은 공개 SDK와 cookbook 예제로 대부분 직접 설명할 수 있다.

공개판에서는 권한 시스템을 `permission_mode`, `allowed_tools`, `disallowed_tools`, `can_use_tool`, hooks, user approval로 설명한다. `allowed_tools`는 도구를 제거하는 목록이 아니라 자동 승인과 관련된 정책이라는 점을 명확히 둔다. 도구를 실제로 막으려면 `disallowed_tools`와 hook/policy를 함께 고려한다. cookbook의 observability agent와 vulnerability detection agent는 Bash를 차단하거나 MCP tools만 허용하는 구체적 사례를 제공한다.

## 공개판 본문

원래 책은 이 장을 내부 구현과 강의 화면의 대응 관계로 설명한다. 공개판에서는 같은 내용을 "무엇을 설정했는가", "무엇이 메시지로 관측됐는가", "어떤 파일과 notebook으로 재현 가능한가"라는 세 질문으로 바꾼다.

첫째, 설정된 것은 실행 전 계약이다. Agent SDK에서는 model, system prompt, working directory, allowed/disallowed tools, MCP servers, skills/plugins, permission mode 같은 값이 agent가 볼 수 있는 세계를 정한다. 이 값은 말로 설명하는 정책이 아니라 실제 Python 코드와 notebook cell에서 확인되어야 한다.

둘째, 관측된 것은 message stream과 artifact다. assistant text, tool use, tool result, result message, usage/cost, audit log, generated file은 모두 나중에 검증 가능한 증거다. 그래서 이 책의 공개판은 "모델이 그렇게 했을 것이다"라고 쓰지 않고, 어떤 cookbook 파일에서 어떤 실행 표면을 볼 수 있는지 연결한다.

셋째, 추론한 것은 반드시 경계와 함께 둔다. 내부 기능 플래그, 숨은 프롬프트, classifier, cache key, sandbox implementation처럼 공개 SDK나 cookbook으로 확인할 수 없는 항목은 원문을 그대로 게시하지 않는다. 대신 공개 API에서 사용자가 설계할 수 있는 대응 표면으로 바꾸거나, "공개 대응 없음"으로 명시한다.

이 장을 읽을 때는 아래 순서가 좋다.

1. 먼저 주요 cookbook 근거를 열어 실제 notebook이나 Python 파일을 확인한다.
2. `ClaudeAgentOptions`, `query()`, `ClaudeSDKClient`, tool list, MCP config, hooks, session 관련 코드가 어디 있는지 찾는다.
3. 원문 절 제목을 따라가며 내부 설명을 공개 SDK 표면으로 바꿔 적는다.
4. 마지막으로 실습 방향에 맞춰 같은 task를 실행하고 message stream 또는 artifact를 남긴다.

## 공개 경계

- 내부 rule matching 코드나 classifier prompt는 공개하지 않는다.
- 권한 설명은 공개 evaluation order와 examples로 제한한다.

## 실습 방향

- Bash를 disallow한 분석 agent와 Bash를 허용한 remediation agent를 비교한다.

## Builder takeaway

이 장의 공개판 목표는 원문을 얕게 요약하는 것이 아니다. 책의 논지를 유지하되, 독자가 직접 열어볼 수 있는 Python cookbook과 공식 문서에 묶어 두는 것이다. 따라서 장을 읽은 뒤에는 적어도 하나의 notebook 또는 Python 파일에서 같은 개념을 확인할 수 있어야 한다. 확인할 수 없는 내부 세부는 주장으로 남기지 않고, 공개 경계나 추론으로 분리한다.

## 부록: 이 장을 실제 SDK 실행으로 확인한 결과

> 위 공개판 본문은 이 저장소의 notebook과 공식 문서에 근거해 다시 쓴 것이다. 아래는 같은
> 장의 주장을 실제 Claude Agent SDK로 실행해 관찰한 기록이며, **실측 결과로 위 본문을 고쳐
> 쓰지 않았다.** 본문 설명과 실제 동작이 어긋나는 곳도 본문을 남기고 아래에 근거와 함께 적는다.

**실행 조건** — 실제 모델 `claude-opus-5`, Claude Agent SDK `0.2.128`, Claude Code CLI
`2.1.221`(과거 비교용으로 `2.1.220` 실행도 함께 참조). 다섯 조건을 각각 새 작업 공간·설정·세션에서
한 건씩 실행했다(동시 실행 1). 원본 사건 287건 중 89건을 정리했다.

### 실제로 확인된 것

- **`acceptEdits`에서 `Read` → `Edit`** — 두 도구가 이어졌고 작업 공간의 표식과 해시가 실제로
  바뀌었다. 그런데 **권한 콜백 기록은 0행**이었고, SDK는 "도구 전체 허용이 콜백을 가렸다"는
  경고를 남겼다.
- **`bypassPermissions` + 거부 콜백** — 통제 MCP 도구 호출 뒤 호스트 실행과 표식 결과가
  나타났고 **콜백 기록은 0**이었다. 우회 모드가 콜백보다 먼저 자동 승인한다는 경고도 실제
  프로세스 기록에 남았다.
- **명시적 거부는 우회 모드보다 강한다.** 같은 도구를 `disallowed_tools`에 넣은 우회 실행은
  권한 거부 상태와 오류 도구 결과를 기록했고, 콜백 0·호스트 handler 0·종료 권한 거절 1이었다.
- 다섯 실행의 원본 SDK와 OTel 순서, 원본 프로세스와 OTel 순서가 각각 순서까지 전부 일치했고,
  무결성 해시도 모두 일치했다.

### 본문을 이렇게 읽으면 안 되는 곳

- **`can_use_tool`을 "모든 도구 직전에 항상 호출되는 콜백"으로 설명하면 안 된다.**
  `acceptEdits`와 우회 모드 실행에서는 도구가 실제로 실행되거나 거부됐는데도 **콜백 기록이 모두
  0**이었다.
- **"`Edit`는 먼저 `Read`하지 않으면 항상 실패한다"는 보편 법칙은 지워야 한다.** CLI
  `2.1.221`에서는 절대 경로와 상대 경로 모두 **선행 `Read` 없이 `Edit`가 성공**하고 작업 공간
  해시가 실제로 바뀌었다. `2.1.220`의 "아직 읽지 않은 파일" 오류는 **버전을 붙인 과거
  관찰**로 남겨야 한다.
- **종료 결과가 `success`인 것을 "모든 도구가 승인되고 실행됐다"로 읽으면 안 된다.** 명시적
  거부 실행은 오류 도구 결과와 권한 거절 1을 남기면서도 종료는 `success`, `is_error=false`였다.
- **권한 모드 값을 설정할 수 있다는 사실과, 모든 모드의 실제 의미를 이 장에서 검증했다는 주장은
  다릅니다.** 이번 실행은 `acceptEdits`와 `bypassPermissions` 두 모드에 집중했다.
- OTel 순서 일치는 기록기가 사건을 잃지 않았다는 확인이며 독립 관측 증거가 아니다.

### 관찰값에서 추론한 것 (관찰이 아니다)

- 명시적 거부가 자동 승인보다 앞서고, ask 콜백은 그 뒤의 미결정 호출에 쓰인다는 모델은 관찰
  결과와 일치한다. 다만 **내부 판정 함수의 호출 순서를 직접 본 것은 아니다.**
- `2.1.220`의 상대 경로 실패와 `2.1.221`의 성공 때문에 CLI 버전은 강한 변화 후보다. 그러나
  프롬프트와 probe 코드도 달라 **버전 하나로 원인을 확정할 수 없다.**

### 이번 실행에서 관찰되지 않은 것

- 내부 권한 판정기·분류기의 정확한 호출 순서와 단축 평가 지점
- 관리·사용자·프로젝트 설정 계층 전체, 그리고 정확 일치·접두·와일드카드 규칙의 우선순위
- `auto` 분류기의 내부 프롬프트와 판정 근거
- `2.1.220`과 `2.1.221` 사이에서 결과가 달라진 내부 원인
- "`PreToolUse`가 모든 도구를 관찰한다"는 이 장 전용 훅 경로 — 이번 다섯 실행에서 실행하지
  않았고 훅 콜백 원본도 비어 있다.
- 실제 사용자 승인 UI, 외부 파괴적 작업, 샌드박스와 OS 강제 — 통제된 임시 파일과 부작용 없는
  handler 실험의 범위 밖이다.

### 앞으로 필요한 관측

- `Read` 선행 요구가 달라진 원인을 좁히려면 **probe 커밋·프롬프트·경로·SDK를 고정하고 CLI만
  `2.1.220`↔`2.1.221`로 바꾸는 순차 회귀 실행**이 필요한다.
- `PreToolUse` 보편 관찰, 기본 ask 콜백, 설정 계층과 와일드카드 규칙은 각각 한 변수만 바꾸는
  별도 실행으로 다뤄야 한다.
- 8f장·4b장의 기존 실행은 재사용할 수 있지만, 이번 다섯 실행과 하나로 합치지 말고 출처와
  세션을 분리해 연결해야 한다.
