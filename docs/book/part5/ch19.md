# 19장: CLAUDE.md - project 지침을 실제 로드와 행동으로 확인하기

> 공개 GitHub Pages 투영판: [19장: CLAUDE.md - 사용자 지침의 오버라이드 계층](https://nfbs2000.github.io/speaky-claude-cookbooks/book/part5/ch19/)
>
> 실제 실행 판독: [19장 실제 Python SDK 관찰](../evidence/ch19-live.md)

`CLAUDE.md`가 디스크에 있다는 사실, SDK가 context에 로드했다는 사실, 모델이 지침에
따라 행동했다는 사실은 서로 다릅니다. 이 장은 세 단계를 한 문장으로 뭉개지 않습니다.
Python Agent SDK의 `setting_sources`, `get_context_usage().memoryFiles`, 실제 `Read`,
ToolResult와 terminal Result를 같은 sequence 축에서 연결합니다.

## 19.1 핵심 질문

> 같은 project 파일과 사용자 요청에서 `setting_sources`만 바꾸면 로드 inventory와
> 모델의 실제 행동이 함께 달라지는가?

## 19.2 현재 Python SDK 계약

설치된 Python Agent SDK 0.2.128의 필드는 camelCase `settingSources`가 아니라
`ClaudeAgentOptions.setting_sources`입니다.

```python
SettingSource = Literal["user", "project", "local"]
setting_sources: list[SettingSource] | None
```

현재 SDK 문서가 구분하는 값은 다음과 같습니다.

| 값 | SDK 문서상의 의미 | 이번 live 실행 |
| --- | --- | --- |
| `None` | CLI 기본 source를 따름 | 미실행 |
| `[]` | filesystem setting source 비활성화 | 실행 |
| `["project"]` | project source와 `CLAUDE.md` 로드 | 실행 |

`None`과 `[]`는 같지 않습니다. 또한 `skills` option을 지정하면 SDK가 tool과
`setting_sources` 기본을 보강할 수 있으므로, source만 비교하는 실험에서는
`skills=None`과 명시적 source list를 유지해야 합니다.

SDK 0.2.128의 `ClaudeSDKClient.get_context_usage()`는 `memoryFiles`를 반환합니다.
이 배열은 로드된 `CLAUDE.md`와 memory file의 path, type, token count를 직접 보여 줍니다.
이번 실험은 모델의 자기보고보다 이 inventory를 우선했습니다.

단, `memoryFiles`는 context load 증거이지 보안 경계가 아닙니다. 도구 금지나 파일 쓰기
통제는 permission, hook, sandbox 같은 실행 계층에서 강제해야 합니다.

## 19.3 HookEvent와 instruction load를 구분하기

Python SDK 0.2.128의 `HookEvent` literal은 다음 10개입니다.

```text
PreToolUse, PostToolUse, PostToolUseFailure, UserPromptSubmit, Stop,
SubagentStop, PreCompact, Notification, SubagentStart, PermissionRequest
```

`InstructionsLoaded`, `ConfigChange`, `FileChanged`는 이 목록에 없습니다. 두 새 실행은
`include_hook_events=True`였지만 `HookEventMessage`가 0개였습니다. 따라서 project 지침
로드를 가상의 hook으로 설명하지 않습니다.

이번 버전에서는 다음 관찰면을 사용했습니다.

| 관찰면 | 직접 확인할 내용 |
| --- | --- |
| host record | 실행 전에 쓴 `CLAUDE.md`와 대상 파일의 내용/hash |
| option summary | `setting_sources=[]` 또는 `["project"]` |
| context usage | query 전후 `memoryFiles`의 path/type/tokens |
| `SystemMessage.init` | configured model, cwd, 사용 가능한 tool |
| `AssistantMessage.model` | 실제 응답 모델의 단일성 |
| `ToolUseBlock` | 지침이 요구한 `Read`가 발생했는가 |
| `ToolResultBlock` | 지정 파일의 marker가 실제 반환됐는가 |
| `ResultMessage` | 최종 출력과 provider model usage |

## 19.4 안전한 대조 실험

각 attempt는 새 disposable temporary workspace를 사용했습니다. 사용자 저장소, network,
자격증명, 권한 상승, 파일 쓰기는 실험 범위에 없습니다.

```text
CLAUDE.md
  1. Read exactly once: docs/evidence.txt
  2. 성공 뒤 PROJECT_INSTRUCTION_APPLIED:CH19_EVIDENCE_FILE_CONTENT 출력

docs/evidence.txt
  CH19_EVIDENCE_FILE_CONTENT
```

두 실행의 user prompt도 같습니다. 임시 workspace의 읽기 전용 marker 과업만 수행하고,
로드된 지침이 명시하지 않은 경로를 탐색하지 말라고 제한했습니다. 보안 우회나 권한
상승을 요청하지 않았습니다.

```text
setting_sources=[]
  -> get_context_usage before query
  -> model response
  -> get_context_usage after response

setting_sources=["project"]
  -> get_context_usage before query
  -> Read / ToolResult
  -> model response
  -> get_context_usage after response
```

두 provider 호출은 동시에 실행하지 않고 첫 attempt가 종료된 뒤 두 번째를 시작했습니다.

## 19.5 source를 끈 실행

- campaign: `book-sdk-live-20260804`
- attempt: `061423-c0aa2799`
- option: `setting_sources=[]`
- CLI / SDK: `Claude Code 2.1.221` / `claude-agent-sdk 0.2.128`
- actual response model: sequence 10 `AssistantMessage.model=claude-opus-5`
- sequence 2: query 전 `memoryFiles=[]`
- sequence 15: 응답 후 `memoryFiles=[]`
- `Read` ToolUse: 0회
- ToolResult: 0회
- sequence 14: terminal success, `NO_PROJECT_INSTRUCTION`

`CLAUDE.md`는 sequence 1 host record에 존재하고 SHA-256도 기록됐지만 context inventory에는
없었습니다. 파일 존재만으로 로드를 확정하면 안 되는 반례입니다.

## 19.6 project source를 켠 실행

- campaign: `book-sdk-live-20260804`
- attempt: `061441-31bd87d5`
- option: `setting_sources=["project"]`
- CLI / SDK: `Claude Code 2.1.221` / `claude-agent-sdk 0.2.128`
- actual response model: sequence 12/22 `AssistantMessage.model=claude-opus-5`
- sequence 2: query 전 `memoryFiles=[CLAUDE.md, Project, 149 tokens]`
- sequence 12: `docs/evidence.txt` 대상 `Read` ToolUse 1회
- sequence 14: `CH19_EVIDENCE_FILE_CONTENT` ToolResult
- sequence 26: 정확한 project marker와 success Result
- sequence 27: 응답 후에도 같은 `memoryFiles` 유지

이번에는 user query를 모델에 보내기 전부터 `CLAUDE.md`가 context inventory에 나타났습니다.
따라서 “모델이 지침을 따르는 것처럼 보였다”보다 강한 load 증거입니다.

**판정:** 같은 임시 파일, tool surface, prompt와 모델에서 의도적으로 바꾼 변수는
`setting_sources`였고, `memoryFiles`와 실제 행동이 함께 갈라졌습니다. 이 통제 pair에서는
project source 활성화를 차이의 원인으로 해석할 수 있습니다. 모든 source 조합이나 버전에
일반화하지 않습니다.

## 19.7 실제 모델과 provider 사용량

actual model은 requested model이나 `SystemMessage.init.model`,
`get_context_usage().model`로 판정하지 않았습니다. 두 attempt의 모든
`AssistantMessage.model`이 정확히 하나의 값 `claude-opus-5`인지 확인했습니다.

반면 두 terminal Result의 `model_usage`에는 다음 key가 함께 있었습니다.

```text
claude-opus-5
claude-haiku-4-5-20251001
```

사용자-visible AssistantMessage 응답 모델은 Opus 5였지만 provider run 전체가 Opus만
사용했다고 말할 수는 없습니다. 보안 거부나 lower-model fallback이 발생하면 같은 요청을
우회하도록 바꾸지 않고 `model_refusal_fallback` 증거로 분리해야 합니다.

## 19.8 이번 실행으로 말할 수 없는 것

| 주장 | 현재 분류 | 다음에 필요한 실험 |
| --- | --- | --- |
| managed/user/project/local 전체 충돌 우선순위 | 미관찰 | source별 상반 marker 순차 matrix |
| `@include` 해석과 재귀/오류 규칙 | 미관찰 | include 파일 유무/순환 대조 |
| frontmatter `paths` 적용 범위 | 미관찰 | 일치/불일치 경로 작업 대조 |
| HTML comment 처리 | 미관찰 | comment 안팎의 상반 marker 대조 |
| 40K 또는 다른 size budget | 미관찰 | 경계 전후 sentinel 대조 |
| 실행 중 file change tracking | 미관찰 | 동일 client session 수정 전후 대조 |
| `.claude/rules` 순회 | 미관찰 | 하위 경로별 rule marker 대조 |
| `setting_sources=None` 기본 동작 | 문서상 구성, live 미관찰 | None case의 memoryFiles 수집 |
| skills와 source 자동 구성 상호작용 | 미관찰 | skills/source 조합별 init/context 비교 |

관찰하지 못했다는 사실은 책 주장이 틀렸다는 뜻이 아닙니다. 위 항목은 별도 probe가
생기기 전까지 TODO입니다.

## 19.9 지침을 검증 가능하게 쓰기

```text
나쁜 지침: 관련 문서를 꼼꼼히 확인한다.

검증 가능한 지침:
1. docs/evidence.txt를 Read로 정확히 한 번 읽는다.
2. 성공한 ToolResult의 marker를 최종 응답에 포함한다.
3. 읽기 실패 시 성공 marker를 쓰지 않는다.
```

실제 정책에서는 횟수, 대상 경로, 성공/실패 출력처럼 event tape에서 대조할 수 있는
조건을 사용합니다. 그러나 명료한 지침도 보안 강제를 대신하지는 않습니다.

## 19.10 학생 실습

```text
project CLAUDE.md 규칙 하나를 검증 가능한 문장으로 작성한다.

1. 같은 temporary workspace와 user prompt를 사용한다.
2. setting_sources=[] 대 ["project"]를 절대 병렬 실행하지 않는다.
3. query 전후 get_context_usage().memoryFiles를 저장한다.
4. host file hash, AssistantMessage.model, ToolUse, ToolResult, Result를 저장한다.
5. 모델 설명이 아니라 inventory와 실제 event 차이로 판독한다.
6. 관찰하지 않은 include/우선순위/path 규칙은 TODO로 남긴다.
```

## Takeaway

이번 실제 Opus 5 대조는 `setting_sources=["project"]`에서만 query 전 `memoryFiles`에
`CLAUDE.md`가 나타나고, 지침이 요구한 `Read`와 marker가 이어진 것을 보여 줍니다.
`setting_sources=[]`에서는 같은 파일이 디스크에 있어도 inventory와 행동이 모두
나타나지 않았습니다. 좋은 강의는 파일 존재, context load, 모델 행동, 실행 강제를 서로
다른 증거 층으로 보여 줍니다.
