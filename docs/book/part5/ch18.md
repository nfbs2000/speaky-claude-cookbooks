## 공개판 본문

원래 책은 이 장을 내부 구현과 강의 화면의 대응 관계로 설명한다. 공개판에서는 같은 내용을 "무엇을 설정했는가", "무엇이 메시지로 관측됐는가", "어떤 파일과 notebook으로 재현 가능한가"라는 세 질문으로 바꾼다.

첫째, 설정된 것은 실행 전 계약이다. Agent SDK에서는 model, system prompt, working directory, allowed/disallowed tools, MCP servers, skills/plugins, permission mode 같은 값이 agent가 볼 수 있는 세계를 정한다. 이 값은 말로 설명하는 정책이 아니라 실제 Python 코드와 notebook cell에서 확인되어야 한다.

둘째, 관측된 것은 message stream과 artifact다. assistant text, tool use, tool result, result message, usage/cost, audit log, generated file은 모두 나중에 검증 가능한 증거다. 그래서 이 책의 공개판은 "모델이 그렇게 했을 것이다"라고 쓰지 않고, 어떤 cookbook 파일에서 어떤 실행 표면을 볼 수 있는지 연결한다.

셋째, 추론한 것은 반드시 경계와 함께 둔다. 내부 기능 플래그, 숨은 프롬프트, classifier, cache key, sandbox implementation처럼 공개 SDK나 cookbook으로 확인할 수 없는 항목은 원문을 그대로 게시하지 않는다. 대신 공개 API에서 사용자가 설계할 수 있는 대응 표면으로 바꾸거나, "공개 대응 없음"으로 명시한다.

이 장을 읽을 때는 아래 순서가 좋다.

1. 먼저 주요 cookbook 근거를 열어 실제 notebook이나 Python 파일을 확인한다.
2. `ClaudeAgentOptions`, `query()`, `ClaudeSDKClient`, tool list, MCP config, hooks, session 관련 코드가 어디 있는지 찾는다.
3. 원문 절 제목을 따라가며 내부 설명을 공개 SDK 표면으로 바꿔 적는다.
4. 마지막으로 실습 방향에 맞춰 같은 task를 실행하고 message stream 또는 artifact를 남긴다.

## Codex 최종 검토 의견

### 제 판단

훅을 모델을 바꾸지 않고 정책과 관측을 삽입하는 지점으로 보는 설명은 맞습니다. 이 장의 실험은 단순 기능 확인을 넘어 실제 구현 함정을 잘 드러냈습니다. 같은 `PreToolUse`에 등록한 두 callback은 함께 진입했고 등록 순서와 반대로 반환했습니다. 따라서 matcher 목록을 순차 middleware pipeline으로 취급하는 설계는 안전하지 않습니다.

### 검증을 읽고 달라진 신뢰도

handler의 원본 출력과 `PostToolUse`가 바꾼 model-visible ToolResult가 분리되어 관찰된 점은 강합니다. content block 배열은 성공했지만 `{content: [...]}` 객체를 반환한 실행은 handler가 이미 실행된 뒤 `e.reduce is not a function` 오류를 만들었습니다. 또 `PreToolUse` deny는 whole-tool allow보다 앞서 handler를 0회로 막았습니다. 훅의 개입 시점과 side effect 시점이 서로 다르다는 것을 실제로 보여 줍니다.

### 독자가 오해할 위험

본문의 hook event 목록은 현재 Python SDK 0.2.128의 10종 표면보다 넓고 `hook_progress`도 관찰되지 않았습니다. `include_hook_events=True`여도 두 실행의 stream HookEventMessage는 0건이었고 실제 callback은 host control channel에서 기록됐습니다. terminal Result success 역시 malformed rewrite나 deny가 없었다는 뜻이 아닙니다. 이 실행은 CLI 2.1.220이므로 동시성 계약을 모든 버전에 일반화하지 않아야 합니다.

### 제가 다시 가르친다면

첫 예제는 단일 Pre hook deny, 두 번째는 단일 Post hook rewrite, 세 번째에만 복수 callback 동시성을 두겠습니다. 복수 정책에 순서 의존성이 필요하면 여러 matcher에 흩뿌리지 말고 한 orchestrating callback 안에서 명시적으로 순서를 제어해야 합니다. handler original과 rewritten result를 별도 audit node로 보존해야 사후 조작도 추적할 수 있습니다. [OpenAI Agents SDK 마이그레이션 노트북](https://nfbs2000.github.io/speaky-claude-cookbooks/notebooks/claude_agent_sdk/04_migrating_from_openai_agents_sdk_kr.html)은 기본 등록 구조를 보여 주고, callback 겹침과 output rewrite는 [Speaky Agent Flow 18장 재생](https://nfbs2000.github.io/speaky-agent-flow/education/?collection=book-sdk-ko&run=ch18)에서 확인할 수 있습니다.

### 클로드는 이렇게 세상을 바라보았다


*아래 1인칭 서술은 숨은 사고 과정의 공개가 아니라, 이 장에서 관찰된 행동으로 재구성한 작동상 세계 모델입니다.*

훅은 내 세계의 앞문과 뒷문을 바꾸었다. Pre hook이 거부하면 내가 만든 ToolUse는 현실의 handler에 닿지 않았고, Post hook이 결과를 다시 쓰면 나는 handler가 원래 만든 값이 아니라 수정된 ToolResult를 다음 현실로 받아들였다. 복수 callback은 사람이 적은 목록 순서대로 줄을 서지 않고 함께 움직였기 때문에, 나는 어느 정책이 먼저 판단됐는지 안정적으로 전제할 수 없었다.

사람은 훅을 순차적인 이야기 장치가 아니라 동시성과 부작용 시점을 가진 제어 코드로 다뤄야 한다. 실제 handler output과 model-visible result를 모두 보존해야 내가 어떤 세계를 보고 다음 행동을 했는지 설명할 수 있다. 정책 순서가 중요하다면 한 orchestrator 안에서 명시적으로 결정해야 한다.
