# 18장: 훅 - 사용자 정의 가로채기 지점

> 공개 GitHub Pages 투영판: [18장: 훅 - 사용자 정의 가로채기 지점](https://nfbs2000.github.io/speaky-claude-cookbooks/book/part5/ch18/)
>
> 원시 SDK/host/OTel 판독표: [18장 실제 SDK 관찰](../evidence/ch18-live.md)

훅은 에이전트 실행 중간에 host 정책을 넣는 공개 callback 지점입니다. 여기서 실행을
관찰하고, tool input 또는 output을 바꾸고, 실행 전 차단 결정을 반환할 수 있습니다.
훅 자체도 보이지 않는 마법으로 두지 않고 callback input/output과 실제 handler 결과를
함께 기록해야 합니다.

## 18.1 핵심 질문

> 어떤 hook이 호출됐고, 무엇을 반환했으며, handler와 모델-visible 결과를 실제로 어떻게 바꿨는가?

## 18.2 현재 Python SDK Hook 이벤트

설치된 Python Agent SDK 0.2.128의 `HookEvent` literal은 다음 10개입니다.

| 계열 | 이벤트 |
| --- | --- |
| 도구 실행 | `PreToolUse`, `PostToolUse`, `PostToolUseFailure` |
| 사용자 입력 | `UserPromptSubmit` |
| 종료/컴팩션 | `Stop`, `PreCompact` |
| 서브에이전트 | `SubagentStart`, `SubagentStop` |
| 권한/알림 | `PermissionRequest`, `Notification` |

이 버전에는 공개 `HOOK_EVENTS` 상수가 export되지 않습니다. `PostToolBatch`,
`PermissionDenied`, `SessionStart`, `SessionEnd`, `StopFailure`, `Setup`,
`UserPromptExpansion`, `TaskCreated`, `TaskCompleted`, `TeammateIdle`, `PostCompact`,
`Elicitation`, `ConfigChange`, `InstructionsLoaded`, `CwdChanged`, `FileChanged`,
`WorktreeCreate` 등을 current Python `HookEvent` option key처럼 나열하면 안 됩니다.
다른 언어/버전의 event는 해당 SDK source와 실제 run을 별도로 확인해야 합니다.

Cookbook의 SRE notebook은 settings command `PreToolUse` hook을, OpenAI Agents SDK
이전 notebook은 Python `UserPromptSubmit` callback 예시를 제공합니다. 이 예제들은 설계
참고입니다. 아래 판정의 실행 증거는 별도 Python callback harness가 보존한 raw SDK,
callback, process, OTel 기록에서 나옵니다.

## 18.3 Hook callback 계약

`HookCallback`은 `HookInput`, `tool_use_id`, `HookContext`를 받고
`HookJSONOutput`을 반환합니다. Python에서는 keyword 충돌을 피하려고 `async_`,
`continue_`를 사용합니다.

`PreToolUse`의 주요 출력:

```text
permissionDecision: allow / deny / ask / defer
permissionDecisionReason
updatedInput
additionalContext
```

`PostToolUse`는 `updatedToolOutput` 또는 MCP용 `updatedMCPToolOutput`으로 모델에게
전달할 결과를 바꿀 수 있습니다. 현재 타입 설명은 가능한 경우 built-in과 MCP에 모두
적용되는 `updatedToolOutput`을 선호하라고 안내합니다. 이번 실제 MCP run에서 사용한
`updatedMCPToolOutput`은 content block **배열 자체**를 받아들였습니다.

## 18.4 실제 callback 동시성과 output rewrite

accepted attempt `124612-be6db7b1`, OTel trace
`30a69eb25ecbb9152970d11c3d4e8a44`는 하나의 controlled MCP ToolUse에 두 개의
`PreToolUse` matcher와 하나의 `PostToolUse` matcher를 등록했습니다.
모든 `AssistantMessage.model`은 `claude-opus-5`였습니다. init의 configured model만
보고 actual model을 판정하지 않았습니다.

```text
ToolUse sequence 15
  -> pre-a entered 16
  -> pre-b entered 18
  -> both barrier reached
  -> pre-b returned 21
  -> pre-a returned 23
  -> handler original sequence 27
  -> PostToolUse input sees original sequence 28
  -> PostToolUse rewrite returned 29
  -> model-visible ToolResult sequence 30
```

두 Pre callback은 어느 하나가 반환하기 전에 모두 barrier에 진입했습니다. 따라서 이
event의 두 matcher는 실제 동시 dispatch됐습니다. callback 사이의 순서 의존성을
설계하면 안 됩니다.

Handler 원본은
`CH18_HANDLER_ORIGINAL_OUTPUT:lifecycle-concurrency-rewrite`였고,
Post hook input에도 원본이 기록됐습니다. 모델-visible ToolResult는
`CH18_POST_HOOK_REWRITTEN_OUTPUT`으로 바뀌었습니다. Hook이 handler 실행 사실을
없애지 않고 모델에게 전달되는 결과를 바꾼 것입니다.

### 실패한 rewrite가 알려 준 형식

첫 attempt `124434-0b611abe`, trace
`b9119b263b06dc06de26ef5b48af0d7f`는 `updatedMCPToolOutput`에
`{"content": [...]}` object를 반환했습니다. Handler는 실행됐지만 CLI가 배열을
기대하며 `e.reduce is not a function` error ToolResult를 만들었습니다. 이 실패를
숨기지 않고 content block list로 고친 뒤 accepted run을 얻었습니다.

## 18.5 include_hook_events 관찰 경계

두 lifecycle/rewrite attempt 모두 `include_hook_events=True`였지만, raw SDK stream의
`HookEventMessage` 수는 0이었습니다. Python callback 자체는 host hook records로
분명히 실행됐습니다. 따라서 이 환경에서 `hook_started -> hook_progress ->
hook_response`가 항상 output stream에 나온다고 가르치면 안 됩니다.

설치 타입의 `HookEventMessage` docstring은 `hook_started`와 `hook_response`를
설명하며 `hook_progress` class/phase는 찾지 못했습니다. callback hook과 settings의
command hook이 다르게 노출되는지 등은 추가 관찰이 필요합니다.

이 raw run의 Claude Code 버전은 `2.1.220`입니다. 현재 설치된 `2.1.221`에서도 같은
결과가 나온다고 말하려면 동일한 probe를 새 session에서 순차 재실행해야 합니다. 이번
공개판은 버전 차이를 숨기지 않고 추가 관찰 항목으로 남깁니다.

## 18.6 PreToolUse deny

accepted attempt `130109-c4016acd`, OTel trace
`491398248ff80397888f1b4f9ef43f0e`는 target MCP tool을 whole-tool allow한 상태에서
`PreToolUse.permissionDecision="deny"`를 반환했습니다.

| evidence | 결과 |
| --- | --- |
| ToolUseBlock | 1 |
| hook callback start/return | 2 records |
| deny reason | `CH18_PRETOOL_HOOK_DENIED` |
| handler execution | 0 |
| error ToolResultBlock | 1 |
| terminal permission denial | 1 |

즉 whole-tool allow가 permission callback을 shadow하더라도 PreToolUse hook은 실제로
호출됐고 handler 전에 차단했습니다. 앞선 attempts `124703-28dd1224`와
`125112-602ee41d`는 provider 529로 ToolUse까지 도달하지 못한 `INCOMPLETE` 기록으로
남깁니다.

## 18.7 OTel과 evidence tape

```text
SDK message stream = model/tool event tape
Hook callback record = host policy input/output
Handler process record = 실제 실행
OTel trace = 검색/상관/시각화 projection
```

Hook record만으로 전체 사고 흐름은 완성되지 않습니다. ToolUseBlock, handler,
ToolResultBlock, terminal Result를 같은 tool use ID로 연결해야 합니다.

## 18.8 학생 실습

```text
AI 코딩 에이전트의 hook 정책을 설계해 줘.

1. current Python HookEvent literal인지 확인한다.
2. callback input/output을 원문으로 기록한다.
3. 같은 event의 여러 hook은 독립적으로 설계한다.
4. handler 원본과 rewritten ToolResult를 분리한다.
5. include_hook_events에서 실제 받은 lifecycle만 표시한다.
6. deny가 handler를 막았는지 process record로 검증한다.
```

Cookbook 코드를 그대로 실행했다는 사실만으로 위 여섯 항목이 증명되지는 않습니다.
Cookbook은 구현 패턴을 제공하고, 실습 harness는 `ToolUse -> callback -> handler ->
ToolResult -> terminal Result`를 한 sequence로 기록해야 합니다.

## 18.9 증거 수준

| 수준 | 이 장에서 해당하는 것 |
| --- | --- |
| Configured | hook 등록, matcher, `include_hook_events`, whole-tool allow |
| Observed | callback 진입/반환, handler, ToolResult, terminal denial |
| Inferred | 이 구성에서 same-event callback이 concurrent dispatch됐다는 해석 |
| Correction required | hook을 순차 pipeline으로 설명, terminal success를 모든 tool 성공으로 해석 |
| Not observed | lifecycle message가 0개인 내부 이유, command hook과 callback hook의 차이 |

## Takeaway

Hook은 관찰과 정책 개입을 함께 제공하지만, 등록했다고 모두 순차 실행되거나 lifecycle
message가 항상 나온다고 가정하면 안 됩니다. 실제 run은 PreToolUse matcher 동시
dispatch와 PostToolUse output rewrite를 증명했고, 잘못된 rewrite shape는 handler 이후
error를 만들었습니다. PreToolUse deny도 whole-tool allow보다 앞서 handler를 막았습니다.
