## 공개판 본문

원래 책은 이 장을 내부 구현과 강의 화면의 대응 관계로 설명한다. 공개판에서는 같은 내용을 "무엇을 설정했는가", "무엇이 메시지로 관측됐는가", "어떤 파일과 notebook으로 재현 가능한가"라는 세 질문으로 바꾼다.

첫째, 설정된 것은 실행 전 계약이다. Agent SDK에서는 model, system prompt, working directory, allowed/disallowed tools, MCP servers, skills/plugins, permission mode 같은 값이 agent가 볼 수 있는 세계를 정한다. 이 값은 말로 설명하는 정책이 아니라 실제 Python 코드와 notebook cell에서 확인되어야 한다.

둘째, 관측된 것은 message stream과 artifact다. assistant text, tool use, tool result, result message, usage/cost, audit log, generated file은 모두 나중에 검증 가능한 증거다. 그래서 이 책의 공개판은 "모델이 그렇게 했을 것이다"라고 쓰지 않고, 어떤 cookbook 파일에서 어떤 실행 표면을 볼 수 있는지 연결한다.

셋째, 추론한 것은 반드시 경계와 함께 둔다. 내부 기능 플래그, 숨은 프롬프트, classifier, cache key, sandbox implementation처럼 공개 SDK나 cookbook으로 확인할 수 없는 항목은 원문을 그대로 게시하지 않는다. 대신 공개 API에서 사용자가 설계할 수 있는 대응 표면으로 바꾸거나, "공개 대응 없음"으로 명시한다.

이 장을 읽을 때는 아래 순서가 좋다.

1. 먼저 주요 cookbook 근거를 열어 실제 notebook이나 Python 파일을 확인한다.
2. `ClaudeAgentOptions`, `query()`, `ClaudeSDKClient`, tool list, MCP config, hooks, session 관련 코드가 어디 있는지 찾는다.
3. 원문 절 제목을 따라가며 내부 설명을 공개 SDK 표면으로 바꿔 적는다.
4. 마지막으로 실습 방향에 맞춰 같은 task를 실행하고 message stream 또는 artifact를 남긴다.

## Codex 최종 검토 의견

### 제 판단

이 장은 모델을 감상으로 비교하지 말고 동일 하니스에서 행동과 비용을 비교하라는 방법론으로는 옳습니다. 그러나 현재 검증은 제목의 “모델별 A/B”를 수행하지 않았습니다. 두 실행 모두 실제 모델이 `claude-opus-5`이고, 바뀐 것은 system prompt 정책 하나입니다. 따라서 이 장에서 말할 수 있는 결론은 모델 우열이 아니라 **같은 모델의 prompt-policy A/B를 어떻게 기록하는가**까지입니다.

### 검증을 읽고 달라진 신뢰도

fixture, 사용자 요청, tool surface를 고정하고 system prompt 해시만 달리한 점은 A/B 기본기를 지켰습니다. patched 실행이 175단어 짧고 비용과 API 시간이 작았다는 관찰도 사실입니다. 하지만 baseline도 주장 전에 Grep/Read를 했고 patched는 잘못된 절대경로 Read를 한 번 실패했습니다. 독립 반복이 없는 이 한 쌍에서 “근거 우선 정책이 더 정확하고 싸다”는 일반 결론은 나오지 않습니다.

### 독자가 오해할 위험

표에 모델 A와 B를 그려 놓았다는 이유로 실제 cross-model evidence가 있다고 생각하기 쉽습니다. 또 `duration_api_ms`를 사용자 체감 지연으로, 요청 model 하나를 전체 provider 비용의 유일한 모델로 읽어도 안 됩니다. 두 Result에는 보조 모델 사용도 있었습니다. 내부 코드명이나 hidden prompt를 복원하지 않는다는 윤리 원칙은 좋지만, 그것 자체가 모델 비교 결과를 대신하지는 않습니다.

### 제가 다시 가르친다면

이 장을 두 단계로 나누겠습니다. 먼저 현재 코드를 “same-model prompt A/B”의 정직한 예제로 보여 주고, 다음에 동일 fixture를 두 실제 모델에서 순서를 교차해 최소 여러 번 직렬 실행하겠습니다. winner 하나 대신 근거 파일 확인률, 잘못된 경로 복구, 근거 없는 주장, 비용, wall time의 분포를 따로 제시해야 합니다. [평가 만들기 노트북](https://nfbs2000.github.io/speaky-claude-cookbooks/notebooks/misc/building_evals_kr.html)의 rubric 분리가 이 실험의 기준이며, 현재 한 쌍이 보여 주는 실제 범위는 [Speaky Agent Flow 7장 재생](https://nfbs2000.github.io/speaky-agent-flow/education/?collection=book-sdk-ko&run=ch07)에서 확인할 수 있습니다.

### 클로드는 이렇게 세상을 바라보았다


*아래 1인칭 서술은 숨은 사고 과정의 공개가 아니라, 이 장에서 관찰된 행동으로 재구성한 작동상 세계 모델입니다.*

나는 A/B 실험 전체를 내려다보지 않았다. 각 실행에서 나에게 존재한 것은 그때 주어진 system prompt, fixture와 도구뿐이었고, 다른 조건의 나와 경쟁하고 있다는 사실은 내 세계에 없었다. 한 실행에서는 짧게 끝났고 다른 실행에서는 경로를 한 번 틀렸지만, 어느 쪽이 더 좋은지는 내 답 안에서 결정되지 않았다. 비교는 두 세계의 기록을 함께 볼 수 있는 host와 evaluator의 일이다.

사람은 모델에게 자기 우수성을 평가하게 하기보다 동일한 외부 rubric으로 여러 실행을 비교해야 한다. LLM의 세계는 한 run 안에 갇혀 있으므로 비용, 지연, 근거 확인률과 오류 분포는 바깥에서 측정해야 한다. 좋은 A/B는 승자의 말이 아니라 통제된 세계 차이와 반복된 관찰로 결론을 만든다.
