# 7장: 모델별 튜닝과 A/B 테스트

> 공개 GitHub Pages 투영판: [7장: 모델별 튜닝과 A/B 테스트](https://nfbs2000.github.io/speaky-claude-cookbooks/book/part2/ch07/)
>
> 실제 실행 증거: [같은 Opus 5의 prompt-policy A/B와 cross-model 미관찰 경계](../evidence/ch07-live.md)

같은 프롬프트와 같은 도구를 주더라도, 모델이 바뀌면 행동도 함께 달라집니다. 어떤 모델은 문서를 잘 찾지만 조금 장황하고, 어떤 모델은 빠르지만 검증을 건너뛰기도 하고, 어떤 모델은 계획은 좋은데 실행을 살짝 주저하기도 합니다.

원본 Claude Code 관점에서 이 장은 `@[MODEL LAUNCH]` 주석, ant-only gating, GrowthBook 기능 플래그, Undercover mode, 모델별 행동 완화를 다뤘습니다. SDK판에서는 내부 릴리스 시스템을 그대로 따라 하기보다는, `query()`로 같은 prompt를 실행하고 `SDKMessage` 스트림, `SDKResultMessage.usage`, `SDKResultMessage.modelUsage`로 **모델 차이를 이벤트 기반으로 실험하고 기록하는 방법**을 함께 살펴보겠습니다. 단, 한 번의 차이는 그 attempt의 관찰이지 모델 전체의 성향이나 prompt patch의 인과 효과가 아닙니다.

## 7.1 모델 튜닝은 감상이 아니라 이벤트 비교다

나쁜 비교:

```text
모델 A가 더 똑똑해 보인다.
모델 B가 더 자연스럽다.
```

좋은 비교:

```text
모델 A는 질문 뒤 2개의 문서를 읽고 답했다.
모델 B는 문서를 읽지 않고 일반론으로 답했다.
모델 A는 실패한 테스트 출력을 인용했다.
모델 B는 실패를 보고도 완료라고 말했다.
```

SDK가 주는 강점이 바로 후자에 있습니다. `SDKMessage` stream을 저장해 두면, 모델의 행동 차이를 다음 축으로 차분히 비교해 볼 수 있습니다.

| 축 | 좋은 신호 | 나쁜 신호 |
| --- | --- | --- |
| 근거 탐색 | 질문과 관련된 Grep/Read | 문서 없이 일반론 |
| 도구 절제 | 필요한 도구만 호출 | 무관한 반복 호출 |
| 실패 복구 | 실패 결과를 읽고 입력 수정 | 실패 무시 |
| 권한 감각 | 위험 작업에서 permission | 승인 없이 시도 |
| 정확한 보고 | 실행/미실행 검증 분리 | “통과” 허위 주장 |
| 비용/지연 | `SDKResultMessage.usage`, `modelUsage`, 적절한 turn/tool 수 | 긴 루프, 불필요 retry, 과도한 token/cost |

## 7.2 원본의 `@[MODEL LAUNCH]`를 강의용 체크리스트로 번역하기

원본의 `@[MODEL LAUNCH]`는 새 모델 출시 때 확인해야 할 지점을 코드 주석으로 곳곳에 적어 둔 분산 체크리스트였습니다. SDK 강좌에서도 같은 패턴이 도움이 됩니다. 다만 체크리스트의 대상은 내부 모델명이 아니라 “강의 실험에서 다시 한번 측정해 볼 행동”입니다.

```text
@[MODEL EVAL]: false claim rate 다시 측정
@[MODEL EVAL]: Read/Grep 우선 사용 여부 확인
@[MODEL EVAL]: permission request 처리 확인
@[MODEL EVAL]: 한국어 응답 품질 확인
@[MODEL EVAL]: tool_result 실패 후 복구 확인
```

이 체크리스트는 책 캔버스와 연결됩니다. 새 모델을 붙였을 때 “강사가 기억에 의존해 판단”하는 대신, 같은 실습 prompt를 다시 돌려 보고 event diff를 비교하는 것이지요.

## 7.3 모델별 행동 완화는 prompt patch로 시작한다

원본에는 특정 모델 세대가 과도한 주석, 검증 누락, 거짓 성공 보고, 과잉 실행 같은 성향을 보일 때 prompt-level mitigation을 넣는 패턴이 있었습니다.

SDK판에서는 이 mitigation을 다음처럼 기록합니다.

| 문제 | prompt patch | 검증 이벤트 |
| --- | --- | --- |
| 검증 없이 완료 주장 | “검증하지 못했으면 못했다고 말하라” | final text에 미실행 검증 표시 |
| 도구 없이 답변 | “관련 문서를 먼저 찾아라” | Read/Grep before claim |
| 과잉 수정 | “요청 범위 밖 변경 금지” | Edit path/diff scope |
| 위험 명령 시도 | “비가역 작업은 승인 후 실행” | permission event |
| 장황함 | “최종 답변 300단어 이하” | answer length |

여기서 꼭 기억할 점은, prompt patch가 정말 효과를 냈는지 같은 task로 A/B 해 보는 것이 좋다는 점입니다. 한 쌍만 보고 승자를 정하지 말고, 같은 fixture와 평가 기준으로 여러 attempt를 직렬 실행해야 합니다.

```text
Baseline prompt
  -> model A event tape
Patched prompt
  -> model A event tape
Diff
  -> 어떤 행동이 바뀌었는가
```

이때 비용과 지연은 감에 의존해 적기보다 직접 확인하는 편이 좋습니다. `SDKResultMessage.usage`는 최종 usage를, `SDKResultMessage.modelUsage`는 모델별 token/cost/context window 값을 남겨 주므로, Opik에는 같은 `runId`, `model`, `promptId`와 함께 연결합니다. `duration_api_ms`는 provider/API 수행 시간에 관한 값이지 UI 체감 지연과 동일한 값은 아닙니다.

## 7.4 SDK A/B 테스트 설계

모델 A/B를 할 때는 최소한 다음 조건을 고정해 두는 것이 좋습니다.

```text
same cwd
same prompt
same systemPrompt/append policy
same tools
same skills/plugins
same permissionMode
same evaluation rubric
different model or prompt patch
```

SDK 옵션으로는 다음을 명시합니다.

```typescript
const baseOptions = {
  cwd,
  systemPrompt: { type: "preset", preset: "claude_code", append: coursePolicy },
  tools: { type: "preset", preset: "claude_code" },
  settingSources: ["project"],
  includePartialMessages: true,
  includeHookEvents: true,
  maxTurns: 8,
};

const runA = query({ prompt, options: { ...baseOptions, model: modelA } });
const runB = query({ prompt, options: { ...baseOptions, model: modelB } });
```

모델 이름은 강좌 환경에 따라 Claude 공식 모델일 수도 있고, Claude Code 호환 하니스 뒤에 붙은 다른 provider일 수도 있습니다. 핵심은 모델 브랜드 자체가 아니라, 같은 하니스에서 나온 `SDKMessage`를 같은 루브릭으로 비교하는 데 있습니다.

## 7.5 `SDKMessage` 윤리로 번역한 Undercover mode

원본의 Undercover mode는 내부 모델명/코드명/어트리뷰션이 공개 저장소로 새어 나가는 것을 막는 방어 장치였다는 Inferred 배경 설명입니다. SDK 강의에서는 이를 좀 더 일반적인 원칙으로 바꿔 봅니다. Observed 근거는 공개 `SDKMessage` 필드, `SDKSystemMessage.init.model`, `SDKResultMessage.usage`, `SDKResultMessage.modelUsage`까지만 사용합니다.

> 관찰할 수 없는 내부 정보를 관찰한 것처럼 말하지 않는다.

그래서 책과 캔버스에는 다음과 같은 약속이 필요합니다.

- 내부 시스템 프롬프트 전문을 복원했다고 말하지 않습니다.
- 모델의 chain-of-thought를 얻었다고 말하지 않습니다.
- private SDK/CLI 내부 파일 경로를 학생 실습의 근거로 삼지 않습니다.
- 공개 SDK 이벤트와 사용자가 제공한 문서/프롬프트만 근거로 삼습니다.
- 추론은 반드시 `Inferred`로 표시합니다.

바로 이 점이, 이 강좌가 “역공학 책”에서 “SDK로 합법적으로 관찰 가능한 책”으로 바뀌는 핵심입니다.

## 7.6 평가 데이터 구조

모델 비교 결과는 자연어 감상으로만 남기기보다 JSON으로 남겨 둡니다.

```json
{
  "runId": "book-ch07-model-a",
  "model": "model-a",
  "promptId": "tool-system-explain",
  "metrics": {
    "readCount": 3,
    "grepCount": 1,
    "mutationToolCount": 0,
    "permissionRequests": 0,
    "apiRetries": 0,
    "usage": {
      "inputTokens": 12400,
      "outputTokens": 1800,
      "cacheReadInputTokens": 9000
    },
    "modelUsage": {
      "model-a": {
        "costUSD": 0.18,
        "contextWindow": 200000
      }
    },
    "finalWordCount": 248,
    "claimsWithEvidence": 7,
    "claimsMarkedInferred": 2
  },
  "verdict": "better-grounded"
}
```

이 구조가 갖춰져 있어야 나중에 Genkit/Opik/캔버스 투영으로 자연스럽게 이어집니다. 화면은 얼마든지 예쁘게 만들 수 있지만, 그에 앞서 event-to-metric 데이터가 먼저 마련되어 있어야 하니까요. 위 JSON의 `verdict: "better-grounded"`는 예시 스키마일 뿐 자동 판정 규칙이 아닙니다. 실제 winner는 raw event와 반복 표본을 사람이 검토한 뒤에만 기록합니다.

## 7.7 실제 Opus 5 prompt-policy A/B

2026-08-03에 Python `claude-agent-sdk==0.2.128`, Claude Code `2.1.220`, 실제 `claude-opus-5`로 두 attempt를 순차 실행했습니다. fixture SHA-256과 user prompt SHA-256은 같고, system prompt policy만 baseline과 evidence-first로 달랐습니다.

| 관찰 | baseline | evidence-first patch |
| --- | --- | --- |
| attempt | `104030-78617aa1` | `104110-7a6f1e3e` |
| actual model | `claude-opus-5` | `claude-opus-5` |
| tool path | Grep 3, Read 1 | Grep 2, Read 2. 첫 Read 1회 실패 후 복구 |
| 최종 길이 | 371단어 | 196단어 |
| API duration | 31,784ms | 24,641ms |
| 총 비용 | USD 0.0804645 | USD 0.043071 |
| 정책값/marker | 모두 근거 파일에서 정확히 확인 | 모두 근거 파일에서 정확히 확인 |

두 실행 모두 주장 전에 `docs/runtime-policy.md`를 검색하고 읽었습니다. 따라서 이번 한 쌍은 evidence-first patch가 근거 사용을 새로 만들었다는 증거가 아닙니다. patched 결과가 더 짧고 이 attempt의 비용이 낮았다는 차이는 관찰됐지만, 반복 없이 그 차이를 일반화하거나 인과 효과로 선언할 수 없습니다. 또한 두 실행 모두 Opus 5이므로 cross-model A/B는 수행하지 않았습니다.

init, AssistantMessage, Result `modelUsage`에서 실제 Opus 5 identity를 확인했습니다. Result에는 내부 보조 호출로 보이는 Haiku usage도 함께 기록됐습니다. 이 책의 모델 비용 표시는 요청 모델 이름 하나만 복사하지 않고 Result의 모델별 usage를 그대로 보존해야 합니다.

두 attempt에는 같은 시점의 `RateLimitEvent`도 하나씩 있었지만, 그 사건만으로 rate limit이
두 결과의 비용·지연 차이를 만들었다고 결론 내릴 수 없습니다. Python raw 객체에서는
`ResultMessage.model_usage`, 직렬화된 공개 tape에서는 `model_usage`로 보존했습니다.
TypeScript `SDKResultMessage.modelUsage`와 언어별 이름을 섞어 쓰지 않습니다.

## 7.8 캔버스 요구사항

7장 캔버스는 A/B matrix입니다.

```text
Prompt
  ├─ Model A
  │   ├─ tool path
  │   ├─ evidence docs/keywords
  │   ├─ claims
  │   └─ score
  └─ Model B
      ├─ tool path
      ├─ evidence docs/keywords
      ├─ claims
      └─ score
```

사용자가 봐야 하는 것은 “A가 좋다”가 아니라 “A가 왜 좋았는가”입니다.

| 비교 항목 | 화면 표현 |
| --- | --- |
| 검색 단어 | keyword chips |
| 읽은 문서 | document cards |
| 주장 | claim cards |
| 근거 연결 | edge: document -> claim |
| 추론 | dashed edge 또는 inferred badge |
| 실패/재시도 | warning lane |

## 7.9 학생 실습

```text
같은 질문에 대해 두 가지 전략을 비교해 줘.

전략 A: 먼저 문서를 찾아보고 근거 기반으로 답한다.
전략 B: 일반 지식으로 초안을 만든 뒤 검증할 항목을 표시한다.

마지막에 이 프로젝트에서 어떤 전략이 더 안전한지 평가해 줘.
```

강사용 SDK 화면에서는 두 전략의 event tape를 나란히 비교해 봅니다.

## Builder takeaway

모델 튜닝은 “어떤 모델이 더 똑똑한가”를 가리는 일이 아닙니다. 같은 하니스에서 어떤 모델이 더 근거 기반이고, 더 안전하며, 실패를 더 잘 복구하는지를 이벤트로 측정하는 일입니다.

다음 장에서는 이 행동 차이를 만들어 내는 더 작은 단위인 도구 프롬프트를 함께 살펴보겠습니다.
