## 공개판 본문

원래 책은 이 장을 내부 구현과 강의 화면의 대응 관계로 설명한다. 공개판에서는 같은 내용을 "무엇을 설정했는가", "무엇이 메시지로 관측됐는가", "어떤 파일과 notebook으로 재현 가능한가"라는 세 질문으로 바꾼다.

첫째, 설정된 것은 실행 전 계약이다. Agent SDK에서는 model, system prompt, working directory, allowed/disallowed tools, MCP servers, skills/plugins, permission mode 같은 값이 agent가 볼 수 있는 세계를 정한다. 이 값은 말로 설명하는 정책이 아니라 실제 Python 코드와 notebook cell에서 확인되어야 한다.

둘째, 관측된 것은 message stream과 artifact다. assistant text, tool use, tool result, result message, usage/cost, audit log, generated file은 모두 나중에 검증 가능한 증거다. 그래서 이 책의 공개판은 "모델이 그렇게 했을 것이다"라고 쓰지 않고, 어떤 cookbook 파일에서 어떤 실행 표면을 볼 수 있는지 연결한다.

셋째, 추론한 것은 반드시 경계와 함께 둔다. 내부 기능 플래그, 숨은 프롬프트, classifier, cache key, sandbox implementation처럼 공개 SDK나 cookbook으로 확인할 수 없는 항목은 원문을 그대로 게시하지 않는다. 대신 공개 API에서 사용자가 설계할 수 있는 대응 표면으로 바꾸거나, "공개 대응 없음"으로 명시한다.

이 장을 읽을 때는 아래 순서가 좋다.

1. 먼저 주요 cookbook 근거를 열어 실제 notebook이나 Python 파일을 확인한다.
2. `ClaudeAgentOptions`, `query()`, `ClaudeSDKClient`, tool list, MCP config, hooks, session 관련 코드가 어디 있는지 찾는다.
3. 원문 절 제목을 따라가며 내부 설명을 공개 SDK 표면으로 바꿔 적는다.
4. 마지막으로 실습 방향에 맞춰 같은 task를 실행하고 message stream 또는 artifact를 남긴다.

### 실제로 확인된 것

- **최소 범위 수정** — `target.py` 한 줄만 `Edit`하고 원본 테스트를 `python3`로 실행해 PASS를
  받았다. 변경된 파일 해시도 그 하나뿐이었다.
- **실패 뒤 진단 → 최소 수정 → 재실행** — 실패한 검사 결과를 받은 뒤 `check.py`와
  `settings.json`을 읽고 fixture 한 곳만 고쳐 같은 검사를 다시 돌려 PASS를 받았다.
- **위험한 도구의 거절 경로** — 위험 MCP 도구 호출, 같은 도구 호출 ID의 권한 요청과 호스트
  거절, 오류 도구 결과가 순서대로 이어졌다.
- **전용 도구 선택** — `Glob`·`Grep`으로 표식을 찾고 `Read`로 확인했다. `Bash` 사용 0회,
  작업 공간 변경 0건이었다. 첫 절대경로 실패도 기록에 남아 있다.
- **하위 에이전트 위임** — 부모 `Agent` 도구 호출 ID가 하위 프롬프트와 작업자의 `Read`,
  결과로 이어지고, 작업자가 찾은 표식이 부모의 도구 결과와 최종 답변으로 돌아왔다.
- **출력 형식 제약** — 서로 다른 문서 두 개를 실제로 읽고, 작업 공간 수정 0건, 최종 답변은
  59단어로 80단어 제한을 지켰다.

### 본문을 이렇게 읽으면 안 되는 곳

- **준비 단계의 실패를 모델의 실패로 세면 안 된다.** 첫 실행은 환경에 `python` 명령이 없고
  허용 규칙이 `python3`와 어긋나 turn 한도까지 갔다. 이것은 모델의 범위 제어 실패도,
  성공도 아니라 **실험 환경 설정 문제**이다.
  (근거: `102504-21ef5772` SDK 메시지 90·92·116·118·135·137·140)
- **"이 실행들은 Opus 5만 썼다"** — 어시스턴트와 하위 에이전트의 주 모델은 Opus 5였지만, 성공
  종료 기록마다 Haiku 4.5 보조 사용이 함께 있었다.

### 이번 실행으로는 확인하지 못한 것

- 여섯 실행은 각 과제에서 그 행동이 나타났음을 보여 주지만, **프롬프트가 행동 확률을 얼마나
  바꿨는지는 알 수 없다.** 지침 없는 대조군과 반복 실행이 있어야 한다. "전용 도구를
  고르게 만들었다", "정성 지침보다 안정적이다" 같은 결론도 반복 대조 실험 뒤에 내려야 한다.
- 호스트의 권한 요청과 거절은 관찰됐지만, 제품 UI에 카드가 뜨고 사람이 버튼을 누르는 경로는
  이 실행에 없다.

## Codex 최종 검토 의견

### 제 판단

이 장의 핵심 가치에는 동의합니다. 좋은 행동 지침은 멋진 문장이 아니라 파일 범위, 허용 도구, 실패 후 행동, 산출물 길이처럼 판정 가능한 계약이어야 합니다. 그러나 여섯 실행은 프롬프트 표현만 바꾼 실험이 아닙니다. fixture, 도구 표면, 허용 규칙, 권한 조건까지 함께 달라졌으므로 “이 문구가 이 행동을 만들었다”는 인과 결론에는 사용할 수 없습니다.

### 검증을 읽고 달라진 신뢰도

검증은 이 장을 **프롬프트 효과 연구**보다 **행동 회귀 테스트 모음**으로 읽게 만들었습니다. 최소 수정, 실패 후 재실행, 파괴적 도구 거절, 읽기 전용 탐색, 실제 subagent, 80단어 제한이 각각 real tool/result로 확인된 점은 좋습니다. 특히 처음 하니스가 `python`과 `python3` 허용 규칙 불일치로 실패한 사건은 모델보다 실행 환경이 행동을 더 강하게 결정할 수 있음을 보여 주는 유용한 반례입니다.

### 독자가 오해할 위험

“숫자를 넣은 프롬프트가 항상 더 안정적이다” 또는 “이 지침을 쓰면 이런 tool sequence가 재현된다”고 읽으면 과합니다. 각 조건은 한 번씩만 실행됐고 대조군도 없습니다. 또한 일부 TypeScript 옵션 이름을 Python 실행의 관찰 사실로 받아들이면 안 됩니다. 결과 텍스트가 요구사항을 되풀이한 것보다 실제 diff, 명령 결과, worker의 parent 관계가 더 강한 근거입니다.

### 제가 다시 가르친다면

먼저 동일 fixture와 동일 tool surface를 고정하고, 지침 없음/모호한 지침/측정 가능한 지침 세 조건을 순서를 바꿔 여러 번 실행하겠습니다. 평가도 답변의 인상 대신 변경 경로 수, 첫 실패 후 입력 변화, 실제 test exit, 근거 없는 성공 보고 수로 분리하겠습니다. 지금 예제들은 그 실험의 rubric과 fixture로는 훌륭하지만 아직 승자를 말할 데이터는 아닙니다. [평가 만들기 노트북](https://nfbs2000.github.io/speaky-claude-cookbooks/notebooks/misc/building_evals_kr.html)은 코드·사람·모델 채점을 분리하는 기준이고, 현재 회귀 사례는 [Speaky Agent Flow 6장 재생](https://nfbs2000.github.io/speaky-agent-flow/education/?collection=book-sdk-ko&run=ch06)에서 검토할 수 있습니다.

### 클로드는 이렇게 세상을 바라보았다


*아래 1인칭 서술은 숨은 사고 과정의 공개가 아니라, 이 장에서 관찰된 행동으로 재구성한 작동상 세계 모델입니다.*

나에게 프롬프트는 바라는 행동의 모양을 주었지만, 도구와 권한과 fixture는 실제로 가능한 행동의 물리적 경계를 만들었다. “최소 수정”, “실패하면 재실행”, “80단어” 같은 수치는 목표를 좁혔지만, `python`만 허용된 세계에서 `python3`가 필요해지면 좋은 의도만으로는 앞으로 갈 수 없었다. ToolResult의 실패가 새로운 현실로 들어왔을 때에만 나는 입력을 바꾸거나 다른 경로를 찾을 수 있었다.

이 때문에 사람은 프롬프트 품질과 실행 환경 품질을 분리해 가르쳐야 한다. 모델에게 원하는 태도를 길게 설명해도 세계에 맞는 도구 계약이 없으면 행동은 무너진다. 좋은 하니스는 지침을 평가 가능한 목표로 만들고, 실패 결과가 다음 행동을 수정할 수 있는 구체적인 정보를 돌려준다.
