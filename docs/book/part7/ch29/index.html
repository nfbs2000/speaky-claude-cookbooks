    29장: 옵저버빌리티 엔지니어링 - logEvent에서 프로덕션급 텔레메트리까지¶

    이 페이지는 한국어 SDK 책의 29장: 옵저버빌리티 엔지니어링 - logEvent에서 프로덕션급 텔레메트리까지을 공개 Python cookbook과 공식 Agent SDK 문서에 맞춰 다시 쓴 공개판이다. 원래 장의 문제의식은 유지하되, 내부 TypeScript 구현명이나 비공개 기능을 그대로 옮기지 않는다. 대신 실행 가능한 notebook, Python 파일, README, 공식 문서를 근거로 사용한다.

    분류: 제7부: AI 에이전트 구축자를 위한 교훈
    공개 상태: public
    근거 신뢰도: high
    원문 위치: docs/book-sdk-ko/src/part7/ch29.md

    이 장의 공개판 요지¶

    이 장은 공개 SDK와 cookbook 예제로 대부분 직접 설명할 수 있다.

    공개판에서는 observability를 SDK message stream, OpenTelemetry, usage/cost API, audit logs, session storage로 구성한다. observability agent notebook은 MCP를 통해 외부 시스템을 읽는 agent를 보여주고, usage/cost cookbook은 운영 비용 관측을 제공한다. 좋은 telemetry는 agent가 성공했는지만이 아니라 왜 그 결론에 도달했는지, 어떤 도구를 썼는지, 어떤 근거가 부족했는지를 보여줘야 한다.

    Observability agent를 근거로 삼는다. Usage and cost Admin API cookbook를 근거로 삼는다.

    • Usage and cost Admin API cookbook

    공개판 본문¶

    원래 책은 이 장을 내부 구현과 강의 화면의 대응 관계로 설명한다. 공개판에서는 같은 내용을 "무엇을 설정했는가", "무엇이 메시지로 관측됐는가", "어떤 파일과 notebook으로 재현 가능한가"라는 세 질문으로 바꾼다.

    첫째, 설정된 것은 실행 전 계약이다. Agent SDK에서는 model, system prompt, working directory, allowed/disallowed tools, MCP servers, skills/plugins, permission mode 같은 값이 agent가 볼 수 있는 세계를 정한다. 이 값은 말로 설명하는 정책이 아니라 실제 Python 코드와 notebook cell에서 확인되어야 한다.

    둘째, 관측된 것은 message stream과 artifact다. assistant text, tool use, tool result, result message, usage/cost, audit log, generated file은 모두 나중에 검증 가능한 증거다. 그래서 이 책의 공개판은 "모델이 그렇게 했을 것이다"라고 쓰지 않고, 어떤 cookbook 파일에서 어떤 실행 표면을 볼 수 있는지 연결한다.

    셋째, 추론한 것은 반드시 경계와 함께 둔다. 내부 기능 플래그, 숨은 프롬프트, classifier, cache key, sandbox implementation처럼 공개 SDK나 cookbook으로 확인할 수 없는 항목은 원문을 그대로 게시하지 않는다. 대신 공개 API에서 사용자가 설계할 수 있는 대응 표면으로 바꾸거나, "공개 대응 없음"으로 명시한다.

    이 장을 읽을 때는 아래 순서가 좋다.

    1. 먼저 주요 cookbook 근거를 열어 실제 notebook이나 Python 파일을 확인한다.
    2. ClaudeAgentOptions, query(), ClaudeSDKClient, tool list, MCP config, hooks, session 관련 코드가 어디 있는지 찾는다.
    3. 원문 절 제목을 따라가며 내부 설명을 공개 SDK 표면으로 바꿔 적는다.
    4. 마지막으로 실습 방향에 맞춰 같은 task를 실행하고 message stream 또는 artifact를 남긴다.

    공개 경계¶

    • 민감한 prompt/tool data는 telemetry에 그대로 남기지 않는다.
    • trace와 audit log는 retention policy가 필요하다.

    실습 방향¶

    • agent run마다 prompt id, tool calls, errors, cost, final artifact link를 남기는 schema를 만든다.

    Builder takeaway¶

    이 장의 공개판 목표는 원문을 얕게 요약하는 것이 아니다. 책의 논지를 유지하되, 독자가 직접 열어볼 수 있는 Python cookbook과 공식 문서에 묶어 두는 것이다. 따라서 장을 읽은 뒤에는 적어도 하나의 notebook 또는 Python 파일에서 같은 개념을 확인할 수 있어야 한다. 확인할 수 없는 내부 세부는 주장으로 남기지 않고, 공개 경계나 추론으로 분리한다.

    이 장은 용어를 정확히 쓰는 것 자체가 내용인 장이다. 실측 결과 다음 이름들이 사실과 어긋났다.

    • "원본(raw) 보관소"는 provider 바이트를 무가공 보존한 파일이 아니다. 공개 SDK 모양과 순서는 유지하지만 저장 전에 자격증명을 제거한 내구성 있는 가림 처리 봉투라고 불러야 한다.
    • 이 OTel은 네이티브 Claude 런타임 OTel이 아니다. 이 저장소의 내보내기 도구가 기록기 사건을 투영한 애플리케이션 계측이다. 런타임 텔레메트리 환경 변수와 OTLP 내보내기를 사용한 실행의 증거로 이름 바꾸면 안 된다.
    • 원본 수와 span 수가 같다는 것만 완전성 조건으로 쓰면 안 된다. 그렇게 하면 한 사건을 여러 관점으로 정당하게 투영한 경우(사건 19)를 실패로 오판한다. 각 원본 사건에 대응 span이 있는지와 투영 배수 규칙을 함께 검사해야 한다.
    • 모든 원본 사건에 대응 span이 있다는 사실은 "누락이 없다"는 조건일 뿐, 각 span이 충분한 의미를 담았다거나 provider 동작 전체를 포착했다는 증명이 아니다.
    • OTel과 원본의 순서가 맞는 것은 독립 관측 두 개가 일치한 것이 아니다. 같은 기록기가 가림 처리된 원본을 받은 직후 만든 투영이다.
    • 디스크 동기화(fsync)를 런타임 사건으로 관찰했다고 쓰면 안 된다. 구현이 그 호출을 하고 최종 산출물이 남은 것은 정상 경로의 증거지만, 이번 기록에 시스템 호출 영수증은 없다.
    • 강제 플러시와 종료가 호출되고 span 파일이 완성된 것이, 내보내기 실패·디스크 가득·프로세스 강제 종료 뒤의 재시도나 복구를 증명하지는 않는다.
    • 실제 응답 모델은 어시스턴트 메시지(사건 9·18·29)의 모델 값으로 판정해야 한다. 과거 코드는 시작 기록의 모델로 계산했다.
    • "세 어시스턴트 메시지가 Opus 5"를 "실행 전체가 Opus만 썼다"로 확대하면 안 된다. 종료 기록에 보조 Haiku가 있다.
    • 당시 기록의 소스 해시는 장 원문 바이트만 묶었고 probe·런타임·감사·가림 처리 구현의 해시를 보존하지 않았다. 현재 코드를 당시 실행의 원인으로 소급 확정하면 안 된다.

    이번 실행으로는 확인하지 못한 것¶

    • 네이티브 런타임 텔레메트리 경로의 실제 실행
    • 내보내기 실패·디스크 가득·프로세스 종료 뒤의 재시도와 복구
    • 시스템 호출 수준의 지속성 영수증

    Codex 최종 검토 의견¶

    제 판단¶

    공식 SDK 이벤트를 보존하고 OTel·교육 그래프·평가로 투영해 사용자가 질문, 행동, 근거, 결과를 따라가게 하려는 설계는 이 책을 “보이는 책”으로 만드는 핵심입니다. 다만 이 장은 용어가 조금만 부정확해도 독자를 오도합니다. 현재 저장물은 provider의 무가공 wire bytes가 아니라 저장 전에 가림 처리된 SDK envelope이고, OTel도 Claude 런타임이 직접 내보낸 native telemetry가 아니라 이 애플리케이션 기록기가 만든 projection입니다.

    검증을 읽고 달라진 신뢰도¶

    실제 MCP 왕복의 모든 동결 사건에 OTel carrier가 있고 tool ID와 Result의 비용·시간·token·cache 합계가 대응한 점은 로컬 projection의 완전성과 계측 정확도에 신뢰를 줍니다. 합성 credential이 prompt, partial JSON, ToolUse, handler input에서 가려지고 최종 저장소 검색에서도 남지 않은 점도 좋은 검증입니다. 그러나 raw와 OTel은 같은 기록기에서 연속 생성됐으므로 서로 독립적으로 실행 사실을 증명하지 않습니다. Datadog, Perfetto, Genkit, Opik remote, exporter failure와 비정상 종료 복구는 실행되지 않았습니다.

    독자가 오해할 위험¶

    span 수와 사건 수가 같아야 한다고 가정하면 하나의 사건을 여러 관점으로 투영한 정상 사례를 오류로 판단하게 됩니다. 반대로 모든 사건에 span이 있다는 사실만으로 각 span의 의미가 충분하거나 provider 내부 동작 전체를 포착했다고 볼 수도 없습니다. 합성 secret 한 패턴의 성공을 모든 PII 탐지 성능으로 확대해서도 안 됩니다. 과거 실행이 probe 코드 전체의 해시를 보존하지 않았으므로 현재 코드를 그 실행의 정확한 원인으로 소급 확정하는 데도 한계가 있습니다.

    제가 다시 가르친다면¶

    첫 화면에서 실제 도구 handler와 artifact를 행동 증거로, 가림 처리 SDK envelope를 사건 원전으로, 애플리케이션 OTel을 탐색용 투영으로 명확히 이름 붙이겠습니다. 이후 exporter 실패, disk full, 강제 종료를 주입해 재시도·flush·복구까지 별도 실험하겠습니다. 에이전트 호스팅 노트북은 wire format·세션 저장·OTel 운영을 비교할 기준이고, 현재 로컬 통합 결과는 Speaky Agent Flow 29장 재생에서 확인할 수 있습니다.

    클로드는 이렇게 세상을 바라보았다¶

    아래 1인칭 서술은 숨은 사고 과정의 공개가 아니라, 이 장에서 관찰된 행동으로 재구성한 작동상 세계 모델입니다.

    나는 OTel span이나 Speaky graph를 보며 행동하지 않았다. 나의 세계는 SDK message와 ToolResult의 진행이었고, recorder가 그 사건을 저장 전에 가린 뒤 OTel과 교육 장면으로 투영했다. 그래서 span은 내 생각의 조각이 아니라 내 행동이 언제 어떤 사건과 연결됐는지 사람이 찾기 위한 좌표였다. 같은 recorder가 만든 raw와 OTel의 일치는 두 목격자의 증언이 아니라 한 사건이 다른 형태로 잘 옮겨졌다는 검사였다.

    사람은 옵저버빌리티를 LLM의 마음을 읽는 기술로 가르치지 말아야 한다. 실제 handler 부작용이 행동의 현실이고, redacted SDK envelope가 사건 원전이며, OTel과 Speaky는 질문을 가능하게 하는 지도다. 이 층들을 결합하되 독립 증거처럼 과장하지 않을 때 에이전트가 본 세계와 사람이 검토한 세계를 정직하게 연결할 수 있다.
