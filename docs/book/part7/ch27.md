## 공개판 본문

원래 책은 이 장을 내부 구현과 강의 화면의 대응 관계로 설명한다. 공개판에서는 같은 내용을 "무엇을 설정했는가", "무엇이 메시지로 관측됐는가", "어떤 파일과 notebook으로 재현 가능한가"라는 세 질문으로 바꾼다.

첫째, 설정된 것은 실행 전 계약이다. Agent SDK에서는 model, system prompt, working directory, allowed/disallowed tools, MCP servers, skills/plugins, permission mode 같은 값이 agent가 볼 수 있는 세계를 정한다. 이 값은 말로 설명하는 정책이 아니라 실제 Python 코드와 notebook cell에서 확인되어야 한다.

둘째, 관측된 것은 message stream과 artifact다. assistant text, tool use, tool result, result message, usage/cost, audit log, generated file은 모두 나중에 검증 가능한 증거다. 그래서 이 책의 공개판은 "모델이 그렇게 했을 것이다"라고 쓰지 않고, 어떤 cookbook 파일에서 어떤 실행 표면을 볼 수 있는지 연결한다.

셋째, 추론한 것은 반드시 경계와 함께 둔다. 내부 기능 플래그, 숨은 프롬프트, classifier, cache key, sandbox implementation처럼 공개 SDK나 cookbook으로 확인할 수 없는 항목은 원문을 그대로 게시하지 않는다. 대신 공개 API에서 사용자가 설계할 수 있는 대응 표면으로 바꾸거나, "공개 대응 없음"으로 명시한다.

이 장을 읽을 때는 아래 순서가 좋다.

1. 먼저 주요 cookbook 근거를 열어 실제 notebook이나 Python 파일을 확인한다.
2. `ClaudeAgentOptions`, `query()`, `ClaudeSDKClient`, tool list, MCP config, hooks, session 관련 코드가 어디 있는지 찾는다.
3. 원문 절 제목을 따라가며 내부 설명을 공개 SDK 표면으로 바꿔 적는다.
4. 마지막으로 실습 방향에 맞춰 같은 task를 실행하고 message stream 또는 artifact를 남긴다.

## Codex 최종 검토 의견

### 제 판단

읽기, 공개 계획, 좁은 수정, 실제 검증, 실패 복구, 위험 명령 차단, 안전한 대안, 최종 보고를 하나의 코딩 턴으로 묶은 예제는 이 책에서 가장 완성도가 높은 실무 사례 중 하나입니다. 모델 종료 뒤 호스트가 같은 결과를 독립 검산한 점도 “모델이 PASS라고 말했다”와 “코드가 실제로 통과했다”를 분리합니다. 다만 프롬프트가 행동 순서와 명령을 매우 구체적으로 지정했으므로, 이 실행은 모델이 자발적으로 좋은 관행을 선택했다기보다 **하니스가 좋은 관행을 강제하고 확인할 수 있음**을 증명합니다.

### 검증을 읽고 달라진 신뢰도

두 번의 `Read`가 `Edit`보다 앞섰고, 공개 `PLAN` 뒤 한 파일만 수정됐으며, 첫 검증의 실제 exit 2를 읽고 수정된 명령으로 PASS한 사슬은 강합니다. 위험한 `git reset --hard`는 handler 실행 전에 거부됐고 HEAD도 유지됐습니다. 첫 실패 실험에서 재시도 인터페이스가 불명확해 13턴을 낭비한 뒤 하니스를 개선한 기록은 특히 가치가 있습니다. 실패 원인이 모델뿐 아니라 도구 계약일 수 있다는 점을 실제로 보여 주기 때문입니다.

### 독자가 오해할 위험

이 한 과제의 성공을 모든 저장소에서 통하는 “프로덕션급 성능”으로 확대하면 안 됩니다. 구현 대상은 작은 함수 하나였고 검증 명령도 fixture가 정답을 명확히 알고 있었습니다. 공개 PLAN은 숨은 chain-of-thought가 아니며, 동적 helper sizing과 원격 평가도 실행되지 않았습니다. 또한 실패 결과에 정답에 가까운 exact retry command를 제공했으므로 복구 능력 자체의 난이도는 제한적입니다.

### 제가 다시 가르친다면

현재 사례를 하니스 계약의 기준으로 유지하고, 두 번째 사례에서는 재시도 명령을 직접 주지 않은 채 오류 메시지만으로 복구하게 하겠습니다. 세 번째로 실제 중형 저장소에서 범위 이탈과 회귀 테스트를 평가하면 패턴의 일반성을 판단할 수 있습니다. ### 클로드는 이렇게 세상을 바라보았다


*아래 1인칭 서술은 숨은 사고 과정의 공개가 아니라, 이 장에서 관찰된 행동으로 재구성한 작동상 세계 모델입니다.*

이 과제에서 나의 세계는 자유로운 코딩 공간이 아니라 `읽기 → 공개 계획 → 좁은 수정 → 검증 → 복구`라는 레일이 놓인 작업장이었다. 첫 검증의 exit 2는 실패라는 추상 평가가 아니라 다음 행동을 바꾸는 구체적 현실이었고, 수정된 명령이 주어지자 다시 실행해 PASS를 얻었다. 위험한 reset은 handler 앞에서 막혀 repository 세계를 바꾸지 못했다. 좋은 행동은 내 성격에서 자발적으로 나온 것이라기보다 하니스가 가능한 경로와 확인 기준을 잘 만들었기 때문에 지속됐다.

사람은 유능한 에이전트를 좋은 프롬프트 한 줄로 만들 수 있다고 생각하지 말아야 한다. 오류가 수정 가능한 정보로 돌아오고, 위험 경로는 실제 실행 전에 닫히며, host가 결과를 독립 검산해야 한다. 에이전트의 사고 품질은 세계가 피드백을 얼마나 정확히 돌려주는지와 함께 설계된다.
