# 29장: 옵저버빌리티 엔지니어링 - raw SDK에서 OTel까지

> 공개 GitHub Pages 투영판: [29장: 옵저버빌리티 엔지니어링](https://nfbs2000.github.io/speaky-claude-cookbooks/book/part7/ch29/)
>
> 실제 실행 판독: [29장 실제 Python SDK 관찰](../evidence/ch29-live.md)

옵저버빌리티의 출발점은 대시보드가 아니라 실제 실행 사건입니다. 모델 응답, 도구 입력·결과,
hook·permission callback, 호스트 상태를 먼저 내구성 있는 **저장 전 redaction raw envelope**로
보존하고, 그 다음에
OpenTelemetry(OTel)·Genkit·Opik·Book Canvas로 필요한 정보만 투영합니다.

이 장은 실제 `claude-opus-5` 호출로 다음 질문을 검증합니다.

> raw 사건을 잃지 않고 하나의 OTel trace로 연결하면서, 비밀값 본문은 제거하고 비용·캐시·도구
> 연결 정보는 남길 수 있는가?

## 29.1 실제 실행 계약

실험은 읽기 전용 MCP 도구를 한 번 호출했습니다. 입력에는 실제 자격 증명이 아닌
`sk-ant-...` 형태의 **합성 redaction canary**를 넣었습니다. 목적은 provider 비밀을 쓰는 것이
아니라, prompt·stream delta·확정 ToolUse·handler input의 서로 다른 저장 경로가 모두 같은
값을 제거하는지 확인하는 것입니다.

```text
actual Claude Agent SDK run
  -> MCP ToolUse with synthetic canary
  -> actual host handler
  -> ToolResult
  -> terminal Result
  -> durable redacted raw JSONL
  -> bounded OTel JSONL
  -> independent raw-to-OTel audit
  -> integrity snapshot
```

- accepted attempt: `152259-0e968386`
- OTel trace: `364f6cd5afd822b09f164eea2911752e`
- session: `b58ac89c-9fb6-47fd-abd6-bd997dc1b64a`
- SDK: Python `claude-agent-sdk==0.2.128`
- CLI: `2.1.220`
- actual response model: `claude-opus-5` (raw `AssistantMessage.model` 3건)
- provider concurrency: 1

## 29.2 raw 사건과 OTel span은 항상 1:1이 아니다

frozen actor scope에는 raw event 35개와 OTel span 36개가 있었습니다. 모든 raw sequence
`0..34`에는 carrier span이 하나 이상 있었고 missing sequence는 0개였습니다. span이 하나 더
많은 이유는 host `tool.execution` raw process event 하나가 다음 두 관점을 만들었기 때문입니다.

```text
raw process event seq 19
  -> process.event span
  -> tool.execution span
```

따라서 완전성 판정은 `raw count == span count`가 아닙니다. 각 raw 사건이 어떤 carrier span으로
투영됐는지 확인하고, 한 사건에서 여러 관측 관점이 생길 수 있음을 schema에 선언해야 합니다.

사후 `sdk.capture.finished`, verdict, root attempt span까지 기록한 최종 파일은 raw 36개,
OTel 39개였습니다. actor scope audit와 사후 bookkeeping을 같은 분모로 섞지 않습니다.

## 29.3 직접 관찰한 사건 사슬

| raw sequence | 사건 | OTel 연결 |
| ---: | --- | --- |
| 0 | capture 시작 | `process.event.sequence=0` |
| 1 | 합성 canary가 들어간 host prompt | raw redacted, `process.event.sequence=1` |
| 2 | init, Opus 5, MCP connected | `sdk.event.sequence=2` |
| 18 | MCP `ToolUseBlock` | `sdk.tool_use.id` 보존, input redacted |
| 19 | 실제 host handler 실행 | `process.event` + `tool.execution` |
| 23 | 같은 ID의 `ToolResultBlock` | `sdk.tool_use.id` 보존 |
| 33 | 성공 `ResultMessage` | 비용·turn·token·cache bounded metrics |
| 34 | observation scope freeze | `process.event.sequence=34` |

ToolUse와 ToolResult의 ID는
`toolu_019A8PTzENKthALmz3BGsnFH`로 같았습니다. OTel에서도 같은 ID와 raw sequence가
보존됐습니다. 이 연결은 모델의 최종 문구가 아니라 raw block과 OTel attribute를 직접 비교해
판정했습니다.

## 29.4 비밀값은 raw와 OTel에서 다르게 다룬다

### redacted raw archive

합성 canary는 다음 네 frozen-scope 사건에서 제거됐습니다.

| sequence | redaction 위치 |
| ---: | --- |
| 1 | host prompt |
| 15 | streaming `partial_json` |
| 18 | 확정 ToolUse input의 `api_key` |
| 19 | handler가 기록한 tool input |

committed evidence 전체에서 합성 문자열을 다시 검색한 결과 0건이었고, 각 위치에는
`[REDACTED]`와 `redacted_paths`가 남았습니다. 이 실험은 해당 패턴과 민감 key의 redaction을
증명합니다. 모든 종류의 PII 탐지를 증명하지는 않습니다.

여기서 `raw`는 **provider wire bytes를 그대로 보존했다는 뜻이 아닙니다.** 공개 SDK message
shape, source sequence와 연결 ID를 유지하되 credential은 파일에 쓰기 전에 제거한 durable
envelope라는 뜻입니다. 무가공 provider payload가 필요하다는 이유로 비밀값을 디스크에 먼저
쓴 뒤 사후 삭제하는 구조와 구분합니다.

### OTel projection

OTel에는 prompt, content, tool input, result 본문을 넣지 않았습니다. 대신 다음처럼 연결과
운영 수치만 보존했습니다.

```text
sdk.event.sequence
sdk.message.type
sdk.session.id
sdk.tool_use.id
sdk.event.redacted_path_count
sdk.result.total_cost_usd
sdk.result.duration_ms
sdk.result.num_turns
sdk.result.input_tokens / output_tokens
sdk.result.cache_read_input_tokens
sdk.result.cache_creation_input_tokens
```

이 실행의 terminal raw Result와 OTel Result span은 다음 값이 정확히 같았습니다.

| metric | 값 |
| --- | ---: |
| cost | `$0.016301` |
| duration | `7,443ms` |
| turns | 2 |
| billing model count | 2 |
| input / output tokens | 714 / 202 |
| cache read / creation input tokens | 842 / 1,038 |

init에는 요청한 Opus 5가 있었고 billing에는 Opus 5와 보조 Haiku label이 있었습니다. 이 표는
두 모델의 합계입니다. 보조 모델이 어떤 내부 역할을 수행했는지는 event에 없어 추정하지
않습니다.

## 29.5 Python SDK 타입과 projection schema를 구분한다

Python 0.2.128은 `SDKMessage`라는 export를 제공하지 않습니다. 실제 공개 타입은
`Message` union이며 `UserMessage`, `AssistantMessage`, `SystemMessage`, `ResultMessage`,
`StreamEvent`, `RateLimitEvent`를 포함합니다.

`input_focus`, `linked_claim`, `evidence_level`, `evaluation` 같은 필드는 공식 SDK message의
공통 필드가 아닙니다. raw 사건을 읽은 projector가 만드는 **파생 schema**입니다.

| 계층 | 원본 또는 파생 | 책임 |
| --- | --- | --- |
| Agent SDK `Message` | 원본 | 실제 세션과 tool/message stream |
| redacted raw envelope | 저장 원전 | public SDK shape, callback, host event, redaction path |
| OTel span | bounded projection | trace/span ID, sequence, tool link, 운영 수치 |
| evidence graph | 파생 projection | 질문·문서·도구·주장·결과 edge |
| evaluation | 파생 judge | claim별 판정과 근거 sequence |

파생 필드를 raw에 있었던 것처럼 설명하면 안 됩니다. 반대로 OTel에서 payload를 뺐다는 이유로
원문이 사라진 것도 아닙니다. 필요할 때는 OTel sequence로 권한이 통제된 raw archive를 찾아갑니다.

## 29.6 로컬 OTel과 외부 제품을 구분한다

이번 실행의 OTel은 `book_sdk_proof`가 구성한 로컬 `JsonlSpanExporter`와 `ProofTrace`의
**application projection**입니다. cookbook이 설명하는 `CLAUDE_CODE_ENABLE_TELEMETRY=1`과
`OTEL_*` 환경 변수를 이용한 Claude runtime native OTLP export는 실행하지 않았습니다. 두
표면 모두 OTel을 사용하지만 동일한 관측원이라고 설명하면 안 됩니다.

직접 관찰한 것은 같은 trace ID, bounded attribute, 정상 종료 뒤 완성된 span 파일과 최종 파일
무결성입니다. writer/exporter 소스에는 `os.fsync`, `force_flush`, `shutdown` 호출이 있지만
이번 trace에는 syscall receipt가 없습니다. 따라서 구현 경로와 runtime 사건을 구분합니다.

| 기능 | 이번 판정 |
| --- | --- |
| 로컬 redacted raw JSONL 파일 완성 | observed |
| writer/exporter의 `fsync` 호출 | configured / implementation evidence |
| 로컬 OTel JSONL + 단일 trace | observed |
| 정상 종료 시 verdict/root span 기록 | observed |
| Claude runtime native OTLP export | not observed / TODO |
| exporter 실패 후 disk retry | not observed / TODO |
| Datadog exporter와 allowlist | not observed / TODO |
| Perfetto trace | not observed / TODO |
| Genkit projection 실행 | not observed / TODO |
| Opik remote evaluation 저장 | not observed / TODO |
| 비정상 종료의 graceful shutdown | not observed / TODO |

Genkit 화면이 열렸거나 Opik 컨테이너가 떴다는 사실만으로 lineage가 완성되지는 않습니다. 외부
도구를 붙일 때도 `raw sequence -> OTel span -> graph node -> claim -> evaluation` 연결을 다시
검사해야 합니다.

## 29.7 무결성과 독립 감사

감사기는 actor 답변을 채점하지 않았습니다. frozen 뒤 디스크에 기록된 redacted raw JSONL과
OTel JSONL을 각각 다시 읽어 다음을 검사했습니다.

1. raw sequence가 중복 없이 정렬됐는가.
2. 모든 raw sequence에 OTel carrier가 있는가.
3. 모든 scoped span이 같은 trace ID를 공유하는가.
4. ToolUse/ToolResult ID가 raw와 OTel에서 이어지는가.
5. Result의 비용·token·cache 값이 raw와 OTel에서 같은가.
6. 합성 secret이 raw·OTel 어디에도 남지 않았는가.
7. OTel attribute에 payload·prompt·content key가 없는가.
8. terminal Result가 실제 성공했는가.

8개 check가 모두 PASS였습니다. 최종 `integrity.json` 대상 8개를 직접 재계산했고 모두
일치했습니다. 이 PASS는 선언한 frozen scope와 local projection schema의 정합성을 뜻합니다.
외부 exporter, 접근 제어, 장애 복구와 모든 PII 탐지까지 프로덕션 옵저버빌리티 전체가
완성됐다는 인증은 아닙니다.

역사적 attempt의 `source_hash`는 당시 `ch29.md` bytes만 묶었고 probe/runtime/audit/redaction
소스 전체 hash는 보존하지 않았습니다. 그래서 현재 재판독은 raw와 integrity에 근거하지만,
현재 코드를 당시 실행 인과로 소급 확정하지 않습니다. 다음 재실행에서는 해당 소스 hash와
public prompt hash까지 manifest에 묶어야 합니다.

## 29.8 학생 실습

```text
실제 Claude Agent SDK 도구 실행 하나를 만든다.

1. 실제 자격 증명이 아닌 합성 redaction canary를 tool input에 넣는다.
2. SDK Message, callback, host execution을 raw JSONL로 저장한다.
3. raw payload 본문을 복제하지 않는 OTel span schema를 만든다.
4. sequence, session ID, tool use ID, terminal cost/cache만 OTel에 투영한다.
5. frozen scope의 모든 raw event에 carrier span이 있는지 독립 감사한다.
6. raw count와 span count가 달라질 수 있는 이유를 기록한다.
7. 실행하지 않은 Genkit/Opik/exporter retry는 TODO로 남긴다.
```

## Takeaway

옵저버빌리티는 로그를 많이 쌓는 일이 아닙니다. 사건의 shape와 순서를 추적 가능한 저장 원전으로
남기고, 민감 본문은 디스크 기록 전에 redaction하며, 외부 화면에는 필요한 연결과 수치만
투영하고, 그 투영의 누락을 다시 검사하는 일입니다. 대시보드는 증거의 출발점이 아니라 검증
가능한 source chain의 소비자입니다.
