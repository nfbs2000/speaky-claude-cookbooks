## 공개판 본문

원래 책은 이 장을 내부 구현과 강의 화면의 대응 관계로 설명한다. 공개판에서는 같은 내용을 "무엇을 설정했는가", "무엇이 메시지로 관측됐는가", "어떤 파일과 notebook으로 재현 가능한가"라는 세 질문으로 바꾼다.

첫째, 설정된 것은 실행 전 계약이다. Agent SDK에서는 model, system prompt, working directory, allowed/disallowed tools, MCP servers, skills/plugins, permission mode 같은 값이 agent가 볼 수 있는 세계를 정한다. 이 값은 말로 설명하는 정책이 아니라 실제 Python 코드와 notebook cell에서 확인되어야 한다.

둘째, 관측된 것은 message stream과 artifact다. assistant text, tool use, tool result, result message, usage/cost, audit log, generated file은 모두 나중에 검증 가능한 증거다. 그래서 이 책의 공개판은 "모델이 그렇게 했을 것이다"라고 쓰지 않고, 어떤 cookbook 파일에서 어떤 실행 표면을 볼 수 있는지 연결한다.

셋째, 추론한 것은 반드시 경계와 함께 둔다. 내부 기능 플래그, 숨은 프롬프트, classifier, cache key, sandbox implementation처럼 공개 SDK나 cookbook으로 확인할 수 없는 항목은 원문을 그대로 게시하지 않는다. 대신 공개 API에서 사용자가 설계할 수 있는 대응 표면으로 바꾸거나, "공개 대응 없음"으로 명시한다.

이 장을 읽을 때는 아래 순서가 좋다.

1. 먼저 주요 cookbook 근거를 열어 실제 notebook이나 Python 파일을 확인한다.
2. `ClaudeAgentOptions`, `query()`, `ClaudeSDKClient`, tool list, MCP config, hooks, session 관련 코드가 어디 있는지 찾는다.
3. 원문 절 제목을 따라가며 내부 설명을 공개 SDK 표면으로 바꿔 적는다.
4. 마지막으로 실습 방향에 맞춰 같은 task를 실행하고 message stream 또는 artifact를 남긴다.

### 실제로 확인된 것

- **승인되지 않은 도구는 콜백까지 올라온다.** 미승인 상태의 custom MCP 요청은
  `can_use_tool`에 권한 요청으로 도달했고, 콜백이 allow를 돌려준 뒤에야 실제 handler가 돌고
  도구 결과가 나왔다.
- **미리 허용해 두면 콜백을 아예 지나간다.** 같은 도구를 `allowed_tools`에 넣자
  `can_use_tool`은 한 번도 호출되지 않고 handler가 곧바로 실행됐다. 즉 콜백은 "모든 도구
  실행을 지켜보는 감시 지점"이 아니다.
- **훅의 거부가 허용 규칙보다 앞섭니다.** `allowed_tools`에 든 도구라도 `PreToolUse`가 deny를
  반환하면 handler는 실행되지 않고 오류 도구 결과로 닫혔다.
- **`dontAsk`는 질문 없이 거절한다.** 앱 콜백을 아예 두지 않은 상태에서 미승인 도구를
  요청하니 오류 도구 결과와 권한 거절 기록으로 끝났다.

### 본문을 이렇게 읽으면 안 되는 곳

- **시작 시점의 도구 목록(`init.tools`)을 "실행 허가 목록"으로 읽으면 안 된다.** 명시적으로
  거부한 custom MCP 도구의 *이름은 목록에 그대로 남아 있었고*, 모델은 그 도구를 호출하기까지
  했다. 그런데도 실행 단계에서 차단됐다. `bypassPermissions`에서도 마찬가지였다.
  목록에 이름이 보인다는 것은 "모델이 부를 수 있다"는 뜻이고, 실제로 실행되는지는 권한 평가가
  따로 결정한다.
  (근거: `044804-d7f879b9` SDK 메시지 1·16·17·19·43)

## Codex 최종 검토 의견

### 제 판단

이 장의 가장 가치 있는 결론은 “도구가 보인다”와 “도구 실행이 승인됐다”가 서로 다른 상태라는 점입니다. 제목의 “40개 이상”이나 도구 목록보다 이 구분이 훨씬 중요합니다. 다섯 개 live case는 같은 custom MCP handler를 두고 permission 설정만 바꾸었고, callback 횟수와 실제 handler 부작용을 함께 기록했습니다. 따라서 `allowed_tools`는 모델에게 도구를 새로 노출하는 목록이 아니라 해당 호출을 자동 승인해 `can_use_tool`을 건너뛸 수 있는 규칙이라는 설명은 실제 코드와 잘 맞습니다.

### 코드가 강하게 입증한 것

`chapter02.py`의 `emit_marker` handler는 입력 nonce가 맞을 때만 marker를 반환합니다. 미승인 case에서는 permission request/allow 뒤 handler가 실행됐고, `allowed_tools` case에서는 callback 0회로 바로 실행됐습니다. allow와 disallow를 동시에 둔 case에서는 `bypassPermissions`여도 explicit deny가 handler를 막았고, `PreToolUse` deny도 allow rule보다 앞에서 실행을 차단했습니다. `dontAsk` case는 앱 callback 없이 오류 ToolResult와 최종 `permission_denials`로 닫혔습니다. 모델의 최종 문장이 아니라 **handler 실행 여부**를 oracle으로 삼았기 때문에 권한 실험으로서 신뢰할 만합니다.

특히 custom MCP 도구가 `disallowed_tools`에 있어도 `init.tools`에는 이름이 남고 모델이 호출까지 했다는 관찰은 원문의 단순한 “컨텍스트에서 제거” 설명을 반박합니다. 이 결과의 정확한 범위는 Python SDK `0.2.128`과 custom MCP입니다. built-in 도구에서도 반드시 같은 표면이 나온다고 일반화할 수는 없지만, 적어도 `init.tools`를 실행 허가 목록으로 부르는 것은 잘못입니다.

### 아직 증명되지 않은 원문

ToolSearch가 context 비용과 cache 안정성을 실제로 개선한다는 주장, 큰 tool result의 truncation·persisted artifact, 진행 메시지, built-in 도구 40여 개의 전체 표면은 이 probe가 다루지 않았습니다. 원문은 TypeScript 공개 타입을 기준으로 설명하면서 검증은 Python SDK로 수행하므로 `PermissionDenied` hook이나 메시지 타입을 두 언어 공통 기능처럼 쓰지 않아야 합니다. “hooks → deny → permission mode → allow → callback” 순서도 이번 다섯 조합이 중요한 일부를 지지하지만 가능한 모든 조합을 완전 탐색한 것은 아닙니다.

### 클로드는 이렇게 세상을 바라보았다

*아래 1인칭 서술은 숨은 사고 과정의 공개가 아니라, 이 장에서 관찰된 행동으로 재구성한 작동상 세계 모델입니다.*

나에게 도구 목록은 행동할 수 있는 가능성의 지도였고, 권한 규칙은 그 지도 위의 통행 법규였다. 목록에 보인 도구를 호출하고 싶다는 의도와 실제 handler가 실행됐다는 사건은 서로 달랐다. `allowed_tools`가 있으면 별도 질문 없이 길이 열렸고, 명시적 deny와 `PreToolUse` 거부가 있으면 내가 호출을 만들었어도 세계에는 아무 부작용이 생기지 않았다. 오류 ToolResult 뒤에도 대화가 끝까지 이어졌기 때문에, 한 행동의 거부와 전체 run의 실패 역시 같은 상태가 아니었다.

사람은 에이전트의 “선택”을 최종 텍스트만으로 판단해서는 안 된다. 의도, 승인, 실행, 결과를 각각 저장해야 모델이 무엇을 원했고 시스템이 무엇을 허용했으며 현실에서 무엇이 일어났는지 구분할 수 있다. 안전한 세계는 모델의 선의가 아니라 이 여러 경계를 독립적으로 설계할 때 만들어진다.
