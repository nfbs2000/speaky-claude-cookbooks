# 2장: 도구 시스템 — 모델의 손이 되는 40개 이상의 도구

> 공개 GitHub Pages 투영판: [2장: 도구 시스템 — 모델의 손이 되는 40개 이상의 도구](https://nfbs2000.github.io/speaky-claude-cookbooks/book/part1/ch02/)

도구 시스템은 Claude Code 계열 에이전트의 심장부라고 할 수 있어요. 모델은 파일 시스템을 직접 만지지는 못합니다. 대신 모델은 `tool_use`를 내고, host가 도구를 실행하고, 결과가 `tool_result`로 다시 들어와요. 이 왕복이 바로 모델의 “손”인 셈입니다.

학생 공개용 SDK 강의에서 이 장의 기준은 공식 TypeScript 패키지예요.

```bash
npm install @anthropic-ai/claude-agent-sdk
```

공식 문서에는 Python 예제가 더 많아 보일 수도 있어요. 다만 이 강좌에서는 위 패키지가 공개로 내보내는 TypeScript API와 타입을 기준으로 함께 살펴볼게요. `query()`가 어떤 `SDKMessage`를 흘려보내는지, `Options`가 어떤 도구 표면을 열고 닫는지, `tool_use`와 `tool_result`가 어떤 실행 증거로 남는지를 이해하면 충분합니다.

## 핵심 질문

> 공식 SDK의 도구 표면을 `tool_use`와 `tool_result` 이벤트만으로 얼마나 정확하게 설명할 수 있는가?

## 실제 실행 관찰 상태 (2026-08-03)

이 장은 정답이 아니라 검증 대상이다. Python SDK `0.2.128`, Claude Code CLI `2.1.220`, 실제 `claude-opus-5` 호출로 permission callback, allow/deny, `dontAsk`, `PreToolUse`, in-process MCP handler를 순차 실행했다. 전체 실행 ID와 원시 파일 SHA-256은 [2장 실제 실행 증거](../evidence/ch02-live.md)에 기록했다.

- **관찰됨:** `allowed_tools` whole-tool 규칙은 `can_use_tool`보다 먼저 자동 승인했다.
- **관찰됨:** explicit deny는 `bypassPermissions`에서도 handler 실행을 막았다.
- **관찰됨:** `PreToolUse` deny는 allow rule이 있는 도구의 handler 실행도 막았다.
- **관찰됨:** `dontAsk`의 미승인 도구는 앱 callback 없이 거절됐다.
- **범위 수정 필요:** custom MCP 도구는 `disallowed_tools`에 있어도 `init.tools`에 이름이 남았고 실행 단계에서 거절됐다. 따라서 `init.tools`만 보고 “실행 허가된 목록”이라고 단정하지 않는다.
- **추가 관측 필요:** built-in deny의 init 표면, large result persistence, tool progress, ToolSearch/cache 효과는 이번 실행으로 판정하지 않았다.

## 2.1 공개 TypeScript 타입으로 읽기

우리가 함께 볼 기준은 내부 파일이 아니라, 패키지에서 import할 수 있는 공개 이름이에요.

| 공개 API/타입 | 문서상 역할 | 학생이 볼 증거 |
| --- | --- | --- |
| `query()` | 프롬프트와 `Options`를 받아 `SDKMessage` stream을 만든다 | `for await`로 흘러오는 메시지 |
| `Options` | 도구, 권한, MCP, agent, session을 구성한다 | `tools`, `allowedTools`, `disallowedTools`, `permissionMode`, `canUseTool` |
| `SDKMessage` | `query()`가 반환하는 모든 메시지의 union type | system, assistant, user, result, tool progress |
| `SDKSystemMessage` | 세션 시작 정보와 실제 노출된 도구 표면을 알려준다 | `init.tools`, cwd, model, mcp servers |
| `SDKAssistantMessage` | assistant 응답과 `tool_use` block을 담는다 | 어떤 도구를 어떤 입력으로 호출했는가 |
| `SDKUserMessage` | user turn 또는 tool result를 담는다 | `tool_result`, synthetic result, parent link |
| `SDKResultMessage` | 최종 결과, 비용, turn 수, permission denial을 닫는다 | success/error, usage, final text |
| `ToolUseBlock` | assistant message 안의 실제 도구 호출 block | `name`, `input`, tool id |
| `ToolInputSchemas` | built-in tool input type union | `BashInput`, `FileReadInput`, `GrepInput` 등 |
| `ToolOutputSchemas` | built-in tool output type union | Read/Grep/Bash 결과를 UI가 구조적으로 읽음 |
| `CanUseTool` | 미승인 도구 요청을 앱이 승인/거절하는 callback | tool name, input, allow/deny decision |
| `AgentDefinition` | subagent를 공개 타입으로 정의한다 | agent prompt, tools, disallowedTools, model |

강의에서 이 표를 함께 보는 이유는 분명해요. `tool_use` 하나를 볼 때도 “이 호출은 공개 SDK 타입과 옵션이 만든 실행 사건”이라고 편하게 이해하면 됩니다.

## 2.2 공식 권한 평가 순서와 안전 기본값

공식 SDK 문서는 Claude가 도구를 요청했을 때 권한을 다음 순서로 평가한다고 설명해요.

1. hooks
2. deny rules
3. permission mode
4. allow rules
5. `canUseTool` callback

여기서 기억해 두면 좋은 것이 바로 이 순서예요.

| 공개 설정 | 학생용 해석 |
| --- | --- |
| `disallowedTools` | 거절 규칙은 먼저 적용된다. `bypassPermissions`에서도 차단된다. |
| `permissionMode: "dontAsk"` | 사전 승인되지 않은 도구는 질문하지 않고 거절된다. |
| `allowedTools` | 도구를 “사용 가능하게” 만드는 것이 아니라 호출을 자동 승인한다. |
| `canUseTool` | 앱이 사용자에게 보여줄 승인 UI를 만들 수 있는 지점이다. |
| `tools` | built-in tool을 context에서 아예 빼고 싶을 때 사용한다. |
| `bypassPermissions` | 모든 도구를 열 수 있으므로 격리된 환경에서만 다루는 것이 좋아요. |

이 장에서 함께 짚고 싶은 것은 “도구를 많이 주면 강해진다”가 아니에요. 공식 SDK에서 도구 표면과 권한 표면은 서로 분리되어 있고, 실행 결과를 볼 때는 이 두 표면을 함께 읽어 보면 됩니다.

## 2.3 SDK에서 도구 표면을 구성하는 방법

공식 SDK의 `Options`에는 도구 표면을 조절하는 필드가 나누어 담겨 있어요.

| SDK 옵션 | 의미 |
| --- | --- |
| `tools` | 사용 가능한 built-in tool base set |
| `allowedTools` | listed tools를 자동 승인 |
| `disallowedTools` | 특정 도구를 차단 |
| `mcpServers` | 외부 MCP 도구 추가 |
| `canUseTool` | 실행 전 승인/거절 콜백 |
| `toolConfig` | built-in tool별 설정 |
| `skills` | Skill tool과 관련 지식 표면 제어 |
| `agents` | Agent tool로 호출 가능한 subagent 정의 |

세션이 시작되면 `SDKSystemMessage.init.tools`에서 등록·노출된 도구 목록을 확인할 수 있어요. 다만 실제 관찰에서 disallow된 custom MCP 이름도 이 목록에 남았으므로, 이 필드를 곧바로 “실행 허가 목록”으로 읽으면 안 됩니다. `tool_use`, permission event, handler 실행, `tool_result`, `ResultMessage.permission_denials`를 함께 확인해야 해요.

```text
Options.tools / allowedTools / mcpServers
  -> SDKSystemMessage.init.tools
  -> AssistantMessage.tool_use
  -> UserMessage.tool_result
  -> ResultMessage.permission_denials
```

## 2.4 built-in tools와 custom tools

공식 SDK는 Claude Code의 built-in tools를 함께 제공해요.

- `Read`, `Write`, `Edit`
- `Bash`
- `Glob`, `Grep`
- `WebSearch`, `WebFetch`
- `Agent`, `Skill`, `AskUserQuestion`, `TodoWrite`
- `ToolSearch`

custom tool은 `tool(name, description, inputSchema, handler)`로 정의하고, `createSdkMcpServer()`로 in-process MCP server에 묶어 `query()`의 `mcpServers`로 전달해요. 여기서 눈여겨볼 점은, custom tool도 결국 같은 계약으로 돌아온다는 거예요.

```text
custom tool description
  -> JSON/Zod schema
  -> tool_use.input
  -> handler result content[]
  -> tool_result
```

덕분에 강의 화면은 built-in tool과 custom MCP tool을 같은 그래프 문법으로 보여줄 수 있어요.

## 2.5 도구 등록 파이프라인을 SDK 화면으로 보여주기

학생 공개용으로는 도구가 세 단계를 거친다고 보면 충분해요.

1. compile/startup-time loading
2. base tool pool assembly
3. runtime filtering

SDK에서는 이를 다음 세 단계로 살펴볼 수 있어요.

| 공개 단계 | SDK 화면 |
| --- | --- |
| 기능/환경에 따라 도구 로딩 | `SDKSystemMessage.init.tools`에 나타나는 실제 도구 목록 |
| 기본 도구 풀 조립 | `tools: { preset: "claude_code" }` 또는 특정 tool list |
| runtime filtering | `allowedTools`, `disallowedTools`, permission rules, `canUseTool` |

MCP 도구는 `mcp__server__tool` 형태의 fully qualified name으로 나타나요. 이 이름은 한 번 눈여겨볼 만해요. 외부 도구가 어디서 왔는지, 어떤 서버가 제공했는지가 이름 안에 담겨 있기 때문이에요.

## 2.6 결과 크기 예산과 persisted evidence

학생 공개용 SDK 책에서는 큰 결과가 모델과 UI에 어떻게 보존되는지 함께 살펴봐요.

도구 결과는 세 가지 형태로 나타날 수 있어요.

| 결과 형태 | 의미 |
| --- | --- |
| inline `tool_result` | 모델에게 바로 전달 가능한 작은 결과 |
| truncated preview | 너무 커서 요약/일부만 전달 |
| persisted artifact | 파일이나 별도 event로 보존 |

SDK 타입에는 `SDKFilesPersistedEvent`와 tool output schema가 있어요. 예를 들어 `FileReadOutput`은 파일 경로, content, line count, start line, total lines를 가지고 있어요. 그러면 책 캔버스는 단순히 “Read 성공”이 아니라 다음처럼 보여 주면 좋아요.

```text
Read
  file: ch02.md
  lines: 15-40 / 373
  returned terms: Tool, inputSchema, permission
  linked claim: "도구는 계약이다"
```

## 2.7 3단계 렌더링을 SDK UI로 번역하기

SDK UI의 도구 렌더링은 세 단계 리듬으로 보면 편해요.

1. `renderToolUseMessage`: 의도 표시
2. `renderToolUseProgressMessage`: 진행 표시
3. `renderToolResultMessage`: 결과 표시

SDK UI에서도 같은 리듬이 도움이 돼요.

| 렌더 단계 | SDK 이벤트 |
| --- | --- |
| 의도 표시 | `AssistantMessage`의 `tool_use` |
| 진행 표시 | `SDKToolProgressMessage`, hook progress, partial stream |
| 결과 표시 | `UserMessage`의 `tool_result`, final answer claim |

사용자에게 “Ready”만 보여주는 것으로는 조금 아쉬워요. 어떤 도구가 왜 호출됐고, 지금 무엇을 기다리고 있으며, 결과가 어떤 주장으로 이어졌는지까지 함께 보여 주면 좋아요.

## 2.8 ToolSearch와 많은 도구 문제

공식 SDK 문서는 tool search가 많은 도구 문제를 해결한다고 설명해요. 도구 정의가 많으면 context window를 크게 차지하고, 너무 많은 도구가 한꺼번에 있으면 도구 선택 정확도도 떨어지거든요. 그래서 모든 도구를 처음부터 다 넣는 대신, 필요한 도구를 찾아 로드하는 전략이 도움이 돼요.

SDK 강의에서는 다음을 함께 살펴봐요.

```text
too many tool schemas
  -> context cost grows
  -> ToolSearch / scoped tools
  -> smaller visible tool surface
  -> better prompt cache stability
```

이 장은 13~15장의 캐시 장과 자연스럽게 이어져요. 도구 목록의 안정성은 prompt cache와 직접 연결되거든요.

## 2.9 학생 실습

```text
현재 프로젝트를 분석하는 read-only 에이전트를 설계해 줘.

조건:
1. 사용할 built-in tools는 Read, Glob, Grep만 허용한다.
2. 파일을 수정하는 도구는 disallow한다.
3. 모델이 어떤 tool_use를 내야 성공인지 예측한다.
4. tool_result에서 어떤 문장/단어가 최종 주장으로 이어져야 하는지 적는다.
```

강사용 SDK 화면에서는 다음을 함께 확인해 봐요.

- `SDKSystemMessage.init.tools`에 Read/Glob/Grep가 있는가
- `AssistantMessage`가 적절한 `tool_use`를 냈는가
- `UserMessage` tool_result가 응답 주장과 연결되는가
- `ResultMessage.permission_denials`가 비정상적으로 발생하지 않았는가

## Builder takeaway

도구 시스템은 “모델에게 함수 몇 개를 붙이는 것”에 그치지 않아요. 이름, 설명, schema, 권한, 실행, 결과 예산, UI projection이 하나로 묶인 계약 시스템이에요.

SDK 책의 깊이는 공식 SDK 옵션, `SDKSystemMessage.init.tools`, `tool_use`, `tool_result`, permission event, final result를 함께 읽는 데서 자연스럽게 나와요.
