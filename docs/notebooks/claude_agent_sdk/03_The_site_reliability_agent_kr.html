SRE 장애 대응 에이전트¶

들어가며¶

새벽 3시, 호출기가 울리고 API가 500 오류를 쏟아냅니다. 반쯤 잠에서 깬 채 대시보드를 노려보며 열댓 개 서비스의 지표와 로그를 맞춰 보는 동안 고객 영향은 분 단위로 커집니다. 이 노트북에서는 그 워크플로를 자율적으로 처리하는 SRE 장애 대응 에이전트를 만듭니다. 장애를 조사하고, 근본 원인을 찾고, 조치를 적용하고, 결과를 문서화합니다.

노트북 02에서는 외부 시스템에서 읽을 수 있는 관측 가능성 에이전트를 만들었습니다. 이 노트북은 한 걸음 더 나아갑니다. 에이전트가 행동도 할 수 있습니다. 설정 파일을 수정하고 서비스를 재시작해 발견한 문제를 고칩니다. 안전한 인프라 접근을 위해 범위를 좁힌 MCP 도구와 함께 Claude Agent SDK를 사용합니다.

배울 내용¶

  • 디렉터리 제한, 명령 허용 목록, 검증 훅으로 MCP 도구의 범위를 좁혀 에이전트에 안전한 쓰기 권한을 주는 방법
  • 정교한 프롬프트보다 명확한 도구 설명이 자율적인 에이전트 동작을 더 효과적으로 이끄는 이유
  • 지표, 로그, 경보, 설정 같은 프로덕션 신호를 종합해 어느 한 출처만으로는 드러나지 않는 일관된 진단을 만들어 내는 방법
  • 조사와 조치를 분리하는 사람 개입 워크플로를 구성해 에이전트가 언제 자율적으로 행동할지 통제하는 방법

마지막에는 이 에이전트를 여러분의 인프라에 연결하고, 팀이 이미 쓰고 있는 플랫폼으로 확장하는 방법을 안내합니다.

사전 준비¶

이 노트북을 실행하려면 다음이 필요합니다.

  • 모의 인프라를 위해 로컬에서 실행 중인 Docker (설치 가이드)
  • Claude Agent SDK로 에이전트를 실행할 Anthropic API 키 (API 키 발급)
  • claude-agent-sdk와 httpx 패키지가 설치된 Python 3.11 이상
  • 이 노트북과 같은 디렉터리의 infra_setup.py와 sre_mcp_server.py(저장소에 포함되어 있습니다)

이 노트북의 핵심 단계를 실행하는 데 추가 외부 계정은 필요하지 않습니다. 인프라(PostgreSQL, Prometheus, API 서버)는 전부 로컬 Docker 컨테이너에서 돌아갑니다. 뒤쪽 절에서는 외부 프로덕션 서비스로 에이전트를 확장하는 방법을 안내합니다.

쿡북 저장소에서 실행하시나요? 노트북을 실행하기 전에 작업 디렉터리가 claude_agent_sdk/site_reliability_agent/인지 확인하세요.

1단계: 인프라 파일 생성하기¶

이 노트북과 함께 두 개의 파일을 넣어 두었습니다.

  1. infra_setup.py — Docker 기반 인프라(Compose 설정, Prometheus, API 서버, 트래픽 생성기)를 생성합니다. 에이전트 테스트용 로컬 환경을 어떻게 구성하는지 이해하려면 이 파일을 살펴보세요.
  2. sre_mcp_server.py — 에이전트가 통신하는 MCP 도구 서버입니다. 가장 중요하게 읽어야 할 파일로, 도구를 정의하고, 안전 범위를 갖춘 핸들러를 구현하고, JSON-RPC로 모든 것을 연결하는 방법을 보여 줍니다. 자체 에이전트 통합을 만든다면 이 패턴을 참고해 에이전트에 알맞은 도구를 주는 방법을 파악하세요.

1a단계: 인프라 준비¶

infra_setup.py는 프로덕션 장애를 시뮬레이션할 완전한 로컬 환경을 생성합니다.

  • config/docker-compose.yml — 네 개의 서비스를 정의합니다. PostgreSQL(데이터베이스), API 서버(DB에 질의하는 FastAPI 앱), 트래픽 생성기(부하를 흉내 내는 연속 HTTP 요청 전송), Prometheus(API 서버에서 지표 수집). 우리가 망가뜨렸다가 고칠 시스템입니다.
  • config/prometheus.yml — Prometheus가 API 서버의 /metrics 엔드포인트를 5초마다 수집하도록 설정해, 오류율·지연 시간·DB 연결 사용량을 실시간으로 볼 수 있게 합니다.
  • config/api-server.env — API 서버의 환경 변수이며, 장애를 유발하기 위해 잘못 설정할 파라미터인 DB_POOL_SIZE가 들어 있습니다.
  • services/api_server.py — HTTP 요청을 처리하고, PostgreSQL에 연결하고, Prometheus 지표를 노출하는 FastAPI 애플리케이션입니다. 요청 수, 지연 시간 히스토그램, DB 연결 풀 게이지를 계측합니다.
  • scripts/traffic_generator.py — 지표가 계속 흐르도록 API 서버에 꾸준히 요청을 보냅니다. 덕분에 장애가 Prometheus에서 즉시 보입니다.
  • hooks/ — 안전 훅 스크립트(5단계에서 채워집니다).

여러분의 인프라에 맞게 바꾼다면 이 생성 파일들을 실제 서비스 연결로 교체하게 되지만, 패턴(Docker Compose + Prometheus + 계측된 서비스)은 동일합니다.

1b단계: MCP 서버¶

sre_mcp_server.py는 에이전트 실행 중에 Claude Agent SDK가 하위 프로세스로 띄우는 도구 서버입니다. 직접 읽고 수정할 수 있도록 독립된 Python 파일로 포함해 두었습니다.

sre_mcp_server.py를 잠시 살펴보세요. 그 구조를 이해하는 것이 자체 에이전트 통합을 만드는 열쇠입니다. 이 서버는 stdin/stdout 위의 JSON-RPC 프로토콜을 구현합니다. Agent SDK가 도구를 호출해야 하면 서버의 stdin에 요청을 쓰고, 서버가 알맞은 핸들러로 보낸 뒤 결과를 stdout에 다시 씁니다.

서버는 네 범주에 걸쳐 도구 12개를 등록합니다.

범주 도구 용도
Prometheus query_metrics, list_metrics, get_service_health 지표 질의, 사용 가능한 데이터 탐색, 상태 요약 조회
인프라 read_config_file, edit_config_file, run_shell_command, get_container_logs 설정 읽기·쓰기, Docker 명령 실행, 로그 확인
진단 get_logs, get_alerts, get_recent_deployments, execute_runbook 애플리케이션 로그, 경보 이력, 배포 추적, 구조화된 플레이북
문서화 write_postmortem 장애 사후 분석을 디스크에 기록

각 도구에는 풍부한 설명이 담긴 JSON Schema 정의가 있고, 에이전트는 이를 읽어 각 도구를 언제 어떻게 쓸지 결정합니다. 잘 쓰인 도구 설명은 에이전트 효과를 좌우하는 가장 중요한 요소 중 하나입니다.

서버에는 해당 API 키가 설정되면 활성화되는 PagerDuty(장애 관리)와 Confluence(사후 분석 문서화)용 프로덕션 확장 도구도 들어 있습니다. 이 노트북 마지막의 "한 걸음 더" 절을 참고하세요.

아키텍처 개요¶

SRE 에이전트는 Model Context Protocol(MCP) 패턴을 사용합니다. 에이전트는 별도의 하위 프로세스로 실행되는 도구 서버와 stdin/stdout으로 연결되어 통신합니다.

Claude Agent SDK  <-- query() loop streams responses
    │                                               
    ▼                                               
MCP Server (subprocess via stdio/JSON-RPC)          
    │                                               
    ├── Prometheus (metrics & health checks)        
    ├── Docker (container logs & commands)          
    └── Config Management (read/edit env files)

왜 하위 프로세스인가? 도구 서버를 별도 프로세스로 실행하면 격리가 이뤄져, 도구 핸들러가 크래시하거나 멈춰도 에이전트가 함께 죽지 않습니다. 또한 에이전트의 추론 루프와 인프라 접근 계층을 깔끔하게 분리할 수 있습니다.

인프라 도구 핸들러¶

아래는 각 인프라 도구의 핸들러 구현입니다. 쓰기 도구의 안전 검사를 특히 눈여겨보세요. 에이전트에 실제 인프라 접근 권한을 안전하게 줄 수 있게 해 주는 안전장치입니다.

  • edit_config_file은 쓰기를 config/ 디렉터리로만 제한합니다
  • run_shell_command는 docker-compose나 docker로 시작하는 명령만 허용합니다
  • get_container_logs는 컨테이너 이름을 화이트리스트와 대조해 검증합니다
SRE_PROJECT_ROOT = os.getcwd()


async def read_config_file(path: str) -> dict[str, Any]:
    """Read a config file, restricted to the config/ directory."""
    full_path = Path(os.path.join(SRE_PROJECT_ROOT, path)).resolve()
    allowed_root = Path(SRE_PROJECT_ROOT, "config").resolve()
    if not full_path.is_relative_to(allowed_root):
        return {
            "content": [
                {"type": "text", "text": "Error: Can only read from config/ directory"}
            ],
            "isError": True,
        }
    with open(full_path, "r") as f:
        content = f.read()
    return {"content": [{"type": "text", "text": content}], "isError": False}


async def edit_config_file(path: str, old_value: str, new_value: str) -> dict[str, Any]:
    """Edit a config file by replacing old_value with new_value. Restricted to config/ directory."""
    full_path = Path(os.path.join(SRE_PROJECT_ROOT, path)).resolve()
    allowed_root = Path(SRE_PROJECT_ROOT, "config").resolve()
    if not full_path.is_relative_to(allowed_root):
        return {
            "content": [
                {
                    "type": "text",
                    "text": "Error: Can only edit files in config/ directory",
                }
            ],
            "isError": True,
        }
    with open(full_path, "r") as f:
        content = f.read()
    if old_value not in content:
        return {
            "content": [
                {"type": "text", "text": f"Error: '{old_value}' not found in {path}"}
            ],
            "isError": True,
        }
    new_content = content.replace(old_value, new_value, 1)
    with open(full_path, "w") as f:
        f.write(new_content)
    return {
        "content": [
            {
                "type": "text",
                "text": f"Updated {path}: replaced '{old_value}' with '{new_value}'",
            }
        ],
        "isError": False,
    }


async def run_shell_command(command: str) -> dict[str, Any]:
    """Run a shell command. Restricted to docker/docker-compose commands."""
    args = shlex.split(command)
    if not args or args[0] not in ("docker-compose", "docker"):
        return {
            "content": [
                {
                    "type": "text",
                    "text": "Error: Only docker and docker-compose commands are allowed",
                }
            ],
            "isError": True,
        }
    result = subprocess.run(
        args, capture_output=True, text=True, cwd=SRE_PROJECT_ROOT, timeout=60
    )
    output = result.stdout + result.stderr
    return {
        "content": [{"type": "text", "text": output or "(no output)"}],
        "isError": result.returncode != 0,
    }


async def get_container_logs(container: str, lines: int = 50) -> dict[str, Any]:
    """Get container logs. Validates container name against whitelist."""
    allowed = {"api-server", "postgres", "prometheus", "traffic-generator"}
    if container not in allowed:
        return {
            "content": [
                {"type": "text", "text": f"Error: Container must be one of {allowed}"}
            ],
            "isError": True,
        }
    result = subprocess.run(
        [
            "docker-compose",
            "-f",
            "config/docker-compose.yml",
            "logs",
            "--tail",
            str(lines),
            container,
        ],
        capture_output=True,
        text=True,
        cwd=SRE_PROJECT_ROOT,
    )
    return {
        "content": [
            {"type": "text", "text": result.stdout or result.stderr or "(no logs)"}
        ],
        "isError": False,
    }

3단계: Prometheus — 지표와 상태 점검¶

Prometheus는 SRE 에이전트의 관측 가능성 계층입니다. 오류율 급등, 지연 시간 상승, 데이터베이스 연결 고갈처럼 무언가 잘못되었음을 알려 주는 정량 신호를 제공합니다.

Prometheus 도구 세 개를 정의합니다.

  • query_metrics — 임의의 PromQL 질의를 실행합니다(에이전트가 조사 내용에 따라 스스로 질의를 작성할 수 있습니다)
  • list_metrics — 어떤 지표가 있는지 탐색합니다
  • get_service_health — 오류율, 지연 시간, DB 연결을 한 번에 확인하는 미리 만들어진 상태 요약입니다

Prometheus 도구 핸들러¶

아래 핸들러들은 Prometheus HTTP API에 질의합니다. get_service_health는 여러 PromQL 질의를 하나의 구조화된 상태 보고서로 묶어 주어, 에이전트가 어디를 더 파고들지 정하기 전에 빠르게 전체를 훑을 수 있게 합니다.

async def query_metrics(promql: str) -> dict[str, Any]:
    """Query Prometheus with a PromQL expression."""
    try:
        async with httpx.AsyncClient() as client:
            response = await client.get(
                f"{PROMETHEUS_URL}/api/v1/query",
                params={"query": promql},
                timeout=10.0,
            )
            response.raise_for_status()
            data = response.json()

        if data["status"] != "success" or not data["data"]["result"]:
            return {
                "content": [
                    {"type": "text", "text": f"No results for query: {promql}"}
                ],
                "isError": False,
            }

        results = []
        for r in data["data"]["result"]:
            metric = r["metric"]
            value = r["value"][1] if "value" in r else "N/A"
            label = ", ".join(f"{k}={v}" for k, v in metric.items() if k != "__name__")
            name = metric.get("__name__", "")
            results.append(f"{name}{{{label}}}: {value}")

        return {
            "content": [{"type": "text", "text": "\n".join(results)}],
            "isError": False,
        }
    except Exception as e:
        return {
            "content": [{"type": "text", "text": f"Prometheus query error: {e}"}],
            "isError": True,
        }


async def list_metrics() -> dict[str, Any]:
    """List all available Prometheus metric names."""
    try:
        async with httpx.AsyncClient() as client:
            response = await client.get(
                f"{PROMETHEUS_URL}/api/v1/label/__name__/values", timeout=10.0
            )
            response.raise_for_status()
            data = response.json()
        metrics = data.get("data", [])
        return {
            "content": [
                {
                    "type": "text",
                    "text": f"Available metrics ({len(metrics)}):\n"
                    + "\n".join(sorted(metrics)),
                }
            ],
            "isError": False,
        }
    except Exception as e:
        return {
            "content": [{"type": "text", "text": f"Error listing metrics: {e}"}],
            "isError": True,
        }


async def get_service_health() -> dict[str, Any]:
    """Get a comprehensive health summary across all services."""
    health_queries = {
        "error_rate_per_service": 'sum(rate(http_requests_total{status="500"}[1m])) by (service)',
        "request_rate_per_service": "sum(rate(http_requests_total[1m])) by (service)",
        "p99_latency": 'http_request_duration_milliseconds{quantile="0.99"}',
        "p50_latency": 'http_request_duration_milliseconds{quantile="0.5"}',
        "db_connections_active": "db_connections_active",
        "db_pool_size": "db_pool_size",
    }
    results = {}
    try:
        async with httpx.AsyncClient() as client:
            for name, promql in health_queries.items():
                response = await client.get(
                    f"{PROMETHEUS_URL}/api/v1/query",
                    params={"query": promql},
                    timeout=10.0,
                )
                data = response.json()
                if data["status"] == "success" and data["data"]["result"]:
                    for r in data["data"]["result"]:
                        label = r["metric"].get(
                            "service", r["metric"].get("__name__", name)
                        )
                        results[f"{name}[{label}]"] = r["value"][1]
                else:
                    results[name] = "no data"

        summary = "Service Health Summary:\n"
        for k, v in sorted(results.items()):
            summary += f"  {k}: {v}\n"
        return {"content": [{"type": "text", "text": summary}], "isError": False}
    except Exception as e:
        return {
            "content": [{"type": "text", "text": f"Health check error: {e}"}],
            "isError": True,
        }

MCP 서버 프로토콜 참고¶

MCP 서버는 독립 프로세스로 실행되며 stdin/stdout에서 JSON-RPC로 통신합니다. Claude Agent SDK가 도구를 호출해야 하면 요청을 보내고, 서버가 올바른 핸들러로 라우팅해 결과를 반환합니다.

서버는 네 가지 JSON-RPC 메서드를 처리합니다.

  • initialize — SDK와의 핸드셰이크(서버 기능 반환)
  • notifications/initialized — 확인 응답(응답 불필요)
  • tools/list — 사용 가능한 모든 도구 스키마 반환
  • tools/call — 특정 도구를 실행하고 결과 반환

서버 루프는 stdin에서 JSON-RPC 요청을 읽어 알맞은 핸들러로 보내고, 결과를 stdout에 다시 씁니다:

async def main():
    reader = asyncio.StreamReader()
    protocol = asyncio.StreamReaderProtocol(reader)
    await loop.connect_read_pipe(lambda: protocol, sys.stdin)

    while True:
        line = await reader.readline()
        request = json.loads(line)

        if request["method"] == "initialize":
            send_result(request["id"], server_info)
        elif request["method"] == "tools/list":
            send_result(request["id"], {"tools": ALL_TOOLS})
        elif request["method"] == "tools/call":
            result = await dispatch(request["params"])
            send_result(request["id"], result)

각 도구 호출은 다음 흐름을 거칩니다. SDK가 JSON-RPC 요청 전송 → 서버가 핸들러로 라우팅 → 핸들러가 결과 반환 → SDK가 응답 수신. 전체 구현은 sre_mcp_server.py를 참고하세요.

5단계: 안전 훅 — 쓰기 작업에 대한 안전장치¶

MCP 도구 핸들러에는 기본적인 안전 검사(디렉터리 제한, 허용된 명령 접두사)가 들어 있습니다. 훅은 두 번째 방어선입니다. 에이전트가 어디를 바꾸는지뿐 아니라 무엇을 바꾸는지 그 내용까지 검증하는 셸 스크립트입니다.

훅은 도구가 실행되기 전에 자동으로 돌아갑니다. PreToolUse 훅이 0이 아닌 상태로 종료하면 도구 호출이 차단됩니다. 그러면 에이전트가 오류를 보고 접근 방식을 바꿔야 합니다.

infra_setup.py는 hooks/ 디렉터리에 훅 스크립트 두 개를 생성합니다.

  1. validate_pool_size.sh — edit_config_file 호출의 new_value 필드를 파싱합니다. 새 DB_POOL_SIZE 값이 안전 범위(5~100)를 벗어나면 훅이 0이 아닌 상태로 종료하며 수정이 차단됩니다.
  2. validate_config_before_deploy.sh — api-server를 재배포하는 run_shell_command 호출 전에 발동합니다. config/api-server.env를 읽어 DB_POOL_SIZE가 안전 범위를 벗어나면 배포를 차단합니다.

두 훅 모두 아래 에이전트 설정에 PreToolUse 훅으로 등록되며, SDK가 해당 도구 실행 전에 자동으로 돌립니다.

엔지니어는 Slack 채널에서 에이전트를 멘션해 상호작용합니다. 에이전트는 스레드 안에서 조사하며 도구 호출과 발견 사항을 실시간으로 스트리밍합니다. 같은 스레드의 후속 메시지는 대화를 이어 갑니다. Slack 통합에는 @멘션을 수신해 에이전트에 메시지를 전달하는 별도의 배포 파일(예: slack-bolt를 사용하는 sre_bot_slack.py)이 필요합니다. 구현 예시는 examples/sre_bot_slack.py를 참고하세요.

에이전트에서 도구 활성화하기¶

에이전트 설정의 allowed_tools에 통합 도구를 추가하세요:

options = ClaudeAgentOptions(
    ...
    allowed_tools=[
        # ... existing investigation + remediation tools ...

        # PagerDuty (requires PAGERDUTY_API_KEY, PAGERDUTY_SERVICE_ID)
        "mcp__sre__pagerduty_create_incident",
        "mcp__sre__pagerduty_update_incident",
        "mcp__sre__pagerduty_get_incident",
        "mcp__sre__pagerduty_list_incidents",

        # Confluence (requires CONFLUENCE_BASE_URL, CONFLUENCE_API_TOKEN)
        "mcp__sre__confluence_create_postmortem",
        "mcp__sre__confluence_get_page",
        "mcp__sre__confluence_list_postmortems",
    ],
)

시스템 프롬프트나 MCP 서버는 바꿀 필요가 없습니다. 에이전트가 서버에서 새 도구를 발견해 알맞은 때에 사용합니다.

마무리¶

이 노트북은 Claude에 에이전트 루프와 알맞은 도구를 줬을 때 무슨 일이 일어나는지 보여 줍니다. 일반적인 조사 지침만 담은 단순한 시스템 프롬프트로, Claude는 잘 설명된 MCP 도구 12개를 활용해 다음을 자율적으로 수행했습니다.

  • Prometheus에 질의해 상승한 오류율과 지연 시간 탐지
  • 여러 신호를 연결해 문제를 DB 연결 고갈로 좁힘
  • 컨테이너 로그를 읽어 가설 확인
  • 설정 파일을 살펴 근본 원인 발견
  • 설정을 수정하고, 서비스를 재배포하고, 수정을 검증
  • 장애 전체를 사후 분석으로 문서화

에이전트는 어떤 도구를 호출할지, 어떤 질의를 쓸지, 결과를 어떻게 해석할지 스스로 정했고, 각 단계에서 알아낸 것에 따라 접근을 조정했습니다. 이것이 에이전트 루프의 힘입니다. 관찰 → 추론 → 행동 → 반복.

아래 그림은 이 노트북에서 만든 에이전트가 프로덕션 배포로 어떻게 확장되는지 보여 줍니다. 핵심 에이전트 루프(Claude Agent SDK)는 그대로이고, 달라지는 것은 여러분이 연결하는 도구, 플랫폼, 스킬입니다. 이 노트북에서는 Prometheus와 Docker를 썼습니다. 프로덕션에서는 Kubernetes, Slack, Confluence, 그리고 여러분의 관측 스택을 위한 MCP 서버와 함께 커스텀 스킬과 훅을 더할 수 있습니다. 각 MCP 서버는 범위를 좁힌 도구를 노출하고 에이전트가 이를 자동으로 발견합니다. 장애가 났을 때 온콜 엔지니어가 손을 뻗는 도구가 무엇인지 생각해 보세요. 그것이 바로 여러분이 만들 도구입니다.

노트북 02에서 노트북 03으로¶

노트북 02에서 에이전트는 지표를 질의하고, CI 상태를 확인하고, 로그를 읽으며 관찰할 수 있었습니다. 이 노트북에서는 에이전트가 행동할 수 있습니다. 읽기 전용 관찰에서 읽기·쓰기 조치로 넘어가는 그 도약이 프로덕션에서 에이전트를 진짜 쓸모 있게 만듭니다. 핵심 설계 통찰은 이것입니다. 광범위한 셸 접근이 아니라, 안전 검사가 내장된 좁은 MCP 도구로 쓰기 권한을 제공하세요.

여기서 어디로 갈까¶

같은 패턴(에이전트 루프 + 범위를 좁힌 도구 + 단순한 프롬프트)이 다음처럼 많은 에이전트 사용 사례에 적용됩니다.

운영과 인프라:

  • 보안 사고 분류 — 경보를 연결하고, 접근 로그를 확인하고, 영향받은 시스템을 격리
  • 인프라 비용 분석 — 클라우드 API에 질의하고, 낭비를 찾아내고, 최적화를 제안하고 적용
  • 배포 검증 — 배포 후 상태 지표를 확인하고, 이상이 있으면 롤백

업무 프로세스 자동화:

  • 이메일 분류와 응답 — 수신 메시지를 읽고, 긴급도를 분류하고, 답장 초안을 쓰고, 필요하면 에스컬레이션
  • 고객 지원 라우팅 — 티켓을 분석하고, 관련 문서를 찾고, 해결책을 제안하고, CRM 갱신
  • 인보이스 처리 — 문서에서 데이터를 추출하고, 발주서와 대조 검증하고, 불일치 표시

리서치와 분석:

  • 경쟁 정보 수집 — 출처를 모니터링하고, 핵심 신호를 추출하고, 구조화된 브리핑 작성
  • 컴플라이언스 감사 — 설정을 정책과 대조 검사하고, 위반을 표시하고, 보고서 생성
  • 데이터 파이프라인 모니터링 — 데이터 신선도를 확인하고, 행 수를 검증하고, 이상 시 경보

어느 경우든 방법은 같습니다. 관련 시스템에 맞는 범위를 좁힌 도구를 정의하고, Claude에 에이전트 루프를 주고, 목표를 설명하는 프롬프트를 작성하세요.
